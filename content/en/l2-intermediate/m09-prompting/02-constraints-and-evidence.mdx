## Objectives & prerequisites

By the end of this lesson you can:

- Separate the three things a good prompt carries: constraints (where not to go), acceptance criteria (when to stop), and the proof you want back.
- Write a prompt whose "done" condition a machine can evaluate, not one you have to eyeball.
- Ask for evidence — the command and its output — instead of accepting an assertion that the work succeeded.
- Show, from two headless envelopes, that an unconstrained version of the same task burns its whole turn budget without finishing.

**Prerequisites.** Lesson `01-task-decomposition` in this module, and a working `claude -p` run. The lab edits files, so you need a scratch clone you do not mind changing.

<WhenNotToUse>
  Constraints narrow the search. When you genuinely do not know what good looks like — you are
  exploring an unfamiliar module, or you want to see how Claude reads the problem before you box it
  in — piling on acceptance criteria just encodes your current guess and hides the alternatives. Ask
  the open question first, then constrain the follow-up. Constraints also cost nothing to state and
  everything to state wrongly: a criterion that is not actually true of your project ("all tests
  must pass") will send the agent chasing pre-existing failures that have nothing to do with your
  task.
</WhenNotToUse>

## Concept

### The three things that are not the same

It is easy to collapse these into "be specific". They do different jobs.

| Element                 | Answers                | Failure when missing                                           |
| ----------------------- | ---------------------- | -------------------------------------------------------------- |
| **Constraint**          | Where must you not go? | Scope creep — files you did not want touched, a new dependency |
| **Acceptance criteria** | When are you finished? | The agent stops when the work _looks_ done                     |
| **Proof**               | What must you show me? | You get "it works" and have to re-run the check yourself       |

The official guidance is blunt about the middle one: Claude stops when the work looks done, and without a check it can run, "looks done" is the only signal available — which makes _you_ the verification loop, so every mistake waits for you to notice it. Give it something that returns a pass or fail and the loop closes on its own.

The third one is a separate ask. The docs put it plainly: have Claude show evidence rather than asserting success — the test output, the command it ran and what it returned, or a screenshot of the result. Reviewing evidence is faster than re-running the verification yourself, and it works for sessions you were not watching.

### What counts as a check

Anything that returns a signal Claude can read in the conversation: a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot compared against a design. "It reads better now" is not a check. "`npm test` reports 16 passed" is.

The docs also rank how hard the check gates the stop, from cheapest to most reliable: asking for the check in the same prompt; setting it as a `/goal` condition that a separate evaluator re-checks after every turn; a `Stop` hook that blocks the turn from ending until a script passes; or a second opinion from a verification subagent. Every step trades setup for attention. This lesson is about the first one, which works on any task today.

### This lesson's example prompt

```text
Add exactly one test to test/overdue.test.ts: isOverdue must return false when
the task has no dueDate. Constraints: follow the injectable-clock style already
used in that file, change nothing under src/, add no new dependency.
Then run 'npm test' and quote its final summary lines as proof the whole suite
still passes.
```

Every clause earns its place. "Exactly one test" and the named file are the target. "Change nothing under `src/`" and "no new dependency" are the constraints — the two ways this task most plausibly goes wrong. "Follow the injectable-clock style already used in that file" points at an existing pattern instead of describing one, which the docs list as its own strategy. And the last sentence is the proof: not "make sure the tests pass", but _quote the summary lines_.

"Add a test for `isOverdue`" is not an unreasonable sentence to say to a colleague — and that is why it is worth running. The agent has to decide which of the function's behaviours is untested, which file the test belongs in, what style to match, and whether to run anything afterwards. Six turns of deciding produced `error_max_turns` and, crucially, **no `result` field at all**. A script consuming that envelope gets an exit code of 1 and nothing to read.

The constrained run made the same decisions in advance, and its `result` ends with the block the docs ask for — the actual output:

```text
 Test Files  4 passed (4)
      Tests  16 passed (16)
```

That block is the run’s own output, not a claim about it — which is the difference between "the tests pass" and evidence. Run `npm test` yourself before step 2 and you can compare the counts directly.

<Callout>
  The turn budget is a real constraint too. Six turns was enough for the constrained run and not
  enough for the unconstrained one — so `--max-turns` is worth setting deliberately in scripts, and
  worth raising before you conclude a prompt failed. Lesson `03-iterative-refinement` shows a case
  where the same prompt fails at 6 turns and succeeds at 10.
</Callout>

## Anti-patterns

Items below that name a documentation page are sourced from it; the rest are this site's own observations (D080).

**Asserting instead of proving.** Accepting "I added the test and everything passes" leaves you with a claim. _Fix:_ ask for the command and its output, and read the output.

**A criterion nobody can evaluate.** "Make it robust", "handle edge cases properly", "production-ready" — none of these has a pass/fail. _Fix:_ name the case and the expected value: `isOverdue` returns `false` when `dueDate` is undefined.

**Constraints that arrive after the diff.** Saying "oh, and don't touch `src/`" once the edits exist means a rewrite. _Fix:_ constraints go in the first prompt; they are cheap to state and expensive to retrofit.

**Confusing a constraint with a criterion.** "Don't add dependencies" never tells the agent it is finished. A prompt made only of prohibitions has no stopping condition. _Fix:_ pair every set of constraints with at least one criterion.

**A criterion that was already failing.** "All tests must pass" in a repository with a known-red test sends the agent off fixing something you did not ask about. _Fix:_ scope the criterion to the suite or file your change affects, or fix the red test first.
