## Objectives & prerequisites

By the end of this lesson you can:

- Name ten prompting anti-patterns, recognise each from its symptom, and apply its fix.
- Say, for any one of them, whether it comes from the official documentation or from this site's own observation — and why that distinction matters.
- Demonstrate the most expensive of them, unbounded exploration, and its fix, from two headless envelopes.

**Prerequisites.** Lessons `01`–`04` of this module. The anti-patterns are the same catalogue read backwards, so the fixes will already be familiar.

<WhenNotToUse>
  A list of anti-patterns is a diagnostic aid, not a style guide. Do not run every prompt through
  all ten before sending it — most prompts are one sentence to a colleague and the cost of getting
  one wrong is one more sentence. Reach for the list when a session went badly and you want to know
  why, or when a prompt is going into a script where nobody will be watching. The official guidance
  makes the same point about its own patterns: they are starting points that work well in general,
  not rules, and sometimes a vague prompt is exactly right because you want to see how Claude
  interprets the problem before constraining it.
</WhenNotToUse>

### 1. The kitchen sink session

_Source: best-practices, "Avoid common failure patterns"._ You start with one task, ask something unrelated, then go back to the first task. Context is now full of irrelevant information.

**Fix:** `/clear` between unrelated tasks.

### 2. Correcting over and over

_Source: best-practices._ Claude does something wrong, you correct it, it is still wrong, you correct again. Context is polluted with failed approaches.

**Fix:** after two failed corrections, `/clear` and write a better initial prompt incorporating what you learned.

### 3. The over-specified CLAUDE.md

_Source: best-practices._ If your `CLAUDE.md` is too long, Claude ignores half of it because important rules get lost in the noise. The tell: Claude keeps doing something you have a rule against.

**Fix:** prune ruthlessly. For each line ask whether removing it would cause a mistake; if not, cut it, or convert it into a hook — hooks are deterministic where `CLAUDE.md` instructions are advisory.

### 4. The trust-then-verify gap

_Source: best-practices._ Claude produces a plausible-looking implementation that does not handle edge cases, and you accept the claim rather than the proof.

**Fix:** always provide verification — tests, scripts, screenshots. If you cannot verify it, do not ship it.

### 5. The infinite exploration

_Source: best-practices._ You ask Claude to "investigate" something without scoping it; it reads hundreds of files and fills the context.

**Fix:** scope investigations narrowly, or delegate them to a subagent so the exploration does not consume your main context. The lab below measures this one.

### 6. No verification criteria

_Source: best-practices, the "Give Claude a way to verify its work" table._ "Implement a function that validates email addresses" states a goal with no pass/fail.

**Fix:** supply the cases and the check in the same prompt, the way the docs' own "after" column does — name the example inputs and their expected results, and say to run the tests after implementing.

### 7. Symptom instead of root cause

_Source: best-practices, the same table._ "The build is failing" hands over a symptom and invites a fix that suppresses it.

**Fix:** paste the error, say what "fixed" looks like, and ask explicitly for the root cause rather than a suppression.

### 8. Chasing every reviewer finding

_Source: best-practices, the callout under "Add an adversarial review step"._ A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Fixing all of them leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that cannot happen.

**Fix:** tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional.

### 9. Dictating instead of delegating

_Source: how-claude-code-works, "Delegate, don't dictate"._ Listing which files to open and which commands to run turns an agent into a slow macro, and throws away the part it is good at.

**Fix:** think of delegating to a capable colleague — give context and direction, then let Claude work out the details. The docs' own example gives the symptom, the area of the code, and nothing else.

### 10. The unanswerable question

_**Observation** — this site's own finding, from the runs captured in this module; not official guidance._ In an unattended run, a prompt vague enough to make Claude ask you a clarifying question ends the turn with nothing done, because there is nobody to answer. It does not look like a failure: the envelope reports `"subtype": "success"`. Two lessons in this module recorded it — `01`'s vague prompt spent five turns and closed with "which direction do you want?", and `03`'s "that's not right, try again" spent four turns and closed with three clarifying questions.

**Fix:** before a prompt goes into a script, ask what the agent would need to ask you — and answer it in the prompt. Interactively the same prompt is fine; the question is cheap when someone is there to answer it.

### This lesson's example prompt

```text
Scope: src/api/server.ts only. List every HTTP route it defines as a markdown
table with method, path, and the status codes it can return. Do not read any
other file, and do not suggest changes.
```

This is anti-pattern 5's fix written out: a scope with a boundary, an output shape, and two explicit prohibitions.

That ratio is the whole argument for scoping.

The scoped result is worth reading closely for a second reason. Its last note says that for `POST /tasks/:id/done` a missing task is not explicitly checked before `markDone` is called, so the exact status code depends on behaviour in `store.ts` — "not read per scope restriction, so its exact status is unconfirmed from this file alone". The boundary you set was respected, and the answer told you where the boundary limited it. A scoped prompt that reports its own blind spot is doing exactly what you want; a scoped prompt whose answer silently omits the uncertainty is worse than an unscoped one.

## Anti-patterns

The ten above are the subject of this lesson. These are the mistakes people make with the list itself.

**Running every prompt through all ten.** Turning a diagnostic aid into a checklist makes ordinary requests expensive to write. _Fix:_ use it after a bad session, or before a prompt goes into a script.

**Treating "vague" as always wrong.** The docs say a vague prompt can be exactly right when you are exploring and can afford to course-correct. _Fix:_ ask whether anyone is there to course-correct. If not, the vagueness is the bug.

**Citing an observation as official guidance.** Anti-pattern 10 is this site's finding, not Anthropic's; presenting it as documented weakens the nine that are. _Fix:_ keep the label when you quote it.

**Fixing the prompt when the problem is the context.** A polluted session makes good prompts behave badly, and no rewording repairs it. _Fix:_ check `/context`, then `/clear`.

**Learning the list and not the reason.** The ten collapse into two ideas — bound the work, and give it something to verify against. _Fix:_ if you can state which of the two an anti-pattern violates, you will recognise the eleventh when you meet it.
