## Objectives & prerequisites

By the end of this lesson you can:

- Turn a one-line request into a numbered set of steps that each name a file, a change and a check.
- Decide when to ask for a plan first and when planning is pure overhead.
- Enter plan mode deliberately, from a keybinding or from the command line.
- Run the same task twice — once with a vague prompt, once with a decomposed one — and read the difference out of a `claude -p --output-format json` envelope instead of arguing about it.

**Prerequisites.** You can run `claude` in a project directory and you have seen a headless run (`claude -p`) at least once — L1 `m01-start` covers both. You do not need the course lab repository checked out at a tag: this module has no lesson tags yet, so its labs run against a fresh clone of the lab repo's `main` branch.

<WhenNotToUse>
  Decomposition costs you the time it takes to write the steps, and it narrows what Claude will
  consider. Skip it when the scope is clear and the fix is small — the docs say plainly that if you
  could describe the diff in one sentence, skip the plan. Skip it too when you are exploring rather
  than building: a deliberately open prompt like "what would you improve in this file?" surfaces
  things you would not have thought to ask about, and a decomposed version of that prompt can only
  return the answers you already imagined.
</WhenNotToUse>

## Concept

### Why an agent needs steps, not a wish

Claude Code works a loop: **gather context, take action, verify results**, repeating until the task is done. The loop needs two things from you that a chat window does not: something concrete to act on, and something to check the action against. A request like "improve the task tracker" gives it neither. The model can gather context all day and never reach a point where it can say the work is finished.

The official guidance names the two halves separately. "Give Claude a way to verify its work" is about the check; "Provide specific context in your prompts" is about the target. Decomposition is what you do when a task is too big to satisfy both in one sentence — you cut it into pieces that each have a target and a check.

A decomposed step has three parts:

| Part   | Question it answers           | Example                                                   |
| ------ | ----------------------------- | --------------------------------------------------------- |
| Target | Which file or symbol changes? | `src/store.ts`, the `listTasks` filter                    |
| Change | What is different afterwards? | accepts a new `"overdue"` status value                    |
| Check  | What proves it worked?        | a new case in `test/store.test.ts` with an injected clock |

If a step cannot name a check, it is not a step yet — it is a wish, and it belongs in the plan-first phase below.

### Ask for the plan before the diff

The docs recommend a four-phase workflow: **explore, plan, implement, commit**. The first two happen in plan mode, where Claude reads files and proposes a plan but makes no edits until you approve. Enter it by pressing `Shift+Tab` until the status bar shows `⏸ plan mode on`, or start the session with `claude --permission-mode plan`.

Plan mode is the interactive route. The route this lesson's lab uses is simpler and works anywhere: ask for the plan in the prompt itself, and forbid edits in the same breath. "Do not edit any file … output a numbered plan … stop after the plan" is a decomposition request that a headless run can satisfy and that you can read in one screen.

Planning is most useful when you are uncertain about the approach, when the change spans several files, or when you do not know the code being modified. Those three conditions are also exactly when decomposition pays for itself.

### This lesson's example prompt

```text
Goal: add a 'labtrack overdue' subcommand that lists only overdue tasks.
Do not edit any file. Read src/store.ts and src/cli.ts, then output a numbered
plan: for each step, the file it touches, the change, and the test that would
prove it works. Stop after the plan.
```

Read it against the table above: the goal is one sentence, the boundary (`do not edit`) is explicit, the entry points are named so exploration cannot sprawl, and the output shape — file, change, test, per step — forces every step to carry its own check.

The two envelopes report the same `num_turns` — five apiece. That is the point worth keeping. Decomposition did not make the run cheaper or shorter; it made the five turns land somewhere useful. The vague run read the repository, correctly worked out that `main` is the clean baseline, and then stopped to ask which of three directions you meant. In a terminal you would answer. In a `-p` run, nobody is there, and the turn budget is simply spent.

The decomposed run's `result` is a plan you could hand to a colleague: a `listOverdue` query in `src/store.ts` reusing the existing `isOverdue`, a thin `runOverdue` wrapper plus a registered `overdue` command in `src/cli.ts`, and for each of them the test that would prove it — with the existing fake-timer pattern in `test/overdue.test.ts` named as the model to follow. Nothing was edited, exactly as the prompt required.

Both envelopes also record a `permission_denials` array. The vague run has two entries in it, both `Bash` calls trying to run `npm test` — the allowlist for this lab was `Read,Grep,Glob`, so they were denied. That is worth noticing for two reasons: the run reached for a check nobody had asked it for, and the transcript shows the denial rather than hiding it, so you can always tell what a run tried to do and was stopped from doing.

### Entering plan mode instead

When you are working interactively rather than headlessly, plan mode does the same job with less typing.

`claude --permission-mode plan` starts a session in it, on every platform. Mid-session, press `Shift+Tab` until the status bar shows `⏸ plan mode on`; `Ctrl+G` opens the proposed plan in your editor so you can cut steps before Claude proceeds.

## Anti-patterns

Items below that name a documentation page are sourced from it; the rest are this site's own observations (D080).

**Asking for an improvement instead of a change.** "Improve the task tracker", "clean this up", "make it better" — the agent has no target and no check, so it either guesses or asks. _Fix:_ name the behaviour that should be different afterwards.

**Decomposing into steps with no checks.** A numbered list is not a decomposition if the numbers are just phases ("1. understand the code 2. write the code 3. test"). _Fix:_ every step names a file, a change and the check that proves it.

**Planning a one-line change.** Plan mode and plan-first prompts add a round trip. On a typo, a log line or a rename they buy nothing. _Fix:_ if you could describe the diff in one sentence, ask for the diff.

**Leaving the exploration unbounded.** "Read the codebase, then plan" invites the agent to read everything; the docs call this the infinite exploration failure. _Fix:_ name the entry points — `src/store.ts` and `src/cli.ts` in this lesson's prompt — or delegate the exploration to a subagent.

**Letting the plan drift into edits.** Without an explicit boundary, a plan request often ends with files already changed, and you lose the review step you asked for. _Fix:_ say "do not edit any file" and "stop after the plan", or use plan mode, which enforces it.
