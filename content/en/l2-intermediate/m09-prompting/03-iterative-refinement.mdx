## Objectives & prerequisites

By the end of this lesson you can:

- Write a correction that carries the defect, the requirement and the check — rather than a verdict.
- Recognise the point at which refining costs more than restarting, and act on it with `/clear`.
- Use `Esc`, `Esc Esc` / `/rewind` and "undo that" to steer without losing the useful part of a session.
- Reproduce a refinement loop headlessly with `--resume` and `--fork-session`, so two different second turns start from exactly the same first turn.

**Prerequisites.** Lessons `01-task-decomposition` and `02-constraints-and-evidence` in this module. The lab resumes a session by id, so you need a `claude -p --output-format json` run whose `session_id` you can capture.

<WhenNotToUse>
  Refinement assumes the first attempt left something worth keeping. When the agent solved the wrong
  problem outright, or when you have already corrected the same issue twice, the context is now full
  of failed approaches and every further correction competes with them. The docs are explicit: after
  two failed corrections, run <code>/clear</code> and write a better initial prompt that
  incorporates what you learned. A clean session with a better prompt almost always outperforms a
  long session with accumulated corrections.
</WhenNotToUse>

## Concept

### A correction is a prompt, not a verdict

"That's not right" tells the agent that its output failed some test it cannot see. It has your judgement and none of your reasons, so its only rational moves are to guess or to ask — and in an unattended run, asking ends the turn with nothing done.

A useful correction has the same shape as a good first prompt, minus the parts already established:

| Part                | What it carries                              |
| ------------------- | -------------------------------------------- |
| **The defect**      | What is actually wrong with what it produced |
| **The requirement** | What must be true instead                    |
| **The check**       | The command whose output will settle it      |

You do not always know the defect — that is fine. You can still state the requirement and the check, and let the agent find the gap itself. The lab below does exactly that.

### Steering, cheaply

Interactively you have controls that a headless run does not, and the docs recommend reaching for them early: the best results come from tight feedback loops, and correcting quickly generally produces better solutions faster.

- **`Esc`** stops Claude mid-action. Context is preserved, so you can redirect.
- **`Esc Esc` or `/rewind`** opens the rewind menu: restore the previous conversation and code state, or summarize from a selected message.
- **"Undo that"** has Claude revert its own changes.
- **`/clear`** resets context between unrelated tasks.

Typing a correction and pressing `Enter` without stopping the running tool also works — Claude reads it as soon as the current action completes and adjusts before deciding its next step.

### Sunk-cost drift

The failure this lesson is named after: you have invested twenty turns, so you keep refining rather than restarting, and each correction adds another failed approach to the context that the next correction has to compete with. The docs describe both the symptom and the threshold — if you have corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Two is the number to remember.

### This lesson's example prompt

```text
Not done yet. Two requirements: (1) 'labtrack list --json' must print valid JSON
and nothing else on stdout. (2) Prove it: run the command and pipe stdout through
node -e "JSON.parse(require('fs').readFileSync(0,'utf8'));console.log('parsed ok')",
then quote the exact output you got.
```

Notice that it never says what is wrong. It states the requirement and hands over an executable check — which is enough, because the check can find the defect that you could not name.

Three things in those recordings are worth stopping on.

**The vague correction returned questions, not code.** Its `result` lists three readings of "that's not right" — which array, which format, which empty-case behaviour — and says it does not want to guess and rework the wrong thing. That is the correct behaviour and a wasted turn: in a headless run there is nobody to answer, and four turns bought you a clarifying question you could have answered in the prompt.

**The recording mentions a commit that is not the agent's.** The vague run's result begins by noting that the `tmp first pass` commit is not its own, since it never ran `git commit`. That commit is the snapshot from step 2 of the lab — the harness that lets both follow-ups start from identical state. It is left in the transcript because a captured session is never edited to look tidier (D070, D093); it is also a genuine lesson in how much of your environment an agent notices.

**Running out of turns is not failing.** The specific correction hit `error_max_turns` at `--max-turns 6`: it exhausted the budget before returning a result, so its envelope carries an `errors` array and no `result`. The same fork with `--max-turns 10` finished in seven turns — two more than the ceiling that had stopped it — and quoted the check’s output:

```text
parsed ok
```

along with the raw `list --json` line it had parsed. Before you conclude a correction was wrong, check whether it simply ran out of room: `subtype` tells you which happened.

## Anti-patterns

Items below that name a documentation page are sourced from it; the rest are this site's own observations (D080).

**Correcting with a verdict.** "Nope", "still wrong", "try again" transfer your conclusion and none of your evidence. _Fix:_ state the requirement and the check even when you cannot name the defect.

**Refining past the second correction.** Three corrections on the same issue means the context now contains three failed approaches, and each one competes with your next instruction. _Fix:_ `/clear` and rewrite the initial prompt with what you learned.

**Re-reading the whole file in every follow-up.** Pasting the current state back into a follow-up doubles the context for information the session already holds. _Fix:_ refer to what changed; the session remembers the rest.

**Treating `error_max_turns` as a bad answer.** A run stopped by its own ceiling looks like a failed prompt and is not one. _Fix:_ read `subtype`, raise `--max-turns`, and re-run before you rewrite anything.

**Refining a task that should have been restarted.** If the first attempt solved a different problem, no correction repairs the framing. _Fix:_ `/rewind` or `/clear`, and write the prompt you should have written.
