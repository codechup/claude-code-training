## Objectives & prerequisites

By the end of this lesson you can:

- Navigate the official prompt library by phase and category, and say where its prompts come from.
- Read a templated prompt as a pattern — a verb, a target slot and an output-shape slot — rather than as a sentence to copy.
- Fill a template's slots for your own project without losing the part that made it work.
- Show, from two headless runs, what the filled template buys over the bare verb.

**Prerequisites.** Lessons `01`–`03` of this module. Some familiarity with a codebase you can point a prompt at.

<WhenNotToUse>
  A library prompt is a starting point that someone else's project shaped. Do not reach for one when
  your task is genuinely specific to your codebase — the closest-matching template will quietly push
  you toward the task it was written for. And never paste a template with its example slot values
  still in it: <code>src/scheduler/queue.ts</code> is the library's placeholder, not a file in your
  repository, and a prompt naming a file that does not exist starts the session with a contradiction
  to resolve.
</WhenNotToUse>

## Concept

### What the library actually is

The prompt library is a page of **copy-paste prompts for Claude Code, tagged by task and role**. As verified on 2026-09-07 it carries **52 prompts**, grouped into five software-lifecycle phases — Discover, Design, Build, Ship, Operate — and then by category within each: Onboard, Understand, Plan, Prototype, Implement, Test, Refactor, Review, Steer, Git, Release, Debug, Incident, Data, Automate. Some are additionally tagged for non-engineering roles (pm, design, docs, marketing, data, ops, security).

Each entry also records where it came from. Counted on 2026-09-07 the breakdown is: Common workflows 23, an Anthropic teams-usage article 13, Best practices 10, and six more from three smaller sources. A library prompt is therefore usually a workflow recipe compressed into one line, which is why Common workflows and Best practices are cited alongside the library here.

### The anatomy of a template

Most entries are not fixed sentences. They contain **slots**, written in braces, with an example value attached. Here is one, verbatim from the library:

```text
explain what {path} does and how data flows through it. write it up as {format}
```

with the library's own example slot values `path: src/scheduler/queue.ts` and `format: an HTML page with a diagram, then open it in my browser`.

Three things are doing work, and it is worth naming them separately:

| Element             | In this template                | Why it matters                                               |
| ------------------- | ------------------------------- | ------------------------------------------------------------ |
| A verb with a scope | `explain what {path} does`      | Bounds the exploration to one file instead of the repository |
| A second question   | `and how data flows through it` | Asks for relationships, not just a description               |
| An output shape     | `write it up as {format}`       | Fixes the form of the answer, so the result is usable as-is  |

The pattern generalises past this one entry: **verb + bounded target + explicit output shape**. That is the shape you are borrowing. The words are incidental.

### Adapting rather than copying

Filling slots well means substituting _your_ values for all three parts:

- **Target:** a real path in your repository. `src/store.ts`, not the library's `src/scheduler/queue.ts`.
- **Output shape:** something you can act on. The library suggests an HTML page with a diagram; if you only want to read the answer in your terminal, ask for a markdown table and say what its columns are.
- **Anything the library could not know:** your project's conventions, the constraint that matters here, the reviewer you are writing for.

Other entries reward the same reading. `where do we {behavior}?` is a search bounded by domain language. `what would break if I deleted {target}?` is an impact analysis with a built-in stopping condition. `look through the commit history of {path} and summarize how it evolved and why` points at a source — the git history — rather than asking the model to speculate, which the best-practices page lists as its own strategy.

### This lesson's example prompt

```text
explain what src/store.ts does and how data flows through it. write it up as a
markdown table of exported functions with their inputs, what they mutate, and
their callers
```

Every slot is filled with something real: a file that exists, and an output shape whose columns are named. The columns are the interesting part — "what they mutate" and "their callers" are questions about the file's relationships, and naming them as columns forces the answer to contain them.

"Explain the code" has a verb and nothing else — no target, no output shape — and it spent all six turns deciding what "the code" meant, ending in `error_max_turns` with no result to return.

The filled template came back in five turns with the table it was asked for. Read its content and you can see each slot paying off: the target slot kept the reading to one file plus the call sites it needed, and the output-shape slot produced columns — inputs, what is mutated, callers — that turned a description into something you could review. It also volunteered the data-flow paragraph the middle clause asked for: that the CLI hydrates the in-memory array from disk at startup while the API starts empty each run.

That is the general lesson of the library. The prompts are not magic words; they are a reminder to always supply a bounded target and an output shape.

## Anti-patterns

Items below that name a documentation page are sourced from it; the rest are this site's own observations (D080).

**Copying a template with its example slots intact.** Asking about `src/scheduler/queue.ts` in a repository that has no such file starts the session with a contradiction. _Fix:_ substitute a real path before you press Enter.

**Treating the library as an incantation list.** Hunting for "the right prompt" instead of writing a bounded one for the task in front of you. _Fix:_ borrow the shape — verb, bounded target, output shape — and write your own sentence.

**Dropping the output shape.** The slot that most often gets cut is `{format}`, and it is the one that makes the answer usable. _Fix:_ always say what form you want the answer in, and for tables name the columns.

**Picking the nearest template instead of the right pattern.** A Debug-phase prompt applied to a Design-phase question drags the session toward symptoms. _Fix:_ pick the phase first — Discover, Design, Build, Ship, Operate — then the category.

**Citing a community prompt collection as if it were the official one.** Unofficial lists drift from current behaviour and can name flags that no longer exist. _Fix:_ start from the official library, and check any borrowed prompt's flags against the docs.
