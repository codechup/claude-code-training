## Objectives & prerequisites

By the end of this lesson you can:

- Hold the model constant and vary only effort, so the numbers you get are about effort.
- Read `thinking_tokens` out of an envelope and use it as the direct evidence that a level changed anything.
- Recognise a null result and report it as one, instead of finding a story in the noise.
- Say when raising effort is likely to pay, and when the same money is better spent elsewhere.

**Prerequisites.** Lesson `03-effort-levels` for the levels themselves, and lesson `02-choosing-a-model` for the headless comparison method — this lab reuses it with the model held fixed.

<WhenNotToUse>
  Do not run an effort sweep to choose a level for tomorrow's work. Effort is calibrated per model
  and per task shape; a sweep on a one-line bug tells you nothing about a refactor across twelve
  files. Run the sweep when a specific, repeatable class of task is failing at your current level,
  and stop as soon as one level clears the bar. And do not sweep on a task with no automated check:
  without a test to run afterwards, you cannot tell a better answer from a longer one.
</WhenNotToUse>

## Concept

### Holding the model still

Lesson `02` varied the model and held everything else fixed. This lesson does the reverse: one model — Sonnet 5 — and three levels, `low`, `medium` and `high`. The discipline is identical. Same prompt, same starting state, same `--max-turns`, same `--allowedTools`; reset the working tree between runs; verify the outcome with `npm test` rather than with the model's summary.

Be honest about what this is. The curriculum calls for an effort-by-model matrix; what is captured below is one row of it — three levels on one model. That is enough to demonstrate the method and to produce a real finding, and it is not enough to extrapolate to Opus or Fable, whose effort scales are calibrated separately.

### The field that makes effort visible

Cost and duration move for lots of reasons. The number that moves _because_ of effort is the thinking-token count, which the envelope reports at `usage.output_tokens_details.thinking_tokens`. Thinking tokens are billed as output tokens, which is the mechanism by which a higher level costs more.

If you sweep three levels and the thinking-token counts barely move, you have learned something real: on this task, the model did not think the extra thinking was warranted. Adaptive reasoning means the model decides step by step whether to think at all — the level sets the budget, not the spend.

This lesson's example prompt is the lab's, and it is deliberately the same shape as lesson `02`'s so the two comparisons are readable side by side:

```text
npm test fails two tests in test/overdue.test.ts. Find the root cause in src/ and
fix it. Do not change any test file.
```

### The real numbers

Captured 2026-09-07 against Claude Code 2.1.263, Sonnet 5, in the order low → medium → high.

| `--effort` | `subtype` | `num_turns` | `duration_ms` | `total_cost_usd` | Output tokens | Thinking tokens | Tests after |
| ---------- | --------- | ----------- | ------------- | ---------------- | ------------- | --------------- | ----------- |
| `low`      | `success` | 6           | 68,737        | 0.1033           | 1,068         | 14              | 15 passed   |
| `medium`   | `success` | 5           | 37,849        | 0.0943           | 978           | 14              | 15 passed   |
| `high`     | `success` | 6           | 54,878        | 0.1081           | 1,275         | 53              | 15 passed   |

Every level produced the same one-line fix in `src/store.ts` — removing the stray `/ 1000` — and every run ended with all fifteen tests passing.

The finding is a null result, and it is worth more than a tidy one would be. The spread in cost across three levels is about 1.15× — roughly a cent and a half on a task that cost about ten cents. The spread in duration does not track the level at all: `medium` was the fastest run and `low` the slowest, which is the signature of ordinary run-to-run variance rather than of a dial doing work.

The thinking tokens explain why. At `low` and `medium` the model spent 14 thinking tokens; at `high`, 53. Even at the default level, on a bug this well-signposted, adaptive reasoning decided there was almost nothing to think about. Effort sets a ceiling on how hard the model may work, not a floor on how hard it must — and a failing test that names the file is about as un-ambiguous as a task gets.

There is a second-order effect visible in the table too. `high` produced the longest answer (1,275 output tokens against `low`'s 1,068) and the most detailed root-cause explanation. If what you need is a better _explanation_, effort bought you something. If what you need is a passing test, it did not.

So: raise effort when the task is genuinely ambiguous — a root-cause hunt with no failing test to anchor it, an architectural choice, a bug that reproduces only sometimes. On a task like this one, the honest recommendation is to leave the dial alone and spend the attention on the prompt.

### One honest caveat

The three `result` strings come back in Turkish, because the capture machine's global Claude Code preferences ask for Turkish. That is genuine output; the same thing happens in lesson `02`. It changes nothing about the numbers, and it is a standing reminder that your own settings ride along with every run.

## Anti-patterns

**Sweeping effort without a check to run afterwards.** Without `npm test`, all three runs "succeed" and you end up ranking prose. _Fix:_ sweep only on tasks with an automated pass/fail, and record it as its own column.

**Reading a 1.15× cost spread as a trend.** Three runs with no repetition cannot separate a small effect from noise — and here the durations are not even monotonic in the level. _Fix:_ if the difference matters, repeat each arm several times; otherwise report it as inconclusive.

**Changing two things at once.** Sweeping effort while also switching models, or while adding a hint to the prompt because the first run struggled, produces numbers about nothing. _Fix:_ one variable per sweep.

**Assuming a level name means the same thing on another model.** The effort scale is calibrated per model. `high` on Sonnet 5 is not `high` on Opus 5. _Fix:_ re-run the sweep on the model you actually intend to use.

**Concluding "effort does nothing" from one null result.** This task was small, well-posed and pointed at by a failing test — the conditions least likely to reward deeper reasoning. _Fix:_ re-run the sweep on an ambiguous task before generalising in either direction.
