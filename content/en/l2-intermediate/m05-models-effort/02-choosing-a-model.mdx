## Objectives & prerequisites

By the end of this lesson you can:

- Design a model comparison that is actually fair: identical prompt, identical starting state, identical turn budget.
- Run the same task headlessly on three models and capture machine-readable evidence with `--output-format json`.
- Read `duration_ms`, `total_cost_usd`, `num_turns`, `subtype` and `result` out of a result envelope and turn them into a decision.
- Separate the two questions people collapse into one — "did it work?" and "what did it cost?" — and measure each with the right instrument.

**Prerequisites.** Lesson `01-model-family` (aliases and what they resolve to), a clone of the lab repository, Node 24, and a terminal. The whole lab is headless, so you will not be babysitting a TUI.

<WhenNotToUse>
  This comparison is a diagnostic, not a habit. Running every task three times triples your spend to
  answer a question you usually already know: most day-to-day coding sits comfortably on Sonnet, and
  the docs say so. Run the comparison when a class of work is genuinely failing, or when you are
  setting a team default and want evidence instead of folklore — not before every task. And do not
  read a single three-run comparison as a benchmark: one bug, one repository, one prompt, one
  afternoon is an anecdote with numbers attached.
</WhenNotToUse>

## Concept

### What makes a model comparison fair

Three things have to be identical across runs, or the numbers mean nothing:

- **The starting state.** Model two must meet the same broken repository model one met. In git terms: `git checkout -- . && git clean -fd` between runs.
- **The prompt.** Byte-for-byte the same string, with no extra hint added because run one struggled.
- **The budget.** The same `--max-turns`, the same `--allowedTools`, the same permission mode.

And one thing has to be measured _outside_ the model's own report: whether the fix worked. A model saying "all tests pass" is a claim; `npm test` exiting green is evidence. That distinction is the whole point of D093 in this course, and it is exactly what separates a useful comparison from a vibe.

### The result envelope is the instrument

`claude -p … --output-format json` prints one JSON object when the run ends. The fields that carry the comparison:

| Field                | What it tells you                                                                 |
| -------------------- | --------------------------------------------------------------------------------- |
| `subtype`            | `success`, or an error kind such as `error_max_turns`                             |
| `is_error`           | Whether Claude Code considers the run to have completed                           |
| `num_turns`          | How many turns the run consumed                                                   |
| `duration_ms`        | Wall-clock time for the whole run                                                 |
| `total_cost_usd`     | Claude Code's local estimate, computed from token counts at list price            |
| `result`             | The final assistant message — present on success, absent when the run was cut off |
| `modelUsage`         | Per-model token counts, `contextWindow`, and that model's `costUSD`               |
| `permission_denials` | Every tool call your `--allowedTools` list refused                                |

`total_cost_usd` is an estimate that Claude Code computes locally from token counts at list price; the authoritative figure is the Usage page in the Claude Console. For a comparison run minutes apart on the same machine, the estimate is exactly the right instrument — you are comparing like with like.

One subtlety that makes the comparison cleaner than you might fear: each model has its own prompt cache. Switching models means the next request reads the whole conversation with no cache hits — so three consecutive runs on three models do not warm each other's caches, and run three is not unfairly cheap.

This lesson's example prompt is the one the lab uses. Notice that it names the symptom and forbids the shortcut, but does not name the file with the bug:

```text
npm test fails one test in test/persist.test.ts. Find the root cause in src/ and
fix it. Do not change any test file.
```

### The real numbers

These are the values from the three envelopes above, captured on 2026-09-07 against Claude Code 2.1.263. The "tests after" column is the writer's own `npm test`, not the model's claim.

| Run              | `subtype`         | `num_turns` | `duration_ms` | `total_cost_usd` | Tests after | Diff                                    |
| ---------------- | ----------------- | ----------- | ------------- | ---------------- | ----------- | --------------------------------------- |
| `--model haiku`  | `error_max_turns` | 7           | 60,125        | 0.0588           | 15 passed   | `src/cli.ts`, 1 insertion, 3 deletions  |
| `--model sonnet` | `success`         | 6           | 38,164        | 0.1201           | 15 passed   | `src/cli.ts`, 1 insertion, 3 deletions  |
| `--model opus`   | `error_max_turns` | 7           | 76,868        | 0.2453           | 15 passed   | `src/cli.ts`, 2 insertions, 3 deletions |

Read that table honestly, because it does not say "the expensive model is better".

**Every model fixed the bug**, and all three found the same root cause: the un-awaited `save()` call. Haiku and Sonnet each produced the same shape of change — one inserted line, three deleted, in `src/cli.ts`. Opus made the same fix and additionally replaced the now-misleading comment above it with an accurate one, which is why its diff has one more inserted line. That is a real, if small, quality difference, and the kind you only see by reading diffs rather than totals.

**Haiku was four times cheaper than Opus** on this task and finished in less wall-clock time. On a scoped bug with a failing test pointing at it, the cheapest model was entirely sufficient.

**Sonnet was the only run that finished.** Haiku and Opus both hit `--max-turns 6` — _after_ editing the file, which is why the tests pass despite `is_error: true` and no `result` string. That is a genuinely important finding: `subtype: error_max_turns` means "the budget ran out", not "the work failed", and if your automation keys off `is_error` alone it will throw away good work. The lesson is that a turn budget is a variable in the experiment, exactly like the model.

**Opus's envelope also explains part of its turn spend.** Its `permission_denials` array records a `Bash` call that was refused:

The allowlist was `Bash(npm test*)`, and the model tried to run `cd "<lab>" && npm test … && npm run typecheck … && npm run lint …`, which does not match that pattern. The denial cost a turn. That is not a model weakness; it is an experiment design flaw worth knowing about — your `--allowedTools` pattern is part of the environment you are comparing models in.

### One honest caveat about the `result` strings

The Sonnet envelope's `result` is in Turkish. That is genuine, unmodified output: the machine that captured these transcripts has global Claude Code preferences asking for Turkish answers, and a headless run loads your settings and memory like any other session. It is a useful reminder that "identical prompt" is not the same as "identical context" — your own configuration is part of every run you make.

## Anti-patterns

**Comparing models without resetting the repository.** Run two finds the bug already fixed and reports success in one turn, and you conclude the second model is faster. _Fix:_ `git checkout -- . && git clean -fd` between runs, and re-run `npm test` to confirm the failure is back.

**Trusting the `result` text as the outcome.** A model's summary is a claim about the work, generated by the thing that did the work. _Fix:_ run the tests yourself and record the exit state; that column is the only one that answers "did it work?".

**Treating `is_error: true` as "the run failed".** Two of the three runs here reported `error_max_turns` after landing a correct fix. _Fix:_ read `subtype` and `terminal_reason`, and check the working tree before discarding the run.

**Letting `--allowedTools` differ between runs.** A pattern that denies one model's tool call and permits another's makes the comparison about your allowlist, not about the models. _Fix:_ fix the allowlist first, then re-run all arms.

**Generalising one bug into a policy.** One async bug in one small TypeScript repository does not tell you which model to use for a schema migration. _Fix:_ run the comparison on work that looks like your work, and re-run it when your work changes.
