## Objectives & prerequisites

By the end of this lesson you can:

- Ask Claude to draft a pull request from a branch's commits, and get back a command rather than an opened PR.
- Write a PR body that carries evidence — the command you ran and what it printed — instead of a claim.
- Check a pull request before it exists with `gh pr create --dry-run`.
- Use a repository's `.github/PULL_REQUEST_TEMPLATE.md` as the shape Claude fills in.
- Find the session that created a PR again with `claude --from-pr <number>`.
- Say what `attribution.pr` controls.

**Prerequisites.** Lessons `01-commits-and-conventions` and `02-worktrees-branches`, the [GitHub CLI](https://cli.github.com) installed and authenticated (`gh auth login`), and a branch with at least one commit on it.

<WhenNotToUse>
  Do not let an agent open pull requests on a repository where a PR is a notification to other
  people — an open-source project you are not a maintainer of, a shared lab or fixture repository,
  anything where a stray PR costs someone else's attention. Draft locally and open it yourself. Skip
  the whole flow when the change belongs in the branch it is already on, when your team reviews by
  stacked patches or a queue rather than PRs, or when the PR would be so large that no reviewer can
  hold it — the fix for that is a smaller branch, not a better description. And never open a PR
  whose evidence section you have not personally reproduced.
</WhenNotToUse>

## Concept

### Ask for the command, not the pull request

You can create pull requests by asking Claude directly ("create a pr for my changes"). That is the fast path, and it is the right one on a repository you own once you trust the flow.

The safer default while you are learning it — and the only acceptable one on a repository you do not own — is to ask for the **command**. This lesson's example prompt does exactly that:

```text
This branch is one commit ahead of main. Read the commit and its diff, then print,
in a single fenced bash code block, the exact `gh pr create` command I should run:
--base with the right base, --title as a Conventional Commits line, and --body
containing a Summary section, a Testing section naming the exact command I ran and
its result, and a Risk line. Do not run gh.
```

You get a reviewable artefact. If the title is wrong or the risk assessment is optimistic, you edit a string instead of a live pull request.

### Evidence is a command and its output

A PR body that says "tests pass" is a claim. A PR body that says `npm test`: 4 files, 16 tests, all passed is evidence, because a reviewer can run the same command and compare. The difference costs one sentence and saves a round trip.

Three sections carry almost all of the value:

| Section     | What belongs in it                                                                 |
| ----------- | ---------------------------------------------------------------------------------- |
| **Summary** | What changed and why, in the reviewer's vocabulary — not a restatement of the diff |
| **Testing** | The exact commands you ran and what they printed                                   |
| **Risk**    | What could break, and what you checked to convince yourself it will not            |

Claude can write all three, but only the Summary and Risk from the diff alone. The Testing section has to come from a command **you** ran — which is why the lab's prompt hands Claude the test result rather than letting it guess or run one.

### Templates are the shape

A repository's `.github/PULL_REQUEST_TEMPLATE.md` is what GitHub pre-fills into the body box. It is also the best thing to hand Claude: instead of describing the sections you want, point at the file.

This training repository's own template is a worked example. It asks for the plan id and milestone, what changed, commands a reviewer can run locally, an evidence checklist that names the two viewport widths for screenshots, a Definition-of-Done checklist covering CI and scope, and handoff notes. Nothing in it is decorative — each box is a thing a reviewer would otherwise have to ask for.

The convention that goes with it: **`main` is PR-only, and every PR is squash-merged** with a Conventional Commits title carrying the plan id, such as `feat(content): m01-start lesson (P13)`. Squash-merging is what makes the branch's messy intermediate commits harmless — the title of the PR becomes the title of the single commit on `main`, which is why the PR title is worth the same care as a commit subject in lesson 01.

### Check it before it exists

`gh pr create --dry-run` prints exactly what would be created and creates nothing:

<CodeBlock title="dry-run against a template">

```bash
gh pr create --base main \
  --title "[P20] L2 Intermediate module: Git flows (m08-git)" \
  --body-file .github/PULL_REQUEST_TEMPLATE.md \
  --dry-run
```

</CodeBlock>

Read the `base:` and `head:` lines first — a PR opened against the wrong base is the most common and most annoying mistake this catches. One caveat, quoted from the GitHub CLI's own help text (captured from gh 2.96.0 in the lab below): `--dry-run` prints details instead of creating the PR, but **may still push git changes**. On a repository you do not have push access to, that push simply fails; on one you do, make sure the branch you are on is the branch you mean to publish.

### Finding the session again

Claude Code links a session to a pull request when Claude creates it with `gh pr create` or `glab mr create`. Later, from anywhere:

<CodeBlock title="reopen the session behind a PR">

```bash
claude --from-pr 1234
```

</CodeBlock>

That opens the session picker filtered to sessions linked to that pull request. Pasting the PR URL into the `/resume` picker's search does the same thing. This is the payoff for letting Claude run `gh pr create` on your own repositories: a month later, the reasoning behind the PR is still one command away.

Finally, the attribution line Claude Code adds to pull request descriptions is controlled by `attribution.pr` in settings — the PR-side sibling of `attribution.commit` from lesson 01.

## Anti-patterns

**Letting Claude open the PR on a repository you do not own.** A pull request is a notification to a maintainer. _Fix:_ ask for the command; open it yourself, if at all.

**A Testing section Claude wrote from the diff.** If Claude did not run the command, the section is a guess with a monospace font. _Fix:_ run it, paste the real result into the prompt, and tell Claude not to run tests itself.

**Ignoring the template.** Filling in your own headings when the repository ships `.github/PULL_REQUEST_TEMPLATE.md` makes every PR shaped differently and hides the checklist the reviewers rely on. _Fix:_ `--body-file .github/PULL_REQUEST_TEMPLATE.md`, then fill it in.

**A PR title that is not the commit you want on `main`.** Under squash-merge the PR title becomes the commit message on the default branch. "Fixes" is then permanent. _Fix:_ write the title as a Conventional Commits subject, exactly as in lesson 01.

**Assuming `--dry-run` is read-only.** It prints instead of creating, but it may still push git changes. _Fix:_ know which branch you are on before running it.
