## Objectives & prerequisites

By the end of this lesson you can:

- Run `/code-review` against your working tree, a PR number, a branch, a path or a ref range.
- Choose an effort level deliberately, and predict what changes between `low` and `high`.
- Say what `--fix` and `--comment` do, and why `--fix` edits are not covered by `/rewind`.
- Pick between `/code-review`, `/simplify` and `/security-review` for a given goal.
- Use `/diff` to look at the working tree without leaving the session.
- Run a review headlessly with `claude -p "/code-review …"` and read the result.

**Prerequisites.** Lessons 01–03 and a clone of the lab repository. The local `/code-review` command needs no GitHub App and no Team or Enterprise plan.

<WhenNotToUse>
  These commands review a diff; they are not a substitute for the checks that already run on every
  commit. Do not use a review pass to find what a type checker, linter or test suite would find in a
  second — configure those instead. Do not run one on a branch with nothing on it: `/code-review`
  reviews your branch's commits ahead of its upstream plus uncommitted changes, so an empty tree has
  nothing to report. Do not treat a clean review as proof of correctness — at `low` and `medium` it
  reports only the findings it is most confident in, and a clean result at `low` means exactly that
  and nothing more. And do not use it as your only security control: `/security-review` looks at a
  diff, not at your threat model.
</WhenNotToUse>

## Concept

### `/code-review` and what it looks at

`/code-review` reviews a diff in your terminal without installing the GitHub App. It reports correctness bugs and reuse, simplification and efficiency cleanups. With no argument it reviews **your branch's commits ahead of its upstream plus any uncommitted changes** — so it needs work on the branch or in the working tree to have something to say.

To review something else, pass a target: a file path, a PR number, a branch name, or a ref range such as `main...my-feature`.

<CodeBlock title="targets">

```bash
/code-review
/code-review src/store.ts
/code-review 1234
/code-review main...my-feature
```

</CodeBlock>

The review runs as a background subagent with its own context window, so it does not fill your conversation; the findings arrive when it completes. `/review` is an alias for `/code-review`.

### Effort is the coverage/confidence dial

Pass an effort level to trade coverage for confidence:

| Level           | What you get                                                                                    |
| --------------- | ----------------------------------------------------------------------------------------------- |
| `low`, `medium` | Only the findings the review is most confident in — fewer false positives                       |
| `high` … `max`  | Broader coverage, and it may include findings it is less sure about                             |
| `ultra`         | The deep multi-agent [ultrareview](https://code.claude.com/docs/en/ultrareview.md) in the cloud |

When you do not type a level, the review reuses the last level from `low` through `max` you typed — even in an earlier session — and shows a notice such as `Reusing high effort, the level you typed last time`. Type a level to change what later runs reuse; a level passed in a non-interactive `-p` run does not update it, and `ultra` neither updates nor uses the remembered level.

This is not an abstract dial. The lab below runs the same one-line diff at `low` and at `high` and gets a clean result and two findings respectively.

### Flags

| Flag        | What it does                                                                                           |
| ----------- | ------------------------------------------------------------------------------------------------------ |
| `--fix`     | Applies the findings to your working tree after the review                                             |
| `--comment` | Posts the findings as inline pull request comments                                                     |
| `--post`    | On an `ultra` cloud review of a `github.com` PR, preselects posting the findings to the PR (v2.1.227+) |

One consequence worth memorising: a **background** review applies its `--fix` edits outside your session's checkpoints, so `/rewind` does not undo them — use git to revert. When the review runs in the foreground, its edits happen during your own turn and `/rewind` restores them as usual. The review follows your `CLAUDE.md` like any session, but it does not read `REVIEW.md` (that file is for the managed GitHub Code Review product).

### Three commands, three jobs

| Command            | Job                                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `/code-review`     | Correctness bugs plus reuse, simplification and efficiency cleanups; takes an effort level, `--fix`, `--comment` and a target |
| `/simplify`        | Cleanup only — readability and maintainability, without hunting for bugs; takes an effort level, `--fix` and a path           |
| `/security-review` | Security vulnerabilities; like `/code-review` it takes a target and can apply its fixes or post them as comments              |

The split matters because it changes what you get back. `/simplify` runs a cleanup-only review and never sets out to find bugs; if you have scripted `/simplify` expecting bug-finding, the replacement is `/code-review --fix`.

And `/diff` is the fourth, smallest one: it shows you the changes in your working tree, including the edits Claude has made so far. Reach for it before any of the other three — reviewing a diff you have not looked at is how a review becomes a rubber stamp.

This lesson's example prompt is the plain-language route to the same thing — Claude can start the review itself when you ask for one:

```text
Review the change I have in the working tree before I open a PR. Be strict: I would
rather see a finding you are unsure about than miss a real one.
```

### Headless reviews

`/code-review` is a bundled skill, and skills are invocable from `-p`:

<CodeBlock title="review from a script">

```bash
claude -p "/code-review high" --model sonnet --max-turns 30 --output-format text
```

</CodeBlock>

In a `-p` run the review runs in the **foreground**: Claude Code waits for it and includes the findings in the response — with one exception, `ultra`, which launches the cloud review without waiting and prints a link. To start a cloud review from a script or CI, run `claude -p '/code-review ultra'`.

Claude can also start `/code-review` on its own when you ask for a review in plain language, and a scheduled task with `/code-review` as its prompt runs one. To keep the command available for you to type while stopping Claude and scheduled tasks from starting it, add a `skillOverrides` entry to a settings file:

<CodeBlock title="~/.claude/settings.json">

```json
{
  "skillOverrides": {
    "code-review": "user-invocable-only"
  }
}
```

</CodeBlock>

The first capture is the lesson in one screen. At `low`, the review of a correct one-line arithmetic fix returned nothing — the effort level is doing exactly what the docs say it does, reporting only high-confidence findings. At `high`, on the byte-for-byte identical diff, it confirmed the fix and then flagged two things the diff exposes but does not introduce: `page` is still unvalidated (and the fix quietly changes what `page = 0` does — previously the first page, now an empty array), and `pageSize` is unvalidated too. The prose in the first capture is Turkish because the recording machine's global Claude Code preferences ask for Turkish answers — the same standing-preferences effect the lab in lesson 01 shows. The findings themselves are language-independent: file, line, and what is wrong.

The `/security-review` capture is worth reading for its shape rather than its verdict. It says no vulnerabilities **and** why: an in-memory array slice with no user-controlled paths, queries, commands or auth logic. A security pass that returns "looks fine" with no reasoning is not a result you can act on.

## Anti-patterns

**Reading a clean `low` review as "no bugs".** `low` and `medium` deliberately withhold anything they are not confident about. _Fix:_ if the answer matters, run `high` — as the lab shows, the same diff produced nothing and then two findings.

**`--fix` on a diff you have not read.** Background `--fix` edits sit outside your checkpoints, so `/rewind` will not take them back. _Fix:_ read the findings first, or use git to revert.

**Using `/simplify` to hunt for bugs.** It is a cleanup-only review by design. _Fix:_ `/code-review --fix` when you want bugs found and fixed.

**Reviewing the wrong thing.** With no target, the review covers commits ahead of the upstream plus uncommitted changes — which on a freshly branched, freshly committed tree can be more or less than you think. _Fix:_ pass an explicit target, such as `main...my-feature`.

**Letting the remembered effort level surprise you.** A bare `/code-review` reuses the last level you typed, possibly from another session weeks ago. _Fix:_ type the level when it matters, and read the `Reusing … effort` notice when it appears.

<Callout variant="changed">
  `/simplify` was the name of today's `/code-review` before v2.1.147, when it applied fixes by
  default. It is now a separate cleanup-only review that applies fixes without hunting for bugs; if
  you scripted `/simplify` for bug-finding, switch to `/code-review --fix`.
</Callout>
