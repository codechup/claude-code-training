## Objectives & prerequisites

By the end of this lesson you can:

- Inject live project state into a session with `SessionStart` and `additionalContext`, and say where in the conversation it lands.
- Decide correctly between a `SessionStart` hook and `CLAUDE.md` for a given piece of information.
- Use the `SessionStart` matcher (`startup`, `resume`, `clear`, `compact`, `fork`) to run different work on a fresh session and a resumed one.
- Run a check — the test suite — from a `Stop` hook, and read its output in the debug log.
- Recognise what a resumed session replays and what it re-runs, so your injected context does not go stale without you noticing.

**Prerequisites.** Lessons `01`–`04`, and the lab at this lesson's tag. `npm ci` matters more here than usual: the `Stop` half of the hook shells out to the repo's own Vitest.

<CodeBlock title="get the lab">

```bash
git checkout lesson/m07-05-start
npm ci
```

</CodeBlock>

<WhenNotToUse>
  A `SessionStart` hook runs on every single session, so it is the wrong home for anything slow or
  anything static. Conventions that never change belong in `CLAUDE.md`, which loads without spawning
  a process; the docs say so directly. A `Stop` hook that runs the full suite is wrong on a
  repository where the suite takes minutes — it fires at the end of every turn, not once per task,
  so you would pay that cost per exchange. And neither event is a substitute for CI: a hook runs on
  the developer's machine, with the developer's environment, and can be disabled with one setting.
</WhenNotToUse>

## Concept

### SessionStart

`SessionStart` runs when Claude Code starts a new session or resumes one. It is for **loading development context** — open issues, recent changes, the current branch — and for setting up environment variables. Only `type: "command"` and `type: "mcp_tool"` handlers are supported.

Its matcher is how the session began:

| Matcher   | Fires when                                                                    |
| --------- | ----------------------------------------------------------------------------- |
| `startup` | New session                                                                   |
| `resume`  | `--resume`, `--continue` or `/resume`                                         |
| `clear`   | `/clear`                                                                      |
| `compact` | Auto or manual compaction                                                     |
| `fork`    | A forked session: `--fork-session`, the `/fork` background copy, or `/branch` |

That matcher is more useful than it looks. "Print the branch and the failing tests" is right for `startup`; "re-state the plan we agreed" is right for `compact`, where the conversation has just been squeezed.

The event's own output fields are:

| Field                | What it does                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------- |
| `additionalContext`  | String added to Claude's context at the start of the conversation, before the first prompt  |
| `initialUserMessage` | Becomes the first user message — in `-p`, even when no prompt is given                      |
| `sessionTitle`       | Names the session, like `/rename`                                                           |
| `watchPaths`         | Absolute paths to watch for `FileChanged` events this session                               |
| `reloadSkills`       | Re-scan skill directories after the hook finishes, so skills it installed work this session |

`SessionStart` is one of the four events where **plain stdout is added to Claude's context** (with `UserPromptSubmit`, `UserPromptExpansion` and `PostModelSwitch`), so a hook that only loads context can `echo` a string and skip JSON entirely. Use the JSON form when you need to combine context with another field, such as `sessionTitle`.

### Where additionalContext actually goes

`additionalContext` is not a chat message. Claude Code wraps the string in a **system reminder** and inserts it at the point where the hook fired — for `SessionStart`, at the start of the conversation, before the first prompt. Claude reads it on the next model request; you never see it in the interface.

Two rules follow from that, and both are in the docs:

- **Write facts, not orders.** "The deployment target is production" reads as project information. Text framed as an out-of-band system instruction can trigger Claude's prompt-injection defences, at which point Claude surfaces your text to you instead of acting on it.
- **Prefer `CLAUDE.md` for anything static.** A hook that prints an unchanging sentence is a process launch per session for something a file does for free.

There is a caveat with a sharp edge: the injected text is saved in the session transcript. When you resume with `--continue` or `--resume`, Claude Code **replays the saved text** for past turns rather than re-running the hook, so timestamps and commit SHAs from a mid-session event go stale. `SessionStart` itself does run again on resume, with `source` set to `"resume"` (or `"fork"`), which is exactly how you refresh it.

### Stop, as a checker

Lesson 04 used `Stop` to announce. Here it does work: run the test suite when the turn ends, so a session that broke something learns about it without you asking.

The lab's hook keeps that deliberately toothless — it runs Vitest and swallows the failure — because the `-start` tags of this course carry seeded bugs and a blocking Stop hook would fight every lesson. In your own repository you have three escalating options:

1. **Report only.** Run the suite, exit 0. The output goes to the debug log; the session is undisturbed.
2. **Tell Claude.** Return `hookSpecificOutput.additionalContext` — "3 tests are failing in `test/overdue.test.ts`". The conversation continues and the transcript labels it `Stop hook feedback`.
3. **Refuse to stop.** `{"decision": "block", "reason": "…"}`, or exit 2 with the reason on stderr. Claude keeps working. Read `stop_hook_active` first and exit early when it is `true`, or you will hit the eight-consecutive-block cap from lesson 04.

### One script, two events

Registering the same script on both events and branching on `hook_event_name` keeps the pair together:

<CodeBlock title=".claude/hooks/session-context.mjs (the shape)">

```javascript
const event = input.hook_event_name ?? '';

if (event === 'SessionStart') {
  console.log(
    JSON.stringify({
      hookSpecificOutput: {
        hookEventName: 'SessionStart',
        additionalContext: `claude-code-lab: a tiny task-tracker CLI + HTTP API. ${bugCount} entries in BUGS.md. Run "npm test" to see current pass/fail.`,
      },
    }),
  );
  process.exit(0);
}

if (event === 'Stop') {
  try {
    execFileSync(process.execPath, ['node_modules/vitest/vitest.mjs', 'run'], {
      cwd: root,
      stdio: 'inherit',
    });
  } catch {
    // A failing suite is expected on most -start tags — never block Stop over it.
  }
  process.exit(0);
}
```

</CodeBlock>

This lesson's worked example prompt exists to prove the injection, by forbidding the obvious alternative:

```text
Without reading any files, tell me what this project is and how many entries BUGS.md has.
Answer only from the context you were already given.
```

That capture has an accident in it that is better than the clean version would have been.

`BUGS.md` is not present at this tag, so the hook's count fell through to its `"unknown"` fallback — and Claude's answer says so, quoting the hook: _"the SessionStart hook explicitly reports 'unknown entries in BUGS.md'"_. Three things are proven at once. The hook ran. Its `additionalContext` reached the model as readable text. And the model is willing to tell you where a fact came from and where it ran out — which is precisely the behaviour you want from injected context, and precisely why it should be phrased as facts rather than instructions.

The debug lines complete the picture. `Hook SessionStart:startup (SessionStart) success` shows the matcher that fired (`startup`); `provided additionalContext (158 chars)` confirms Claude Code accepted the string; and the `Hook Stop` entry carries the Vitest summary — `Test Files 4 passed (4)`, `Tests 15 passed (15)` — captured from a process that ran after the answer was written, without anyone asking for tests.

### What to put in the context string

Good candidates change between sessions and are cheap to compute:

<OSTabs>
  <Fragment slot="macos">

```bash
git rev-parse --abbrev-ref HEAD          # current branch
git status --porcelain | head -20        # uncommitted work
gh issue list --assignee @me --limit 5   # what you are on the hook for
```

  </Fragment>
  <Fragment slot="linux">

```bash
git rev-parse --abbrev-ref HEAD          # current branch
git status --porcelain | head -20        # uncommitted work
gh issue list --assignee @me --limit 5   # what you are on the hook for
```

  </Fragment>
  <Fragment slot="windows">

```powershell
git rev-parse --abbrev-ref HEAD                    # current branch
git status --porcelain | Select-Object -First 20   # uncommitted work
gh issue list --assignee @me --limit 5             # what you are on the hook for
```

  </Fragment>
</OSTabs>

Bad candidates are the ones that belong in a file: coding conventions, the test command, directory layout. If the sentence would be identical next month, put it in `CLAUDE.md`.

## Anti-patterns

**A slow `SessionStart` hook.** Every session pays it, including the ones where you only wanted to ask a quick question. _Fix:_ keep it to cheap local commands; move anything network-bound behind a cache or drop it.

**Static text in a hook.** "This repo uses pnpm" does not change. _Fix:_ `CLAUDE.md`.

**Writing the context as instructions.** "You must always run npm test before answering" reads as an out-of-band system command and can trip prompt-injection defences, so Claude shows it to you instead of following it. _Fix:_ state facts — "the test command is `npm test`" — and leave the instructions to `CLAUDE.md` and your prompt.

**Assuming resumed sessions re-run everything.** Mid-session `additionalContext` is replayed from the transcript on `--resume`, so a timestamp injected an hour ago comes back unchanged. _Fix:_ put volatile facts in the `SessionStart` hook, which does re-run on resume, and keep them out of `PostToolUse`.

**A blocking `Stop` test-runner on a repo with a slow or flaky suite.** It fires at the end of every turn and can only block eight times before it is overridden. _Fix:_ report first (option 1), graduate to `additionalContext` (option 2), and only block when the check is fast and deterministic.
