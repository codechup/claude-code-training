## Objectives & prerequisites

By the end of this lesson you can:

- Write a `PostToolUse` hook that runs a formatter on the file Claude just wrote or edited.
- Pull the edited path out of `tool_input.file_path` and skip everything you should not touch.
- Explain why a formatter hook must end in exit 0 on every path, including its failure paths.
- Verify a hook whose stdout you never see, by checking its effect rather than its output.
- Decide when to format silently and when to tell Claude what you changed.

**Prerequisites.** Lessons `01-hook-anatomy` and `02-block-dangerous-commands`, and the lab repository at this lesson's tag:

<CodeBlock title="get the lab">

```bash
git checkout lesson/m07-03-start
npm ci
```

</CodeBlock>

The `-start` tag already contains the guard hook you wrote in lesson 02, so `.claude/settings.json` exists and you are adding a second event to it rather than creating the file.

<WhenNotToUse>
  Skip the formatter hook when your editor already formats on save and Claude's edits go through the
  same files — you would be paying for a process launch per edit to do work that is already done.
  Skip it when the repository has no agreed format, because a hook that reformats every file Claude
  touches turns a two-line change into a 200-line diff nobody can review. And do not use
  `PostToolUse` for anything that must _prevent_ a bad edit: the tool has already run by then, and
  the docs are blunt that `PostToolUse` hooks cannot undo actions. Validation belongs in
  `PreToolUse`.
</WhenNotToUse>

## Concept

### PostToolUse in one paragraph

`PostToolUse` fires **after a tool call succeeds** (its sibling `PostToolUseFailure` fires when one fails). The input carries the usual common fields plus `tool_name`, `tool_input`, `tool_use_id` and `tool_response`. It cannot block: exit 2 does not undo the tool call, though it does show your stderr to Claude — which is the supported way to put a warning in front of the model after the fact. The event's own decision fields are the top-level `decision: "block"` / `reason` pair (feedback, not a rollback) and `hookSpecificOutput.additionalContext`.

For a formatter, none of that matters. You want the hook to be invisible: format the file, exit 0, say nothing.

### Getting the path

For `Write` and `Edit`, the file is at `tool_input.file_path`, and it is absolute. The lab hook resolves it, then applies four filters before it spends a process on Prettier:

1. the tool is `Write` or `Edit` (a matcher already narrows this, but a hook that is also correct on its own is a hook you can move);
2. the path is inside the repository — `relative(root, abs)` must not start with `..`;
3. the extension is one Prettier handles here (`.js`, `.json`, `.md`, `.mjs`, `.cjs`, `.ts`, `.yaml`, `.yml`);
4. the file exists, and `node_modules/prettier` exists.

<CodeBlock title=".claude/hooks/format-on-save.mjs (the shape)">

```javascript
const tool = input.tool_name ?? '';
if (tool !== 'Write' && tool !== 'Edit') return;

const filePath = input.tool_input?.file_path;
if (typeof filePath !== 'string' || filePath.length === 0) return;

const abs = isAbsolute(filePath) ? filePath : resolve(input.cwd ?? root, filePath);
const rel = relative(root, abs).replace(/\\/g, '/');
if (rel.startsWith('..') || rel.length === 0) return; // not inside this repo

if (!KNOWN.has(extname(abs).toLowerCase())) return;
if (!existsSync(abs)) return;

const prettier = join(root, 'node_modules', 'prettier', 'bin', 'prettier.cjs');
if (!existsSync(prettier)) return; // dependencies not installed yet

spawnSync(process.execPath, [prettier, '--write', '--ignore-unknown', rel], {
  cwd: root,
  encoding: 'utf8',
});
```

</CodeBlock>

### Every path exits 0

The whole script is wrapped so that it cannot fail loudly:

<CodeBlock title="the outer wrapper">

```javascript
try {
  main();
} catch (err) {
  console.log(`format-on-save: ${err?.message ?? err}`);
}
process.exit(0);
```

</CodeBlock>

That is not defensive habit, it is the contract. A formatter is a convenience; a convenience that reports errors into the session interrupts work for something the user did not ask about. On a non-zero exit other than 2 the transcript gets a `<hook name> hook error` notice, and on exit 2 your stderr goes to Claude as a warning about an edit that already happened. Neither helps when Prettier simply cannot parse a half-written file.

### You will not see its stdout

For `PostToolUse`, stdout goes to the debug log and is not shown in the transcript. So there is no "hook ran" message to look for. You verify a formatter the way you verify any silent side effect: **look at the file.** That is what the lab does — read it before, read it after.

This lesson's worked example prompt is designed to make the hook visible by fighting it:

```text
In src/scratch.ts, add a subtract function next to add, written in exactly this compact
style: export function subtract(a,b){return a-b}. Do not run any command afterwards;
just make the edit and say DONE.
```

The interesting part of that capture is not the formatting — it is Claude's answer.

The prompt asked for a compact one-liner and forbade running any command. The edit landed exactly as asked; then the hook rewrote it, along with the `add` function that was already in the file. Claude noticed, said so, and offered to disable the hook. Nothing in the session was told a hook existed — it inferred it from the file changing under its own edit.

That is the real cost of a `PostToolUse` formatter, and it is worth paying with your eyes open. A hook that silently rewrites the model's output makes the model's mental image of the file wrong until it reads the file again. Two consequences follow:

- **Format the whole file or none of it.** Half-formatting produces churn that Claude will keep trying to "fix".
- **Consider telling Claude what happened.** If the rewrite is substantial, return `hookSpecificOutput.additionalContext` — "Prettier reformatted `src/scratch.ts` after your edit" — so the next tool call starts from the truth rather than from a guess. Write it as a factual statement, not an instruction; text framed as an out-of-band system command can trip Claude's prompt-injection defences.

### The same hook for other toolchains

The structure does not change with the formatter; only the command does.

```powershell
# Go

# Rust
rustfmt $File
```

One Windows-specific trap from the docs: in **exec form** — the form you get when you set `args` — `command` must resolve to a real executable. The `.cmd` and `.bat` shims that npm and friends drop in `node_modules/.bin` are not executables and cannot be spawned without a shell. Invoke the script through `node` instead (`"command": "node", "args": ["…/bin/prettier.cjs", "--write"]`), which works on every platform, or use shell form and let the shell find the shim. The lab hook sidesteps this entirely by calling `process.execPath` on Prettier's `.cjs` entry point.

## Anti-patterns

**Letting the formatter fail loudly.** A non-zero exit turns a cosmetic step into a session-level error notice, and exit 2 puts your stderr in front of the model. _Fix:_ catch everything, exit 0.

**Formatting files outside the repository.** `tool_input.file_path` is whatever Claude edited, which can be a file in another directory you added with `/add-dir`. _Fix:_ compute the relative path and bail when it starts with `..`.

**Running the formatter on every tool call.** Without a matcher, `PostToolUse` fires for `Read`, `Grep`, `Bash` and everything else, and your hook pays a process launch each time. _Fix:_ `"matcher": "Write|Edit"`, plus the tool-name check inside the script.

**Reformatting the repository as a side effect.** A hook that runs `prettier --write .` instead of `--write <file>` turns one edit into a whole-tree diff. _Fix:_ format exactly the file in `tool_input.file_path`.

**Trying to reject a bad edit from `PostToolUse`.** The write already happened; there is nothing to veto. _Fix:_ move the check to `PreToolUse`, where a `deny` stops it, and keep `PostToolUse` for repair and reporting.
