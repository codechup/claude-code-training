## Objectives & prerequisites

By the end of this lesson you can:

- Follow a fixed order when a hook misbehaves, instead of guessing.
- Turn on hook debug logging with `--debug-file` or `/debug`, and read the lines that matter.
- Recognise the three outcomes a hook run can have — silent success, blocking error, non-blocking error — and which one you are looking at.
- Diagnose the four failures that cause most hook bugs: a bad script path, `exit 1` where you meant `exit 2`, stdout that is not pure JSON, and a matcher that never matches.
- Explain why a hook that works interactively can behave differently in `-p`, and vice versa.

**Prerequisites.** Lessons `01`–`06`. The lab runs in a scratch folder.

<WhenNotToUse>
  This lesson is for hooks that are configured and misbehaving. If nothing is configured at all,
  `/hooks` tells you that in one keystroke and there is nothing to debug. If the problem is Claude's
  behaviour rather than the hook's — the hook fires, returns what you intended, and the session
  still does something you dislike — that is a prompting or permissions question, not a hook one.
  And do not debug a hook by adding `console.log` calls: on most events stdout is invisible, and on
  the events where it is not, it corrupts your JSON.
</WhenNotToUse>

## Concept

### The order

1. **`/hooks`.** Is it registered at all, on the event you think, from the file you think? Sources are labelled `User Settings`, `Project Settings`, `Local Settings`, `Plugin Hooks`, `Session Hooks`. If it is missing, your JSON is probably invalid — trailing commas and comments are not allowed — or the file watcher missed the edit, in which case restart the session.
2. **Run it by hand.** A hook is a program that reads stdin. Pipe it a sample event and check the exit code. This takes seconds and rules out half of everything.
3. **Read the debug log.** Which hooks matched, their exit codes, and their full stdout and stderr are written there and nowhere else.
4. **Only then** suspect the matcher, the event, or Claude.

### Turning on the log

Start Claude Code with `claude --debug-file <path>` to write the log to a known location, or run `claude --debug` and read `~/.claude/debug/<session-id>.txt`. Note that `--debug` does not print to the terminal. Mid-session, `/debug` turns logging on and tells you the path. For matcher-level detail — which matchers were tested and how many hooks were found — set `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose`.

The lines you are looking for are shaped like this:

```text
2026-07-19T02:03:24.382Z [DEBUG] Hook output does not start with {, treating as plain text
2026-07-19T02:03:24.382Z [DEBUG] Hook PostToolUse:Write (PostToolUse) success:
hook-ran
```

A `success:` line means it ran and exited 0. An `error:` line carries the interpreter's message. The `does not start with {` line is the single most useful diagnostic on the page — it means your JSON was read as plain text and every decision in it was ignored.

### The three outcomes

The troubleshooting guide names them, and telling them apart is most of the work:

- **Silent success.** You see nothing. Confirm the hook ran by its effect — a reformatted file, a line in a log — or by the debug log.
- **Blocking error.** On most events you see the feedback: the reason from your JSON's blocking decision if it made one, otherwise the hook's stderr.
- **Non-blocking error.** The action proceeded and the transcript shows a `<hook name> hook error` notice — the first line of stderr prefixed `Failed with non-blocking status code:`, or a JSON validation or parse message.

### The four failures

**1. The script path is wrong.** The shell exits with something like 127 and you get a non-blocking notice: `Failed with non-blocking status code: /bin/sh: /path/to/hook.sh: No such file or directory`. **The action proceeds.** For a policy hook this is the worst failure mode there is — a mistyped path in `settings.json` leaves the gate silently disabled, so watch for that notice on a guard's first run. Fixes: use `${CLAUDE_PROJECT_DIR}` or an absolute path, `chmod +x` the script, and add `"args": []` to switch to exec form, which spawns the script directly with no shell quoting to get wrong.

**2. `exit 1` where you meant `exit 2`.** Non-blocking on most events: your policy hook becomes a warning and the command runs. Exit 2 is the only code that blocks through the code alone (except `WorktreeCreate`, where any non-zero exit aborts).

**3. Stdout is not pure JSON.** Claude Code parses stdout as JSON only when it starts with `{` and ends with `}`. The classic cause is a shell profile that prints a banner: Git Bash and setups where `BASH_ENV` points at `~/.bashrc` still source your profile even in a non-interactive shell, and the banner gets prepended:

```text
Shell ready on arm64
{"decision": "block", "reason": "Not allowed"}
```

Now stdout starts with `S`, the whole thing is plain text, and on exit 0 **nothing is reported in the transcript at all** — only the debug log records the attempt. Fix your profile:

<CodeBlock title="guard your shell profile">

```bash
# In ~/.zshrc or ~/.bashrc
if [[ $- == *i* ]]; then
  echo "Shell ready"
fi
```

</CodeBlock>

The other cause is building JSON with string concatenation, so a quote or backslash in a value breaks it. Use `jq -n --arg`, or `JSON.stringify`, or Python's `json.dumps` — never `echo "{...$var...}"`.

**4. The matcher never matches.** Matchers are case-sensitive. A matcher containing only letters, digits, `_`, `-`, spaces, `,` or `|` is an exact list; anything else is an unanchored regular expression. And check the event itself: `PreToolUse` fires before the call and `PostToolUse` after, `PermissionRequest` only exists where a permission prompt does.

### Two environment traps

**Interactive versus `-p`.** Workspace trust holds back settings-file hooks in an interactive session until you accept the dialog, while a `-p` session treats the folder as trusted. So "it works headlessly but not in my terminal" is usually trust, not the hook. Going the other way, `terminalSequence` is ignored under `-p`, and `PermissionRequest` has no prompt to fire on.

**The working directory.** Handlers run in the current directory. If that directory has been deleted — a worktree or temp dir another shell removed — Claude Code falls back to the session's starting directory, the project root, your home directory or the system temp directory, and records a warning naming the fallback in the debug log. A hook that assumes `./node_modules` exists will fail in ways that make no sense until you read that line.

### The Stop-hook loop

One failure has its own symptom: Claude keeps working instead of stopping, then the turn ends with a warning that the `Stop` hook blocked too many consecutive times. Claude Code overrides a `Stop` hook after **eight** blocks in a row. Read `stop_hook_active` from the input and exit early when it is `true`:

<CodeBlock title="the Stop-hook guard clause">

```bash
#!/bin/bash
INPUT=$(cat)
if [ "$(echo "$INPUT" | jq -r '.stop_hook_active')" = "true" ]; then
  exit 0  # Allow Claude to stop
fi
# ... rest of your hook logic
```

</CodeBlock>

Raise `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` only when the loop genuinely converges.

This lesson's worked example prompt, for when you would rather have Claude read the evidence with you:

```text
My PreToolUse hook is not firing. Read .claude/settings.json and .claude/hooks/, then read
debug.txt and tell me which of these is true: it is not registered, it is not matching, it
failed to start, or it ran and its output was ignored. Quote the log line you used.
```

Everything worth learning about hook debugging is in that capture.

The session answered the question perfectly. Nothing in the terminal suggested a problem. One character in `settings.json` was wrong, the gate was completely off, and **the only evidence anywhere was one line in a log nobody had asked for**. Now imagine that hook had been lesson 02's guard rather than a recorder.

That is why the habit matters more than the technique: after you write or move a policy hook, run it once with `--debug-file` and grep for `error:`. It takes twenty seconds and it is the difference between a guard and the belief that you have one.

The fixed run is quiet in the opposite way — no error line, and the hook's effect shows up in `events.log`. A hook that succeeds says nothing at all, so "no output" is never evidence either way. Check the effect.

In an interactive session, `Ctrl+O` opens the transcript view, which is where a blocking error's feedback and a non-blocking error's notice appear. For a broader configuration problem — settings not loading, the wrong file winning — the docs point at `/context`, `/doctor` and the settings-precedence walkthrough in _Debug your config_.

## Anti-patterns

**Debugging with `console.log`.** On most events stdout is invisible, and where it is not, it destroys your JSON. _Fix:_ write to a file, or to stderr and read the debug log.

**Assuming no output means no problem.** A successful hook is silent, a failed one is nearly silent, and a hook whose JSON was ignored is completely silent on exit 0. _Fix:_ check the effect, then the log.

**Skipping the piped test.** Half of hook bugs are ordinary script bugs, and a session is an expensive way to find a typo. _Fix:_ `echo '{…}' | ./my-hook.sh; echo $?` before anything else.

**Fixing the hook when the matcher is wrong.** If the script never ran, its contents cannot be the bug. _Fix:_ `/hooks` first — registered, right event, right source file — and only then read the script.

**Leaving a policy hook unverified after a rename or a move.** Paths break silently, and a non-blocking notice on the first run is easy to miss. _Fix:_ re-run with `--debug-file` and grep for `error:` every time you touch the path.
