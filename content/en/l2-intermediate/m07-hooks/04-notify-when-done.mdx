## Objectives & prerequisites

By the end of this lesson you can:

- Say what `Notification` fires for, what `Stop` fires for, and why they are not the same "done".
- Write one hook that serves both events by branching on `hook_event_name`.
- Emit a desktop notification the supported way, with `terminalSequence`, and say where that field is inert.
- Post to Slack from a hook without putting the webhook URL in the repository.
- Recognise the two failure modes of `Stop` hooks: the eight-block cap, and never firing on an interrupt.

**Prerequisites.** Lessons `01`–`03`, and the lab at this lesson's tag:

<CodeBlock title="get the lab">

```bash
git checkout lesson/m07-04-start
npm ci
```

</CodeBlock>

<WhenNotToUse>
  A notification hook earns its keep on long, unattended runs. It is noise on a short interactive
  session where you are already looking at the terminal — `Stop` fires every time Claude finishes
  responding, not once per task, so a desktop alert per turn trains you to ignore alerts. Do not use
  a `Stop` hook as a task-completion signal for automation either: it fires on every turn and never
  on a user interrupt, and an API error fires `StopFailure` instead. And do not put a webhook URL,
  token or channel id in a hook that lives in a shared repository; that is what
  `.claude/settings.local.json` and environment variables are for.
</WhenNotToUse>

## Concept

### Two different "done"

`Notification` runs when Claude Code sends a notification, and it matches on the notification type. The useful ones early on are `permission_prompt` (Claude needs you to approve a tool use, and the prompt has waited about six seconds) and `idle_prompt` (Claude finished responding about 60 seconds ago and you have not typed since). There are a dozen more, including `auth_success`, the `elicitation_*` family, `agent_needs_input` and `agent_completed`, and the `quota_auto_resume_*` types.

Two properties matter. You receive these events **even with desktop notifications turned off** — the `preferredNotifChannel` setting changes how you are alerted, not whether your hook runs. And the timing of `permission_prompt`, `idle_prompt` and the elicitation dialogs is gated on you appearing to be away: the timer starts when the prompt appears and every keystroke defers it. If you want to react the instant Claude asks for permission, use `PermissionRequest` instead.

`Stop` runs when the main agent **has finished responding**. Not when the task is finished — when the turn is. It does not run on a user interrupt, and an API error fires `StopFailure` instead. `SubagentStop` is the same event for a subagent.

Neither event is a completion signal in the project-management sense. They are the session's edges.

### What each can return

`Notification` hooks cannot block or modify notifications. Claude Code discards their `systemMessage` and `continue` fields; they are for side effects — forwarding to an external service. The one output that does work is `terminalSequence`.

`Stop` hooks can block. `decision: "block"` with a `reason` prevents Claude from stopping and tells it why to keep going; `hookSpecificOutput.additionalContext` does the same thing more gently, labelled `Stop hook feedback` in the transcript rather than a hook error. Both run into the same guard rail: **Claude Code overrides a Stop hook after it blocks eight times in a row.** A Stop hook that can block must read `stop_hook_active` from its input and exit early when it is `true`.

### Desktop notifications, the supported way

Hooks run without a controlling terminal, so writing escape sequences to `/dev/tty` fails. Return the sequence in `terminalSequence` and Claude Code emits it for you — race-free, and it works inside tmux and on Windows:

<CodeBlock title="a Notification hook that pings the desktop">

```bash
#!/bin/bash
# Notification hook: ping the desktop when Claude Code needs attention.
input=$(cat)
title="Claude Code"
body=$(jq -r '.message // "Needs your attention"' <<<"$input")
seq=$(printf '\033]777;notify;%s;%s\007' "$title" "$body")
jq -nc --arg seq "$seq" '{terminalSequence: $seq}'
```

</CodeBlock>

The allowlist is narrow on purpose: OSC `0`/`1`/`2` (window and icon titles), OSC `9` (iTerm2, ConEmu, Windows Terminal, WezTerm), OSC `99` (Kitty), OSC `777` (urxvt, Ghostty, Warp), and a bare BEL. Anything else — cursor moves, colours, OSC 8 hyperlinks, OSC 52 clipboard writes — is rejected and the whole field is ignored.

Two limits to plan around. Claude Code writes the sequence **only in an interactive session, and only while its interface is on screen**: in `-p` and in the Agent SDK the field is ignored. And a `WorktreeCreate` command hook cannot use it at all, because its stdout is read as a path.

If you would rather use the platform's own notifier, the official guide's `Notification` examples are one-liners in settings:

On macOS, `osascript` routes through Script Editor, which needs notification permission granted once in System Settings or it fails silently. On Linux, `notify-send` needs a notification daemon — it will not work over SSH or in a container. On Windows the example opens a dialog box, which can appear behind your terminal.

### Slack, without leaking the webhook

A Slack notification is a POST to an incoming-webhook URL. The URL is a secret: anyone holding it can post to your channel. Keep it out of the repository — read it from the environment, and let the hook do nothing when it is unset:

<CodeBlock title=".claude/hooks/notify-slack.mjs">

```javascript
#!/usr/bin/env node
// Stop hook: post one line to Slack. No webhook configured -> do nothing, quietly.
import { readFileSync } from 'node:fs';

const url = process.env.SLACK_WEBHOOK_URL;
if (!url) process.exit(0);

let input = {};
try {
  input = JSON.parse(readFileSync(0, 'utf8') || '{}');
} catch {
  process.exit(0);
}

const text = `Claude Code finished a turn in ${input.cwd ?? 'a session'}.`;
await fetch(url, {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ text }),
}).catch(() => {});
process.exit(0);
```

</CodeBlock>

Export `SLACK_WEBHOOK_URL` in your shell profile, or set it in `.claude/settings.local.json`'s `env` block — that file is gitignored when Claude Code writes to it. Claude Code also ships a `type: "http"` hook that POSTs the event JSON to a URL directly, with `headers` interpolated from environment variables you list in `allowedEnvVars`; that is the right tool once your endpoint speaks the hook JSON format rather than Slack's.

This lesson's worked example prompt is deliberately ordinary — the point is what happens around it:

```text
In one sentence, what does src/store.ts do?
```

The capture is short, and its most useful content is the absence: one `[Stop]` line, no `[Notification]` line. That is not a broken hook. `Notification` fires when Claude Code sends a notification, and the types that mean "I need you" — `permission_prompt`, `idle_prompt` — are gated on a human being away from the keyboard. A `-p` run has no keyboard and no prompts, so nothing is sent.

This is the general shape of testing session-edge hooks: the `Stop` half is provable headlessly, and the `Notification` half needs a real terminal you can walk away from. That is also why this lesson describes the desktop and Slack halves with configuration rather than a recorded session — a `terminalSequence` is ignored under `-p`, and a webhook you cannot show is a webhook you should not paste into a lesson.

## Anti-patterns

**Treating `Stop` as "the task is done".** It fires every time Claude finishes responding. Three turns of conversation is three `Stop` events. _Fix:_ if you need "the work is finished", check the condition itself — tests green, branch pushed — inside the hook, and stay quiet otherwise.

**A blocking `Stop` hook with no exit condition.** Block on "tests are failing" and a session that cannot make the tests pass loops until Claude Code overrides you after eight consecutive blocks. _Fix:_ read `stop_hook_active` and exit 0 when it is `true`; raise `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` only when the loop genuinely converges.

**Writing escape sequences to `/dev/tty`.** Hooks have no controlling terminal; the write fails, and on Windows there is no `/dev/tty` at all. _Fix:_ return `terminalSequence` and let Claude Code emit it.

**Committing the webhook.** A Slack URL in `.claude/settings.json` is a public credential the moment the repo is cloned. _Fix:_ read it from the environment and no-op when it is missing, so the hook is safe to commit and useless to a stranger.

**Alerting on every turn.** The fastest way to make a notification hook worthless. _Fix:_ narrow the matcher (`permission_prompt` rather than everything), or gate the alert on elapsed time in the script.
