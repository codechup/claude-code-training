## Objectives & prerequisites

By the end of this lesson you can:

- Run `/skill-doctor` in both an interactive session and in `-p` mode, and read its report.
- Explain the difference between the per-turn cost of a skill's _listing_ and the one-off cost of its _body_.
- Use `skillOverrides` — through the `/skills` menu or by hand — to move a skill between `on`, `name-only`, `user-invocable-only` and `off`.
- Diagnose a skill that never triggers, and know which of the three causes you are looking at.
- Say where `/skill-doctor` is unavailable, and what to run instead.

**Prerequisites.** Lessons `01`–`05`, and Claude Code v2.1.252 or later. A project with at least two or three skills in it — the state you finish lesson 05 in is ideal.

<WhenNotToUse>
  `/skill-doctor` measures usage; it does not measure quality. A skill that runs on every prompt and
  produces mediocre output looks excellent in this report. Seeing a skill trigger tells you Claude
  found it, not that it did what you intended — for that, the docs point at a baseline comparison:
  run the same realistic prompts in a fresh session with the skill available and again with it
  disabled, and compare. Do not use `/skill-doctor` for that, and do not delete a rarely used skill
  on the strength of a low count if the few times it runs are the times that matter.
</WhenNotToUse>

## Concept

### What it costs to have a skill you never use

Claude Code loads a listing of skill names and descriptions into context so Claude knows what is available. Every skill in that listing adds to your context **on every turn**, whether or not Claude ever uses it. The body is different: it loads only when the skill runs, and then it stays for the rest of the session.

So a skill has two costs, and they behave nothing alike:

| Cost              | When it is paid                    | How to reduce it                                                           |
| ----------------- | ---------------------------------- | -------------------------------------------------------------------------- |
| The listing entry | Every turn, for the whole session  | `skillOverrides: "name-only"` or `"off"`; `disable-model-invocation: true` |
| The rendered body | Once per invocation, then persists | Keep the body short; move detail into supporting files                     |

`/skill-doctor` reports the first and shows you which skills are not earning it.

### Reading the report

`/skill-doctor` shows what each of your skills costs and how often it gets used. In an interactive session the report opens in the `/plugin` manager's **Stats** tab; in non-interactive mode with `-p`, Claude Code prints it as text. It covers the skills in your session other than bundled and enterprise skills, flags skills in the listing that have never been invoked, says where to turn them off, and lists plugins you have not used recently.

The `context` column is the part people misread. It is the size of _this skill's one-line listing entry_, included every turn — not the size of `SKILL.md`. A dash means the skill is not in the current listing at all, and therefore costs nothing per turn. In the capture below, two of the three skills show a dash: both set `disable-model-invocation: true`, which keeps their description out of Claude's context entirely, exactly as the table in lesson 02 says.

### Turning a skill down instead of off

`skillOverrides` in `.claude/settings.json` or `.claude/settings.local.json` controls visibility without editing a `SKILL.md` you may not own:

| Value                   | Listed to Claude     | In the `/` menu |
| ----------------------- | -------------------- | --------------- |
| `"on"` (the default)    | Name and description | Yes             |
| `"name-only"`           | Name only            | Yes             |
| `"user-invocable-only"` | Hidden               | Yes             |
| `"off"`                 | Hidden               | Hidden          |

The `/skills` menu writes this for you: highlight a skill, press `Space` to cycle states, `Esc` to save to `.claude/settings.local.json`. The menu labels `"user-invocable-only"` as `user-only`. Plugin skills are not affected by `skillOverrides` — manage those through `/plugin`.

`"name-only"` is the underrated setting. It frees listing budget while keeping the skill typable, which is what you want for a skill you invoke by hand but never want Claude to guess at.

### Why a skill is not triggering

Three causes, in the order worth checking:

1. **Its description is not in the listing at all.** Either you set `disable-model-invocation: true` (in which case it is working as designed and you must type it), or the listing overflowed. The budget scales at 1% of the model's context window, and when it overflows Claude Code drops descriptions **starting with the skills you invoke least** — so the skills you use most keep their full text, and the neglected ones get quieter. `/doctor` estimates the listing's cost and its biggest contributors; `--debug` writes a warning to the debug log when the budget is exceeded.
2. **The description does not match how you ask.** Put the key use case first, and use `when_to_use` for trigger phrases. Remember the combined cap of 1,536 characters per entry.
3. **`paths` is narrowing it.** A skill with `paths` set activates automatically only when Claude is working with matching files.

The `/context` Skills row reports the listing size _after_ the budget is applied, so it matches what the model actually receives. To raise the budget, set `skillListingBudgetFraction` (for example `0.02` for 2%) or the `SLASH_COMMAND_TOOL_CHAR_BUDGET` environment variable.

The prompt to type when the report is in front of you:

```text
Here is my /skill-doctor output. Three skills have never been invoked. For each,
tell me whether the fix is a better description, a `paths` restriction, or turning
it off in skillOverrides — and write the settings.json entry for the ones to turn off.
```

### Where it is not available

`/skill-doctor` requires Claude Code v2.1.252 or later, and is not available in sessions that skip feature-flag fetching. Over Remote Control from a phone or browser it replies `Skill usage reports are not available on this connection.` — run it in the terminal on the machine where the session is running.

## Anti-patterns

**Reading the `context` column as the size of `SKILL.md`.** It is the one-line listing entry, paid per turn. The body is a separate, one-off cost paid at invocation. _Fix:_ use `/context` for what the whole session is carrying, and `/skill-doctor` for what the listing costs.

**Deleting a skill because the count is low.** The report measures frequency, not value. _Fix:_ set it to `"name-only"` first — you keep it typable and stop paying for its description — and delete only if you never reach for it.

**Fixing a non-triggering skill by rewriting the body.** Claude decides whether to load a skill from its `description` and `when_to_use`; the body is what it reads _after_ deciding. _Fix:_ rewrite the description, key use case first.

**Raising `skillListingBudgetFraction` as the first move.** More budget means more context spent on descriptions on every turn, forever. _Fix:_ trim descriptions and set low-priority skills to `"name-only"` first; raise the budget only when the trimmed listing still overflows.

**Expecting the report over Remote Control.** It replies that skill usage reports are not available on that connection. _Fix:_ run it in the terminal on the machine hosting the session.
