## Objectives & prerequisites

By the end of this lesson you can:

- Pass values into a skill and read them back with `$ARGUMENTS`, `$ARGUMENTS[N]` and the `$N` shorthand.
- Declare named arguments in frontmatter and use `$name` placeholders in the body.
- Use `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_SESSION_ID}` and `${CLAUDE_EFFORT}`, and say where each one is substituted.
- Predict what happens when you pass an argument no placeholder receives, and when a placeholder has no argument.
- Build and run `/commit-msg` against the lab repo, with and without a scope hint.

**Prerequisites.** Lessons `01-skills-vs-commands` and `02-skill-md-anatomy`. A clone of `claude-code-lab` and git on your PATH.

<WhenNotToUse>
  Arguments are for the one or two values that change per run — an issue number, a scope, a path.
  They are not a configuration system: if your skill needs five arguments in a fixed order, nobody
  will remember the order, and `argument-hint` only helps while you are typing. Put stable settings
  in the skill body or a supporting file instead. And do not reach for arguments at all when the
  skill can read what it needs itself — `/commit-msg` runs `git diff --staged` rather than making
  you paste the diff in.
</WhenNotToUse>

## Concept

### `$ARGUMENTS` and its indexed forms

Both you and Claude can pass arguments when invoking a skill. Everything after the skill name becomes the argument string.

| Placeholder     | Expands to                                                                 |
| --------------- | -------------------------------------------------------------------------- |
| `$ARGUMENTS`    | All arguments passed, as typed                                             |
| `$ARGUMENTS[N]` | A specific argument by 0-based index — `$ARGUMENTS[0]` is the first        |
| `$N`            | Shorthand for `$ARGUMENTS[N]`: `$0` is the first argument, `$1` the second |
| `$name`         | A named argument declared in the `arguments` frontmatter list              |

Indexed arguments use shell-style quoting, so `/my-skill "hello world" second` makes `$0` expand to `hello world` and `$1` to `second`. `$ARGUMENTS` always expands to the full argument string as typed.

Two edge cases worth committing to memory:

- **An indexed placeholder with no argument stays as literal text.** `$2` when only one argument was passed reaches Claude as the characters `$2`.
- **A named placeholder with no argument expands to an empty string.** That is the opposite behaviour, and it matters when you write conditional-sounding instructions like "if `$scope` is empty, infer it".

If you pass arguments but _no placeholder receives one_, Claude Code appends `ARGUMENTS: <your input>` to the end of the skill content, so Claude still sees what you typed. A named placeholder counts as receiving one even when its position is empty; an indexed placeholder left as literal text does not.

### Named arguments

Declare them in frontmatter as a space-separated string or a YAML list; names map to positions in order.

<CodeBlock title=".claude/skills/migrate-component/SKILL.md">

```yaml
---
name: migrate-component
description: Migrate a component from one language to another
arguments: [component, from-lang, to-lang]
---
Migrate the $component from $from-lang to $to-lang.
Preserve all existing behavior and tests.
```

</CodeBlock>

`/migrate-component SearchBar JavaScript TypeScript` fills all three. The same skill written with `$0`, `$1`, `$2` behaves identically — named arguments buy readability, not capability.

### The `${CLAUDE_*}` substitutions

| Variable                | Expands to                                                                                                      |
| ----------------------- | --------------------------------------------------------------------------------------------------------------- |
| `${CLAUDE_SESSION_ID}`  | The current session ID — useful for per-session log files                                                       |
| `${CLAUDE_EFFORT}`      | The current effort level: `low`, `medium`, `high`, `xhigh` or `max`                                             |
| `${CLAUDE_SKILL_DIR}`   | The directory containing this `SKILL.md`. For a plugin skill, the skill's own subdirectory, not the plugin root |
| `${CLAUDE_PROJECT_DIR}` | The project root — the same path hooks and MCP servers receive. Requires v2.1.196 or later                      |
| `${CLAUDE_PLUGIN_ROOT}` | The plugin's installation directory; substituted only in plugin skills                                          |
| `${CLAUDE_PLUGIN_DATA}` | The plugin's persistent data directory, which survives updates; plugin skills only                              |

`${CLAUDE_SKILL_DIR}` and `${CLAUDE_PROJECT_DIR}` are substituted in **two** places: the skill body, and Bash rules inside `allowed-tools`. Using the same variable in both is how a skill runs a bundled script with no permission prompt:

<CodeBlock title="a skill that runs its own script without prompting">

```yaml
---
name: render-chart
description: Render a chart from a CSV file
allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)
---
Run `${CLAUDE_SKILL_DIR}/scripts/render.sh <csv-file>` to render the chart.
```

</CodeBlock>

Both occurrences expand to the same absolute path, so the rule matches the exact command the body asks for.

### Escaping, and text that looks like a placeholder

To write a literal `$` before a digit, before `ARGUMENTS`, or before a declared argument name, escape it with a backslash: `\$1.00`. Only a single backslash directly before the token escapes it; `\\$1` leaves both backslashes and still expands. The escape covers argument placeholders only — a backslash does not stop a `${CLAUDE_*}` substitution.

Argument _values_ are inserted as literal text and never re-expanded. If a skill body contains `Summarize $0` and you run `/summarize "$ARGUMENTS from yesterday"`, Claude receives `Summarize $ARGUMENTS from yesterday`.

### Stacking

You can put several skills at the start of one message. Typing `/write-tests /fix-issue 123` loads both and passes the trailing text `123` to each as `$ARGUMENTS`. Claude Code expands the first skill plus up to five more, and stops at the first token that is not an inline user-invocable skill — including a skill that runs as a forked subagent, such as `/code-review`. That token and everything after it become the argument text.

Here is this lesson's worked prompt — the thing you would actually type to get the skill you are about to build:

```text
Add .claude/skills/commit-msg/SKILL.md to this repo. It should read the staged
diff and print one conventional commit message. Treat $ARGUMENTS as an optional
scope hint, and infer the scope from the changed paths when it is empty.
Pre-approve only `git diff` and `git status`, and never run `git commit`.
```

### The skill you are writing

<CodeBlock title=".claude/skills/commit-msg/SKILL.md">

```markdown
---
name: commit-msg
description: Draft a conventional commit message for the currently staged diff. Prompt-only — reads the diff and $ARGUMENTS (an optional scope hint), writes nothing.
when_to_use: Staged changes exist and you want a conventional-commit message drafted from them instead of writing one by hand.
argument-hint: '[optional scope, e.g. cli or api]'
allowed-tools: Bash(git diff:*), Bash(git status:*)
disable-model-invocation: true
model: haiku
effort: low
---

# /commit-msg

Run `git diff --staged` and `git status --short`. From the staged diff, write one
conventional commit message: `type(scope): summary`, types `feat|fix|docs|chore|test|refactor`.

- If `$ARGUMENTS` gives a scope, use it; otherwise infer one from the changed paths
  (`cli`, `api`, `store`, `test`, `docs`).
- Summary line under 72 characters, imperative mood ("add", not "added").
- Add a body only if the diff needs one sentence of "why" beyond the summary.
- Print the message only — do not run `git commit`.
```

</CodeBlock>

(This site's formatter normalises YAML strings to single quotes; the lab repo's copy writes `argument-hint` with double quotes. Both are the same YAML string.)

`Bash(git diff:*)` is the `:*` form of a trailing wildcard — `Bash(git diff:*)` and `Bash(git diff *)` match the same commands. The `:*` suffix is only recognised at the end of a pattern; in `Bash(git:* push)` the colon is a literal character and matches nothing useful.

Note what the two captures prove. The first run received `store` as `$ARGUMENTS` and used it. The second passed nothing, so `$ARGUMENTS` expanded to an empty string and the skill fell back to inferring the scope from the changed path — which is why the fallback instruction has to be _in the body_. An empty placeholder is not an error Claude Code reports; it is just an empty string, and your skill has to say what to do with one.

## Anti-patterns

**Relying on `argument-hint` to enforce anything.** It is a hint shown during autocomplete. Nothing validates it, and nothing fills a missing argument. _Fix:_ state the default in the body — "if `$ARGUMENTS` is empty, do X".

**Positional arguments past two.** `$0 $1 $2 $3` is a command-line interface nobody has a manual for. _Fix:_ use named arguments so the body reads as English, and keep the count low.

**Assuming `$2` is empty when nothing was passed.** It is not: an indexed placeholder with no argument reaches Claude as the literal text `$2`, which reads as noise inside an instruction. _Fix:_ use named arguments (which expand to an empty string) when a value is genuinely optional.

**Writing a path into the body instead of `${CLAUDE_SKILL_DIR}`.** A relative path resolves against the session's current working directory, which moves when Claude runs `cd`. _Fix:_ `${CLAUDE_SKILL_DIR}` in both the body and the `allowed-tools` rule.

**Pasting the data the skill could fetch.** Passing a diff as an argument burns context and goes stale the moment anything changes. _Fix:_ let the skill run `git diff --staged` itself, or inject it with `` !`git diff --staged` `` (lesson 05).
