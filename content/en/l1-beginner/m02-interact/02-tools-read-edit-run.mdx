## Objectives & prerequisites

By the end of this lesson you can:

- Name the tools you will see scroll past in an ordinary session — `Read`, `Edit`, `Write`, `Glob`, `Grep`, `Bash` (or `PowerShell`), `WebFetch` — and say what each one is for.
- Explain the read-before-edit rule, why `Edit` replaces an exact string rather than a pattern, and what `replace_all: true` is for.
- Predict whether Claude will reach for `Glob`, `Grep` or `Read` for a given question.
- Read a tool call in a transcript and know which permission rule shape (`Bash(npm test)`, `Read(./.env)`, `WebFetch(domain:example.com)`) would govern it.
- Run a real session that finds a bug with search, fixes it with one edit, and proves the fix with the test runner.

**Prerequisites.** Lesson `01-prompting-basics`, and a clone of the lab repository with Node 24 available.

<WhenNotToUse>
  You never call these tools yourself, and you should not try to. Claude picks them; your levers are
  the prompt and the permission rules. Reaching for tool names in a prompt ("use Grep, then Read,
  then Edit") is dictating the steps — the anti-pattern from the previous lesson — and it makes the
  session worse on any task bigger than a demo. The one honest exception is teaching and debugging,
  which is exactly what this lesson's lab does: naming the tools makes the recording legible. In
  real work, name the goal.
</WhenNotToUse>

## Concept

### Tools are what make it an agent

Without tools a model can only reply with text. With them it can read your code, change it, run your test suite and fetch a page. Each tool call returns information that feeds back into the loop and informs the next decision — that is the whole mechanism.

The docs group the built-ins into five categories:

| Category              | What Claude can do                                                                             |
| --------------------- | ---------------------------------------------------------------------------------------------- |
| **File operations**   | Read files, edit code, create new files, rename and reorganise                                 |
| **Search**            | Find files by pattern, search content with regex, explore codebases                            |
| **Execution**         | Run shell commands, start servers, run tests, use git                                          |
| **Web**               | Search the web, fetch documentation, look up error messages                                    |
| **Code intelligence** | Type errors after edits, jump to definitions, find references (via a code-intelligence plugin) |

### The ones you will actually see

| Tool         | What it does                                               | Worth knowing                                                                                                             |
| ------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `Read`       | Returns file contents with line numbers                    | Also handles images, PDFs and Jupyter notebooks; a large file comes back as a `PARTIAL view`                              |
| `Edit`       | Exact string replacement in one file                       | No regex, no fuzzy match. `old_string` must match once — or pass `replace_all: true`. See the read-before-edit note below |
| `Write`      | Creates or overwrites a file                               | Overwrites. For a partial change, `Edit` is the right tool                                                                |
| `Glob`       | Finds files by pattern (`**/*.ts`, `*.{json,yaml}`)        | Results capped at 100 files; does not respect `.gitignore` by default                                                     |
| `Grep`       | Searches file contents, **ripgrep syntax**, not POSIX grep | Respects `.gitignore`; three output modes (`files_with_matches`, `content`, `count`)                                      |
| `Bash`       | Runs shell commands                                        | 2-minute default timeout, 10-minute maximum; can run in the background                                                    |
| `PowerShell` | Runs PowerShell natively on Windows                        | Opt-in elsewhere with `CLAUDE_CODE_USE_POWERSHELL_TOOL=1`                                                                 |
| `WebFetch`   | Fetches a URL and extracts content with a small model      | Lossy by design; responses cached for 15 minutes                                                                          |
| `WebSearch`  | Performs a web search                                      | No specifier — you allow or deny the whole tool                                                                           |

One detail on `Edit` is worth stating precisely, because it changed with the models. The tools reference: "Claude reads the file in the current conversation before editing it, and a read cut short with a `PARTIAL view` notice doesn't count. Claude Opus 4.6, Claude Haiku 4.5, and older models always require the read. Newer models can edit an unread file when reading it wouldn't need a permission prompt and the Read tool is available." So read-before-edit is a hard requirement on older models and a near-always-observed habit on newer ones — do not build a workflow that depends on skipping it.

Beyond these there is a longer list — `Agent` for spawning a subagent, `Skill`, `AskUserQuestion`, `EnterPlanMode`/`ExitPlanMode`, `Monitor`, the `Task*` checklist tools — and the tools reference is the authority for all of it.

### How Claude picks

It is not a lookup table; the model chooses based on your prompt and on what the previous call returned. The docs' own worked example, for "fix the failing tests":

1. Run the test suite to see what is failing.
2. Read the error output.
3. Search for the relevant source files.
4. Read those files.
5. Edit them.
6. Run the tests again to verify.

The pattern that generalises: **narrow before you read**. `Glob` answers "which files exist that look like X". `Grep` answers "which files contain X, and on what line". `Read` is the expensive one — it puts the whole file in the context window — so a well-behaved session greps first and reads second. You can watch that happen in the lab's first recording.

### Tool names are the unit of permission

Every permission rule is written as `Tool` or `Tool(specifier)`, so knowing tool names is what lets you write rules at all:

<CodeBlock title="permission rule shapes">

```json
{
  "permissions": {
    "allow": ["Bash(npm run *)", "Read(./docs/**)"],
    "deny": ["Bash(git push *)", "WebFetch"]
  }
}
```

</CodeBlock>

`Edit(/src/**)` covers writes to that path and also grants reads there. `WebFetch(domain:example.com)` matches by host. A bare tool name used as a **deny** rule removes the tool from Claude's context entirely — it never sees it. The next lesson is entirely about this.

Three details in those recordings repay a second look.

The search run answered `test\store.test.ts:29`, `src\api\server.ts:75` and so on — **Windows path separators**, because that capture was made on native Windows. Tool output reflects the machine it ran on; that is what an unedited transcript looks like.

The fix run's allowlist is `Bash(npm test)`, not `Bash`. That single rule is the difference between "Claude may run the test suite" and "Claude may run anything". It is also why the run could verify itself: without a `Bash` rule of some shape, the session can diagnose but cannot prove.

And the fix was **one `Edit`**, not a rewrite. `Edit` replaces an exact string in a file that has already been read; that constraint is what keeps a one-line bug a one-line diff.

## Anti-patterns

**Asking for a rewrite when you want a fix.** "Rewrite `store.ts` properly" invites `Write`, which overwrites the file wholesale. _Fix:_ describe the defect; a targeted `Edit` follows from a targeted request.

**Allowing `Bash` when you meant one command.** `--allowedTools "Bash"` in a script hands over the whole shell. _Fix:_ write the narrowest rule that still lets the session verify itself — `Bash(npm test)`, `Bash(npm run *)`.

**Letting a session read whole directories.** "Read everything under `src/` and tell me what it does" fills the context window before the work starts. _Fix:_ ask a question search can answer first, or delegate the exploration to a subagent.

**Expecting POSIX grep syntax.** The tools reference is explicit that `Grep` "uses **ripgrep syntax** (not POSIX grep)", so a pattern that works in a shell `grep` may not match here. _Fix:_ write ripgrep patterns — or describe what you are looking for and let Claude write the pattern.

**Assuming `Glob` respects `.gitignore`.** It does not, by default — `Grep` does. A glob over a repository with `node_modules` present will happily return build artefacts. _Fix:_ pattern narrowly (`src/**/*.ts`), or search content with `Grep` instead.
