## Objectives & prerequisites

By the end of this lesson you can:

- Enter and leave plan mode three ways: `Shift+Tab`, the `/plan` prefix on a single prompt, and `claude --permission-mode plan`.
- Say precisely what plan mode blocks and what it still permits.
- Read the three approval options Claude offers when a plan is ready, and pick the right one.
- Edit a proposed plan before it runs with `Ctrl+G`, and make plan mode a project default.
- Judge when planning pays for its overhead — and when it does not.

**Prerequisites.** Lesson `03-permissions` (plan mode is a permission mode), and a clone of the lab repository.

<WhenNotToUse>
  Plan mode adds a round trip, and the docs say so plainly: for a task whose scope is clear and
  whose fix is small — a typo, a log line, a rename — ask Claude to do it directly. The rule of
  thumb the guide gives is the useful one: **if you could describe the diff in one sentence, skip
  the plan.** Planning earns its cost when you are uncertain about the approach, when the change
  touches several files, or when you do not know the code being modified. It is also the wrong tool
  for containment: plan mode stops Claude editing your source, but in a session started with bypass
  permissions available, Claude Code does not enforce those blocks at all.
</WhenNotToUse>

## Concept

### What plan mode is

> Plan mode tells Claude to research and propose changes without making them. Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source.

Edits stay blocked until you approve the plan. The exception is a session started with bypass permissions available, where Claude is still _instructed_ to plan without editing but the blocks are not enforced.

What still runs while planning depends on your setup. When auto mode is available and `useAutoModeDuringPlan` is on — it is on by default — the classifier reviews shell commands during planning instead of prompting you: approved commands run, rejected ones are blocked. Otherwise, commands outside the built-in read-only set prompt for approval.

### Getting in and out

<CodeBlock title="entering and leaving plan mode">

```bash
# Start a whole session in plan mode
claude --permission-mode plan

# Inside a session: press Shift+Tab until the status bar reads
#   ⏸ plan mode on
# Press Shift+Tab again to leave plan mode without approving anything.

# Plan for one prompt only: prefix it with /plan
#   /plan add rate limiting to the API and tell me what changes

# Make plan mode the default for a project's terminal sessions,
# in .claude/settings.json:
#   {"permissions": {"defaultMode": "plan"}}
```

</CodeBlock>

Conversations started by the VS Code extension do not read project settings for the starting permission mode — set `claudeCode.initialPermissionMode` to `plan` in your VS Code user settings instead.

### Approving a plan

When the plan is ready Claude presents it and asks how to proceed. The options:

| Option                          | What it does                                                                                      |
| ------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Yes, and use auto mode**      | Approve and continue in auto mode. Reads **Yes, auto-accept edits** when auto mode is unavailable |
| **Yes, manually approve edits** | Approve and review each edit individually                                                         |
| **No, keep planning**           | Stay in plan mode and say what to change                                                          |

Approving exits plan mode and switches the session into whichever mode the option describes, so Claude starts editing immediately. Two things worth knowing before you press a key:

- **`Ctrl+G` opens the proposed plan in your default text editor** so you can change it before Claude proceeds. This is the highest-leverage key in this lesson: correcting a plan costs one edit; correcting an implementation costs a session.
- Accepting a plan gives the session a **generated title** based on the plan, unless you have already named the session.

To plan again afterwards, cycle back with `Shift+Tab` or prefix your next prompt with `/plan`.

### The four-phase workflow

The official guide's recommended shape, and the reason plan mode exists:

1. **Explore.** `read /src/auth and understand how we handle sessions and login.` Claude reads and answers; nothing changes.
2. **Plan.** `I want to add Google OAuth. What files need to change? What's the session flow? Create a plan.`
3. **Implement.** Approve, or `Shift+Tab` out, then: `implement the OAuth flow from your plan. write tests for the callback handler, run the test suite and fix any failures.`
4. **Commit.** `commit with a descriptive message and open a PR`

One quiet benefit: a plan written in plan mode is **re-injected from disk after compaction**, unlike ordinary conversation history, which is summarised. On a long task the plan is one of the few things that survives intact.

Three honest notes about those recordings.

**The plan is written to a file.** The first transcript ends by naming a plan file under `~/.claude/plans/` (the absolute path was redacted in the recording). That file is what gets re-injected after compaction, and it is what `Ctrl+G` opens in an interactive session.

**The planning run found a better fix than the obvious one.** It noticed that `isOverdue(task, now)` already accepts an injectable clock, so no source change is needed at all — only the test. That is the value of separating the plan from the diff: you get to see the reasoning before it becomes code.

**Headless plan mode is not interactive plan mode.** In one of this module's other captures Claude reported that "the `ExitPlanMode` tool is disabled in this session", because there is no one to show an approval dialog to. In `-p`, plan mode gives you the plan and stops; the approval step is a terminal-session feature. Use `-p --permission-mode plan` for read-only analysis in scripts and CI; use the interactive session when you want the approve/revise loop.

## Anti-patterns

**Planning a one-line change.** A plan for a typo costs a round trip and produces a document nobody reads. _Fix:_ if you can describe the diff in one sentence, just ask for the diff.

**Approving a plan you skimmed.** Approving switches the session straight into an editing mode, so the plan is the last cheap moment to disagree. _Fix:_ read it; press `Ctrl+G` and edit it; or choose **No, keep planning**.

**Treating plan mode as a sandbox.** It blocks edits to your source, but in a session with bypass permissions available those blocks are not enforced, and it was never an isolation boundary for untrusted code. _Fix:_ for containment use the sandbox, a container or a VM.

**Planning forever.** Three rounds of "no, keep planning" usually means the task is under-specified, not that the plan is bad. _Fix:_ go back to lesson 01 — name the goal, the constraints and the evidence — and re-ask.

**Expecting `-p --permission-mode plan` to hand you an approval dialog.** It will not; there is no interactive surface. _Fix:_ read the returned plan, then run the implementation as a separate command.
