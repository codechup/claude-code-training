## Objectives & prerequisites

By the end of this lesson you can:

- Name the three parts every workable prompt carries: the **goal**, the **constraints** (where to look, what not to touch) and the **evidence** you want back.
- Rewrite a vague request into a specific one using the four patterns the official best-practices guide names: scope the task, point to sources, reference existing patterns, describe the symptom.
- Predict what a prompt with no verifiable "done" will produce — and recognise it in a real transcript.
- Say when a vague prompt is the right choice, and steer a running session with `Esc` or a typed correction instead of starting over.

**Prerequisites.** Claude Code installed and authenticated (module `m01-start`), and a local clone of the course lab repository. This lesson's lab is read-only: nothing you run here edits a file.

<WhenNotToUse>
  Do not spend effort crafting a prompt when you are exploring. "What would you improve in this
  file?" is a legitimate prompt — the official guide says so — and it surfaces things you would not
  have known to ask about. Skip the ceremony too when the change is smaller than its description: if
  you can type the fix faster than you can describe it, type the fix. And do not treat prompt
  wording as the fix for a bad session. If you have corrected Claude twice on the same point, the
  context is polluted with failed approaches; `/clear` and start again with a better first prompt.
</WhenNotToUse>

## Concept

### Claude Code is not a chat box, and not a compiler either

A chat model needs your words to contain the information. An agent does not: it can go and get the information itself. So a prompt's job is not to describe the code — Claude will read the code — but to **fix the target, the boundary and the proof**.

The docs put it as _delegate, don't dictate_: "Give context and direction, then trust Claude to figure out the details." The worked example the official docs use is one sentence of symptom plus one directory:

```text
The checkout flow is broken for users with expired cards.
The relevant code is in src/payments/. Can you investigate and fix it?
```

Notice what it does not say: which files to open, which commands to run, what the fix looks like. It does say what is broken, for whom, and where to start.

### The three parts

| Part            | The question it answers               | What it looks like in practice                                       |
| --------------- | ------------------------------------- | -------------------------------------------------------------------- |
| **Goal**        | What is different when this is done?  | "page 1 returns the first two tasks", not "fix pagination"           |
| **Constraints** | Where to look, and what not to touch  | "the logic is in `src/store.ts`", "do not edit any files"            |
| **Evidence**    | What proof comes back with the answer | "quote the failing assertion", "run `npm test` and show the summary" |

The third one is the one people skip, and it is the one that changes the most. The best-practices guide is blunt about it: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." Give it something that returns a pass or a fail and the loop closes without you.

### Four rewrites, from the official guide

The best-practices guide carries two before/after tables — one for giving Claude a way to verify its work, one for providing specific context. Four of their rows are the shortest useful summary of the craft:

| Pattern                  | Before                                                | After                                                                                                                                                                          |
| ------------------------ | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Scope the task**       | "add tests for foo.py"                                | "write a test for foo.py covering the edge case where the user is logged out. avoid mocks."                                                                                    |
| **Point to sources**     | "why does ExecutionFactory have such a weird api?"    | "look through ExecutionFactory's git history and summarize how its api came to be"                                                                                             |
| **Describe the symptom** | "fix the login bug"                                   | "users report that login fails after session timeout. check the auth flow in src/auth/, especially token refresh. write a failing test that reproduces the issue, then fix it" |
| **Provide verification** | "implement a function that validates email addresses" | "write a validateEmail function. example test cases: user@example.com is true, invalid is false … run the tests after implementing"                                            |

Two more levers worth knowing on day one. Reference a file with `@` instead of describing where it lives — Claude reads it before replying. And paste the actual error text, screenshot or log rather than paraphrasing it; the docs' "address root causes" row is literally "the build fails with this error: \[paste error]".

### A prompt is the start of a conversation, not a contract

You do not need a perfect prompt, because you are not committed to it. While Claude is working:

- Press `Esc` to stop it immediately. The running tool call is cancelled and your context is kept.
- Type a correction and press `Enter` to send it **without** stopping the running tool — Claude reads it as soon as the current action finishes and adjusts before choosing its next step.

That is why "start specific, then iterate" beats "write the perfect prompt". The cost of a slightly-wrong first prompt is one `Esc`.

Read those four recordings honestly, because they do not say what a tidy lesson would like them to say.

**"fix it" worked.** On a four-file repository whose git history contains a commit literally called `seed bug B1 - off-by-one in paginate`, Claude found the bug from two words. That is a fact about this lab, not about your codebase. Scale the repository up and "fix it" becomes "fix what?" — and you pay for the search in turns and context.

**"review store.ts" also worked**, and returned a review. Note what came back at the end: _"Let me know if you'd like me to fix the off-by-one."_ A prompt with a target but no goal buys you a round trip.

**"make the store code faster" is the interesting failure.** There was no evidence the store was slow, and no definition of "faster", so Claude invented both: it proposed replacing the array with a `Map`, rewriting six functions — and explicitly listed the _actual_ failing bug as out of scope. A prompt with no verifiable goal does not produce nothing. It produces confident work on the wrong problem.

**The fourth prompt** named the symptom with numbers, named the two files, set a boundary ("Do not edit any files") and asked for three specific artefacts. It returned exactly three artefacts and a closing line: _"No files were edited, per your instruction."_

## Anti-patterns

**Describing the code instead of naming the symptom.** Pasting a function into the prompt and asking "is this right?" throws away the agent's biggest advantage — it can read the file, the tests and the git history. _Fix:_ describe what a user sees going wrong, and name the directory.

**Asking for a change with no way to check it.** "Make it faster", "clean this up", "improve the error handling" have no pass/fail. _Fix:_ attach a check — a test to run, a command that must exit 0, a number that must change — in the same message.

**Dictating the steps.** "Open `store.ts`, go to line 57, change `page` to `page - 1`" is a slow way to type an edit yourself. _Fix:_ state the goal and the constraint; let Claude find line 57.

**Prompting into a polluted session.** The third and fourth correction on the same point rarely lands, because the context now holds three failed approaches. _Fix:_ `/clear`, then one better prompt that incorporates what you learned.

**Waiting for the turn to finish before correcting.** Watching Claude head down the wrong path for two more minutes costs you time and context. _Fix:_ `Esc` to stop, or type the correction and press `Enter` to steer without stopping.

**Treating a claim as evidence.** "The tests pass" is a sentence. The test runner's summary line is evidence. _Fix:_ ask for the command and its output, and read it.
