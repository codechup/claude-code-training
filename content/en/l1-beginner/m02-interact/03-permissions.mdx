## Objectives & prerequisites

By the end of this lesson you can:

- Name all six permission modes — `default` (labelled **Manual**), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` — and say what runs without asking in each.
- Switch modes three ways: `Shift+Tab` in a session, `--permission-mode` at startup, `permissions.defaultMode` in a settings file.
- Write allow, ask and deny rules with the correct `Tool(specifier)` syntax, including where the `*` belongs in a `Bash` rule.
- State the evaluation order — **deny, then ask, then allow** — and explain why a deny rule cannot carry exceptions.
- Predict which settings file wins when two disagree, and know which values a project settings file is not allowed to set.

**Prerequisites.** Lesson `02-tools-read-edit-run` (permission rules are written in tool names), and a clone of the lab repository.

<WhenNotToUse>
  Permission rules are not a security boundary against a hostile repository or a hostile web page.
  They constrain what Claude Code will run, not what a command does once it runs, and they are
  enforced by Claude Code rather than by the model — instructions in a prompt or in `CLAUDE.md`
  shape what Claude *tries*, never what is *allowed*. For untrusted code you want isolation as well:
  the Bash sandbox, a container or a VM (level 3's security module). And do not reach for
  `bypassPermissions` to make prompts stop: the docs restrict it to isolated containers and VMs
  without internet access, and the modes below solve the prompt-fatigue problem properly.
</WhenNotToUse>

## Concept

### Modes set the baseline

A permission mode decides which actions run **without asking you first**. Rules then layer on top.

| Mode                | What runs without asking                                                                               | Best for                                        |
| ------------------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| `default`           | Reads only                                                                                             | Reviewing every action yourself, sensitive work |
| `acceptEdits`       | Reads, file edits, and common filesystem commands (`mkdir`, `touch`, `mv`, `cp`, `rm`, `rmdir`, `sed`) | Iterating on code you are reviewing             |
| `plan`              | Reads, plus classifier-approved commands when auto mode is available                                   | Exploring a codebase before changing it         |
| `auto`              | Everything, with background safety checks by a classifier model                                        | Long tasks, reducing prompt fatigue             |
| `dontAsk`           | Only pre-approved tools                                                                                | Locked-down CI and scripts                      |
| `bypassPermissions` | Everything                                                                                             | Isolated containers and VMs only                |

Two naming points that trip people up. The mode whose config value is `default` is shown as **Manual** in the CLI, in `claude --help`, in the IDE extensions and in the desktop app; the CLI also accepts `manual` as an alias wherever you type the value (Claude Code v2.1.200 or later). And `auto` is not "no checks" — a second model, the classifier, reviews actions in the background and blocks the risky ones instead of asking you.

Which mode a **new** session starts in depends on how you launched it. On Pro, Max and Team plans an interactive terminal or VS Code session starts in `auto`; a `claude -p` run, an Agent SDK session, an Enterprise plan or a Console API key starts in `default`. That last one matters for every headless example on this site: **`-p` starts in Manual mode unless you say otherwise.**

### Switching modes

<CodeBlock title="three ways to set the mode">

```bash
# 1. During a session: press Shift+Tab to cycle
#    auto -> default -> acceptEdits -> plan -> back to default
#    The status bar shows the active mode:
#      "⏸ manual mode on"   "⏵⏵ accept edits on"   "⏸ plan mode on"
#      "⏵⏵ auto mode on"    "⏵⏵ don't ask on"      "⏵⏵ bypass permissions on"

# 2. At startup, for one session:
claude --permission-mode plan

# 3. As a default, in a settings file:
#    {"permissions": {"defaultMode": "default"}}
```

</CodeBlock>

`dontAsk` never appears in the `Shift+Tab` cycle — set it with the flag. `bypassPermissions` appears in the cycle only if the session was started in a way that enables it. The same `--permission-mode` flag works with `-p`.

### Rules: allow, ask, deny

Rules are written `Tool` or `Tool(specifier)`:

<CodeBlock title=".claude/settings.json">

```json
{
  "permissions": {
    "allow": ["Bash(npm run *)", "Bash(git commit *)", "Read(./docs/**)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "WebFetch"]
  }
}
```

</CodeBlock>

Three things to internalise about `Bash` wildcards, because getting them wrong is the most common permissions mistake:

- **Put the `*` after the subcommand.** Everything before the first `*` is matched literally. `Bash(git log *)` allows only `git log`; `Bash(git * main)` allows `git push origin main` — and `git -c core.fsmonitor=<script> diff main`, which runs a program you named.
- **A trailing `* ` with a space before it also matches the bare command.** `Bash(ls *)` matches `ls` and `ls -la`, but not `lsof`. `Bash(ls*)` — no space — matches `lsof` too.
- **`:*` is the same as a trailing ` *`.** `Bash(ls:*)` ≡ `Bash(ls *)`. The permission dialog writes the space form when you pick "Yes, and don't ask again".

You can also match a top-level input parameter with `Tool(param:value)` in a **deny or ask** rule — `Agent(model:opus)`, `Bash(run_in_background:true)` — but not a tool's primary content field (`command`, `file_path`, `url`), because a compound command could slip past it.

### The one prompt this lesson turns on

Every rule above exists to answer one question about one prompt. Keep this one in mind while you read
the lab:

```text
Run the test suite and tell me what fails.
```

In `default` mode that prompt stops for approval before the test runner starts. In `acceptEdits` it
still stops, because `npm test` is not a filesystem command. With `allow: ["Bash(npm test)"]` it runs
straight through. With `deny: ["Bash(npm test)"]` it is refused no matter which mode you are in — and
that last case is the one the lab records.

### The order that decides everything

> Rules are evaluated in order: **deny, then ask, then allow.** The first match in that order determines the outcome, and rule specificity doesn't change the order.

Two consequences worth memorising:

1. **A deny rule cannot carry exceptions.** `deny: ["Bash(aws *)"]` blocks `aws s3 ls` even if `allow` also lists `Bash(aws s3 ls)`.
2. **A deny in any scope beats an allow in any other scope.** User settings allow, project settings deny → denied. Project allows, user denies → denied. Managed settings sit highest of all: no other level, command-line arguments included, overrides a managed permission rule.

A **bare** tool name as a deny rule (`"deny": ["Bash"]`) removes the tool from Claude's context entirely — it never sees the tool exists. A scoped rule (`Bash(rm *)`) leaves the tool available and blocks matching calls.

Use `/permissions` in a session to see every active rule and which `settings.json` each came from.

The first recording is the one that surprises people: `--allowedTools "Read"` looks like a lockdown, and the session still ran the test suite. It did so because `--allowedTools` **adds** to the allow rules that settings files already contribute — and because `dontAsk` permits the built-in read-only Bash commands too. If you want a genuinely sealed run, deny what you do not want; do not merely omit it from the allowlist.

The second recording quotes Claude Code's own refusal text, which is worth reading once in full: it tells the model it may look for a legitimate alternative tool, but must not work around the _intent_ of the denial, and must stop and explain if the capability is essential.

The third is the precedence rule as a one-liner. The project's `.claude/settings.json` allows `Bash(npm test)`. A deny rule supplied at a higher-precedence scope blocks it anyway. Deny wins, every time, from any scope.

## Anti-patterns

**Using an allowlist as a denylist.** Leaving a tool out of `--allowedTools` does not seal it — settings files, read-only Bash commands and the mode itself can all still permit it. _Fix:_ write explicit `deny` rules for what must never run.

**Writing `Bash(git * main)` and calling it narrow.** The `*` stands in for the subcommand, so that rule permits `git push origin main` and `git -c core.fsmonitor=<script> diff main`. _Fix:_ put the `*` after the subcommand — `Bash(git log *)`.

**Expecting a specific allow to beat a broad deny.** `deny: ["Bash(aws *)"]` plus `allow: ["Bash(aws s3 ls)"]` denies the read-only command too. _Fix:_ deny narrowly, or use `ask` when you want a prompt rather than a block.

**Reaching for `bypassPermissions` on your laptop.** It skips checks including writes to protected paths such as `.git` and `.claude`. The docs restrict it to isolated containers and VMs without internet access. _Fix:_ use `acceptEdits` for edit-heavy work, `auto` for long tasks, or a sandbox.

**Telling Claude in `CLAUDE.md` what it may not do and calling that a control.** Permission rules are enforced by Claude Code, not by the model; prose shapes intent, not authority. _Fix:_ `/permissions`, a settings rule, a permission mode, or a `PreToolUse` hook.

<Callout variant="changed">
  `"defaultMode": "bypassPermissions"` and `"defaultMode": "auto"` in a project's
  `.claude/settings.json` or `.claude/settings.local.json` no longer take effect — those two values
  apply only from user or managed settings. Setting `bypassPermissions` there starts the session in
  Manual mode instead. Verified against `permission-modes.md` for Claude Code 2.1.263.
</Callout>
