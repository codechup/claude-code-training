## Objectives & prerequisites

By the end of this lesson you can:

- Use `/memory` to list, open and edit every memory file across user and project scope.
- Tell `/memory` and `/context` apart, and know which question each one answers.
- Add something to memory by asking, and choose whether it lands in auto memory or in `CLAUDE.md`.
- Prune a stale memory, and know where the pruning has to happen.
- Recognise the removed `#` shortcut in an old tutorial and know what replaced it.

**Prerequisites.** Lessons `01-claude-md` through `04-auto-memory`. An interactive Claude Code session — everything here is TUI, not headless.

<WhenNotToUse>
  `/memory` is an interactive editor: it opens files in your editor and, for a terminal editor like
  Vim, hands over the terminal until you exit. None of that belongs in a script, a CI job or a
  `claude -p` run. Automation edits memory files the ordinary way — they are plain markdown on disk,
  and a script should write them directly rather than driving a TUI. And `/memory` is not a load
  check: it lists locations, including ones that do not exist yet, which is a different question
  from what the current session actually read.
</WhenNotToUse>

## Concept

### `/memory` — see and edit everything

`/memory` lists your `CLAUDE.md`, `CLAUDE.local.md` and other memory file locations across user and project scopes. It includes user and project `CLAUDE.md` entries for files that **do not exist yet**, which is the fast way to create one: select an entry and, if the file is missing, it is created first and then opened.

It does three things in one screen:

- Select any file to open it in your editor.
- Toggle auto memory on or off (this writes `autoMemoryEnabled` to `~/.claude/settings.json`).
- Open the auto memory folder, to browse what Claude has saved for this repository.

<CodeBlock title="in an interactive session">

```text
/memory
```

</CodeBlock>

How the editor behaves depends on which one you use. A GUI editor such as VS Code opens the file in a separate window and you can keep using the session while it is open. A terminal editor such as Vim takes over the terminal until you exit it.

### `/memory` versus `/context`

They answer two different questions, and confusing them is the most common way to spend twenty minutes debugging nothing:

| Command    | Question it answers                                                        |
| ---------- | -------------------------------------------------------------------------- |
| `/memory`  | What memory files exist, or could exist, and let me edit them              |
| `/context` | What actually loaded into **this** session — see the **Memory files** list |

If an instruction is not being followed, `/context` first. A file that is missing from that list is a file Claude cannot see, and no amount of rewording it will help.

<CodeBlock title="the debugging order">

```text
/context
/memory
/doctor
```

</CodeBlock>

`/context` tells you what loaded, `/memory` lets you fix it, and `/doctor` (alias `/checkup`) proposes trims for a checked-in `CLAUDE.md` — cutting content Claude can derive from the codebase and keeping pitfalls, rationale and conventions that differ from tool defaults.

### Quick notes: ask, do not type a prefix

When you ask Claude to remember something — "always use pnpm, not npm", or "remember that the API tests require a local Redis instance" — Claude saves it to auto memory.

This lesson's worked example prompt is the one that puts the note where you want it rather than where Claude guesses:

```text
Add this to CLAUDE.md: relative imports keep the explicit .ts extension,
because this project runs TypeScript on Node without a build step.
```

The distinction is worth being deliberate about:

| You want it…                                  | Say                             | It lands in                          |
| --------------------------------------------- | ------------------------------- | ------------------------------------ |
| Remembered for you, on this machine, per repo | "Remember that …"               | Auto memory (`~/.claude/projects/…`) |
| Committed, shared with the team               | "Add this to CLAUDE.md: …"      | The project `CLAUDE.md`              |
| Written by your own hand                      | `/memory`, then select the file | Whichever file you selected          |

Older tutorials tell you to start a message with `#` instead. That shortcut is gone — see the Changed callout after the anti-patterns below.

### Pruning

Memory files are excluded from the transcript retention sweep — `MEMORY.md` and its topic files stay until you or Claude edits or deletes them. Nothing expires on its own, so pruning is a thing you do, not a thing that happens.

Prune in the place the memory lives:

- **A stale `CLAUDE.md` line** — `/memory`, open the file, delete the line. Or let `/doctor` propose the trim.
- **A stale auto memory** — `/memory`, open the auto memory folder, delete the topic file, and delete its line from `MEMORY.md`. Both are plain markdown; editing them by hand is expected, not a hack.
- **A `MEMORY.md` that has grown past 200 lines** — the overflow is silently not loaded. Merge entries down to one line each and push detail into topic files.
- **Two instructions that contradict each other** — this is the one worth hunting for. Claude may pick either arbitrarily, so an outdated rule you never deleted is not neutral; it is a coin flip. Review your `CLAUDE.md`, your nested `CLAUDE.md` files and your `.claude/rules/` together, not one at a time.

For debugging which instruction files load, when and why, there is an `InstructionsLoaded` hook — useful when a path-scoped rule or a lazily-loaded subdirectory file is behaving unexpectedly. Hooks are module `m07-hooks`.

## Anti-patterns

**Using `/memory` to check whether a file loaded.** It lists locations, including ones that do not exist yet. That is not the same question. _Fix:_ `/context`, and read the **Memory files** list.

**Adding, never removing.** Nothing expires. Every line you add is a line loaded into every session until you delete it, and old advice does not politely stand aside for new advice. _Fix:_ treat memory files like code — review and delete on the same schedule you add.

**Saying "remember this" for something the team needs.** That lands in auto memory: machine-local, uncommitted, invisible to everyone else. _Fix:_ say "add this to CLAUDE.md" when you mean the project, and commit it.

**Fixing a conflict by adding a third instruction.** "Ignore the rule above about tabs" leaves both earlier rules in context and adds a new one to disagree with. _Fix:_ delete the wrong one.

**Following a 2025 tutorial's `#` shortcut.** It was removed in 2.0.70; typing it does nothing special. _Fix:_ ask Claude to edit `CLAUDE.md`, or open it with `/memory`.

**Driving `/memory` from a script.** It is a TUI that can hand your terminal to Vim. _Fix:_ memory files are plain markdown on disk — write them directly.

<Callout variant="changed">
  Older tutorials tell you to start a message with `#` to add a quick memory entry. The official
  changelog’s 2.0.70 entry (15 December 2025) reads "Removed # shortcut for quick memory entry (tell
  Claude to edit your CLAUDE.md instead)", and no current page documents it. Ask Claude to edit your
  `CLAUDE.md`, or open the file with `/memory`. Typing `#` at the start of a prompt today is just a
  prompt that begins with a hash.
</Callout>
