## Objectives & prerequisites

By the end of this lesson you can:

- Put a topic-scoped instruction in `.claude/rules/<topic>.md` instead of growing `CLAUDE.md`.
- Write `paths:` frontmatter with glob patterns so a rule loads only when Claude reads matching files.
- Say precisely what triggers a path-scoped rule — and what does not.
- Choose between a rule, a `CLAUDE.md` entry and a skill.
- Use `~/.claude/rules/` for personal conventions across every project.

**Prerequisites.** Lessons `01-claude-md` and `02-hierarchy-imports`. A clone of `codechup/claude-code-lab` for the lab.

<WhenNotToUse>
  A rule still loads into context — every session for an unscoped rule, and on every matching file
  read for a scoped one. For instructions that only matter while you are doing one particular task,
  a skill is the better home: it loads when you invoke it or when Claude judges it relevant to your
  prompt, not before. And a path-scoped rule is a poor choice for anything that must survive
  `/compact` intact, because scoped rules live in message history and are summarised away with
  everything else, reloading only when a matching file is read again.
</WhenNotToUse>

## Concept

### Rules are `CLAUDE.md`, split by topic

Put markdown files in `.claude/rules/`. Each covers one topic, with a descriptive filename. All `.md` files are discovered recursively, so subdirectories work:

<CodeBlock title="a project's .claude/ layout">

```text
your-project/
├── .claude/
│   ├── CLAUDE.md           # Main project instructions
│   └── rules/
│       ├── code-style.md   # Code style guidelines
│       ├── testing.md      # Testing conventions
│       └── security.md     # Security requirements
```

</CodeBlock>

A rule **without** `paths:` frontmatter is loaded at launch with the same priority as `.claude/CLAUDE.md`. So splitting an unscoped `CLAUDE.md` into unscoped rules buys you tidiness, exactly like `@path` imports — and exactly like imports, it buys you no context back.

The frontmatter is what makes rules different.

### `paths:` frontmatter

Add a `paths` list of glob patterns and the rule becomes conditional: it applies only when Claude works with matching files.

<CodeBlock title=".claude/rules/api.md">

```markdown
---
paths:
  - 'src/api/**/*.ts'
---

# API Development Rules

- All API endpoints must include input validation
- Use the standard error response format
- Include OpenAPI documentation comments
```

</CodeBlock>

The trigger is specific and worth memorising: **path-scoped rules fire when Claude reads a file matching the pattern** — not on every tool use, and not because the file merely exists in the repo. If Claude never opens a file under `src/api/`, that rule never enters the conversation. Matching also works when Claude reaches a file through a symlinked path into the project directory.

Common patterns:

| Pattern                | Matches                               |
| ---------------------- | ------------------------------------- |
| `**/*.ts`              | All TypeScript files in any directory |
| `src/**/*`             | All files under `src/`                |
| `*.md`                 | Markdown files in the project root    |
| `src/components/*.tsx` | React components in one directory     |

You can list several patterns, and use brace expansion for multiple extensions:

<CodeBlock title=".claude/rules/typescript.md">

```markdown
---
paths:
  - 'src/**/*.{ts,tsx}'
  - 'lib/**/*.ts'
  - 'tests/**/*.test.ts'
---
```

</CodeBlock>

Braces multiply: `src/*.{ts,tsx}` expands to two patterns, `{a,b}/{c,d}/*.{ts,tsx}` to eight. A rule's whole `paths` list shares one budget of 1,000 expanded patterns and 4 MiB; patterns without braces do not count against it. A pattern that would blow the budget is used unexpanded, and its literal braces then match nothing.

One glob footgun: `[` starts a bracket expression. A pattern like `photos [2024/**` that cannot be read as one is invalid — it matches nothing, while the rule's other patterns keep working. Escape a literal bracket as `photos \[2024/**`.

### User-level rules

`~/.claude/rules/` applies to every project on your machine. Use it for preferences that are yours rather than the project's — commit message style, how you like tests laid out. User-level rules are loaded **before** project rules, which gives project rules higher priority.

### Rule, CLAUDE.md, or skill?

This lesson's worked example prompt is the one that forces Claude to show its own sources, which is how you tell the three apart in practice:

```text
Read src/store.ts. Do not edit anything. Then list, as short bullets, the
conventions this project expects for code under src/, and say for each where
that convention comes from.
```

The answer names `.claude/CLAUDE.md`, `.claude/rules/style.md` or nothing at all — and that tells you whether your rule is where you think it is.

### Sharing rules across projects

`.claude/rules/` supports symlinks, so one maintained set of rules can serve several repositories. Symlinks are resolved and loaded normally, and circular symlinks are detected and handled.

<OSTabs>
  <Fragment slot="macos">

```bash
ln -s ~/shared-claude-rules .claude/rules/shared
ln -s ~/company-standards/security.md .claude/rules/security.md
```

  </Fragment>
  <Fragment slot="linux">

```bash
ln -s ~/shared-claude-rules .claude/rules/shared
ln -s ~/company-standards/security.md .claude/rules/security.md
```

  </Fragment>
  <Fragment slot="windows">

```powershell
# Requires Developer Mode or an elevated shell.
New-Item -ItemType SymbolicLink -Path .claude/rules/shared -Target $HOME/shared-claude-rules
New-Item -ItemType SymbolicLink -Path .claude/rules/security.md -Target $HOME/company-standards/security.md
```

  </Fragment>
</OSTabs>

## Anti-patterns

**Splitting an unscoped `CLAUDE.md` into unscoped rules and expecting a context saving.** Rules without a `paths` field load at launch, unconditionally. _Fix:_ the saving comes from `paths:`, not from the file split.

**Scoping a rule that has to be true everywhere.** "Never commit secrets" behind `paths: ['src/**']` is off duty every time Claude is not reading `src/`. _Fix:_ leave genuinely global instructions unscoped, or in `CLAUDE.md`.

**Assuming a rule fires because a matching file exists.** The trigger is Claude _reading_ a matching file. A session that never opens `src/api/` never sees the API rule. _Fix:_ if you need it earlier, drop the scope or point the session at the area first.

**Expecting a scoped rule to survive `/compact`.** Path-scoped rules and nested `CLAUDE.md` files live in message history and are summarised away; they reload as Claude re-reads matching files. _Fix:_ if an instruction must persist across compaction, drop the `paths:` frontmatter or move it to the project-root `CLAUDE.md`.

**Writing a glob you never verified.** `photos [2024/**` matches nothing. A pattern with runaway brace expansion is used unexpanded and its literal braces match nothing either. _Fix:_ prove the rule fires by asking Claude to read one matching file and name its sources, exactly as this lab does.

**Restating in a rule what `CLAUDE.md` already says.** Duplicated instructions cost context twice and drift apart. _Fix:_ one home per fact.

<Callout variant="changed">
  Rules that load on demand — path-scoped rules and rules in nested `.claude/rules/` directories —
  are now skipped when you exclude `project` from `--setting-sources`. Before v2.1.211 they loaded
  even then.
</Callout>
