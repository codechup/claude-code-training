## Objectives & prerequisites

By the end of this lesson you can:

- Say what auto memory is, who writes it, and how it differs from `CLAUDE.md`.
- Name the four memory types — `user`, `feedback`, `project`, `reference` — and what goes in each.
- Find the memory directory for a repository, and read `MEMORY.md` and its topic files.
- Explain the 200-line / 25 KB index limit and why it exists.
- Turn auto memory off for one session, one project, or entirely.

**Prerequisites.** Lesson `01-claude-md`. A scratch folder for the lab, and a terminal.

<WhenNotToUse>
  Auto memory is machine-local: files are not shared across machines or cloud environments, and they
  are not in version control. Anything your team needs — build commands, conventions, architecture
  decisions — belongs in a committed `CLAUDE.md` or a rule, not in notes on one laptop. Turn auto
  memory off entirely in a shared or ephemeral environment, in a CI runner where a per-project
  directory would accumulate for no one, and in any session where you would rather nothing about the
  conversation persisted afterwards.
</WhenNotToUse>

## Concept

### Two systems, one context window

Both memory systems load at the start of every conversation, and Claude treats both as context rather than enforced configuration. The split is about who writes them:

|                  | CLAUDE.md files                           | Auto memory                                                                                       |
| ---------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Who writes it    | You                                       | Claude                                                                                            |
| What it contains | Instructions and rules                    | Learnings and patterns                                                                            |
| Scope            | Project, user, or org                     | Per repository, shared across worktrees                                                           |
| Loaded into      | Every session                             | Every session (first 200 lines or 25 KB)                                                          |
| Use for          | Coding standards, workflows, architecture | Your preferences, corrections you give Claude, project context Claude cannot derive from the code |

### The four types

As it works, Claude saves four kinds of note. The docs describe the kind as a `type` field in the memory file's frontmatter; in the recording below it appears as `type:` under a `metadata:` block in that frontmatter. The four kinds are:

- **`user`** — your role, expertise and working preferences.
- **`feedback`** — corrections you give Claude, and approaches you confirm.
- **`project`** — ongoing work, deadlines and decisions Claude cannot derive from the code or git history.
- **`reference`** — where to find information outside the project, such as an issue tracker or a dashboard.

Two exclusions matter as much as the four inclusions. Claude **skips anything it can derive from the codebase** — architecture, file paths, a debugging fix — and it **skips anything your `CLAUDE.md` files already say**. It also does not save something every session; it decides case by case whether a fact would be useful in a future conversation.

This is the sentence to hold on to: auto memory is for what the code cannot tell Claude and you have not written down.

### Where the files live

Each project gets its own directory at `~/.claude/projects/<project>/memory/`. The `<project>` segment is derived from the git repository, so **every worktree and subdirectory of one repo shares a single auto memory directory**. Outside a git repository, the project root is used instead.

<CodeBlock title="~/.claude/projects/<project>/memory/">

```text
MEMORY.md           # Index, one line per memory, loaded into every session
user_role.md        # One memory
feedback_testing.md # One memory
...                 # Any other topic files Claude creates
```

</CodeBlock>

`MEMORY.md` is an index, not a store. Claude reads and writes files in this directory throughout a session, using `MEMORY.md` to keep track of what is where. **Topic files are not loaded at startup** — Claude reads them on demand with its ordinary file tools when it needs the detail.

You can move the directory with `autoMemoryDirectory` in `settings.json`, read from any settings scope. The value must be an absolute path or start with `~/`:

<CodeBlock title="settings.json">

```json
{
  "autoMemoryDirectory": "~/my-custom-memory-dir"
}
```

</CodeBlock>

Set from a project's `.claude/settings.json` or `.claude/settings.local.json`, Claude Code honours it under the same workspace-trust rule as hooks in settings files — a cloned repository can supply those files, so trust is checked first.

### The 200-line index limit

The first 200 lines of `MEMORY.md`, or the first 25 KB, whichever comes first, are loaded at the start of every conversation. Anything past that threshold is not loaded.

Claude Code enforces this actively. After Claude writes to `MEMORY.md` it measures the file: near a limit, Claude is reminded to shorten it — one line per entry, detail into topic files, stale entries merged or dropped. Over a limit, the write still succeeds but Claude Code returns an error telling Claude to rewrite the index, because everything past the limit is dropped on the next load.

That limit applies only to `MEMORY.md`. A `CLAUDE.md` is loaded in full up to 4 MiB, and a larger one is skipped entirely.

Retention is deliberately separate too: Claude Code deletes old session transcripts after the `cleanupPeriodDays` period, but the memory directory is excluded from that sweep. `MEMORY.md` and its topic files stay until you or Claude edits or deletes them.

### Turning it off

Auto memory is on by default. Three levers, from narrowest to broadest:

| Scope       | How                                                                                                |
| ----------- | -------------------------------------------------------------------------------------------------- |
| One session | `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` — takes precedence over the setting, in either direction       |
| One project | `"autoMemoryEnabled": false` in that project's settings                                            |
| Everywhere  | The auto memory toggle in `/memory`, which writes `autoMemoryEnabled` to `~/.claude/settings.json` |

<OSTabs>
  <Fragment slot="macos">

```bash
CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude -p "Summarise the failing test." --output-format text
```

  </Fragment>
  <Fragment slot="linux">

```bash
CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude -p "Summarise the failing test." --output-format text
```

  </Fragment>
  <Fragment slot="windows">

```powershell
$env:CLAUDE_CODE_DISABLE_AUTO_MEMORY = "1"
claude -p "Summarise the failing test." --output-format text
```

  </Fragment>
</OSTabs>

When `autoMemoryEnabled` is `false`, Claude neither reads from nor writes to the memory directory. The settings reference is explicit about the ranking: `CLAUDE_CODE_DISABLE_AUTO_MEMORY` is listed as `autoMemoryEnabled`’s per-session override and takes precedence over it "in either direction", so the variable can turn auto memory back on for one session as well as off.

### What this looks like in a real project

This training site's own repository is a worked example of the division of labour, and it is public, so you can read every file in it. Its committed `CLAUDE.md` holds what every session must know — the session protocol, the hard rules about evidence and public-repo hygiene, the command list. Its `.claude/rules/content.md` carries lesson-authoring conventions behind `paths: ['content/**/*.mdx', 'content/_shared/**']`, so they cost context only while someone is actually editing a lesson. Neither file records that a particular contributor prefers PowerShell commands, or that they were corrected last week about transcript formatting. That is the auto-memory half — per person, per machine, uncommitted, and nobody else's business.

The worked example prompt for this lesson is the one that puts something in that half deliberately:

```text
Remember for future sessions: I am a technical writer, not the maintainer of
this project, and I always want commands given for Windows PowerShell first.
```

## Anti-patterns

**Relying on auto memory for anything a teammate needs.** It is machine-local and not in version control, so "Claude already knows" is true for exactly one person. _Fix:_ if it matters to the team, move it into `CLAUDE.md` or a rule and commit it.

**Never reading it.** Notes accumulate quietly and stay until edited or deleted — they are excluded from the transcript retention sweep. A stale preference from six months ago is still shaping answers today. _Fix:_ run `/memory`, open the auto memory folder, and read it now and then.

**Letting `MEMORY.md` become the store instead of the index.** Past 200 lines or 25 KB the overflow is simply not loaded, so the memories you think are active are invisible. _Fix:_ one line per entry, detail in topic files — and take the "shorten the index" reminder seriously when it appears.

**Assuming a subagent inherits it.** The main conversation's auto memory is not loaded into subagents; the exception is a fork, which inherits the parent conversation. A subagent's own memory, enabled with its `memory` frontmatter field, is a separate directory. _Fix:_ do not use auto memory as a channel between a session and its subagents.

**Leaving it on in a shared or throwaway environment.** A CI runner or a shared box accumulates a per-project directory nobody will ever read. _Fix:_ `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` for the session, or `autoMemoryEnabled: false` for the project.

**Expecting per-worktree memories.** The `<project>` segment is derived from the git repository, so every worktree of one repo writes into one directory. _Fix:_ if you need genuinely separate notes, that is what `autoMemoryDirectory` is for.

<Callout variant="changed">
  When Claude writes a memory file that already begins with YAML frontmatter, Claude Code now stamps
  the write time into a `modified` field as an ISO 8601 timestamp, so both you and Claude can see
  how current a fact is. Files with no frontmatter never get one added. The `modified` field
  requires Claude Code v2.1.214 or later.
</Callout>
