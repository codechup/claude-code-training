## Objectives & prerequisites

By the end of this lesson you can:

- Say what `CLAUDE.md` is and when in a session it is read.
- Decide whether a given fact belongs in `CLAUDE.md`, in a path-scoped rule, or in a skill.
- Put the file in the right place — `./CLAUDE.md` or `./.claude/CLAUDE.md` — and know why either works.
- Draft one with `/init` and refine it, instead of writing 200 lines by hand.
- Prove the file is loaded, two ways: `/context` in an interactive session, and a headless run whose answer changes because of it.

**Prerequisites.** Claude Code installed and signed in (module `m01-start`), and a terminal in a project directory you can write to. The lab uses the course sandbox repository, so a `git clone` of `codechup/claude-code-lab` too.

<WhenNotToUse>
  `CLAUDE.md` is context, not enforcement. Claude reads it and tries to follow it; there is no
  guarantee of strict compliance. If a thing must happen at a fixed moment — before every commit,
  after every edit — write a hook instead, because hooks run as shell commands regardless of what
  Claude decides. If a thing must be blocked outright, use `permissions.deny` in settings, or a
  `PreToolUse` hook. And if a thing is a multi-step procedure, or only matters for one corner of the
  codebase, it does not belong in a file that loads into every single session: make it a skill or a
  path-scoped rule, so it costs context only when it is relevant.
</WhenNotToUse>

## Concept

### What it is

Every Claude Code session starts with a fresh context window. `CLAUDE.md` is one of the two mechanisms that carry knowledge across that boundary — the one **you** write. (The other is auto memory, which Claude writes; lesson `04-auto-memory` covers it.)

The file is plain markdown. Claude Code reads it at the start of every conversation and delivers it as a user message after the system prompt. That detail matters, and it is the reason for the "When not to use" section above: what you put in `CLAUDE.md` shapes behaviour, it does not enforce it.

### Where the project file goes

A project `CLAUDE.md` can live in either of two places, and Claude Code loads both:

| Path                  | Why you would pick it                                                    |
| --------------------- | ------------------------------------------------------------------------ |
| `./CLAUDE.md`         | Visible at the repository root; obvious to a human opening the repo.     |
| `./.claude/CLAUDE.md` | Keeps the project root clean, next to the rest of your `.claude/` setup. |

Both are committed and shared with your team through source control, so a project `CLAUDE.md` should carry project-level standards, not your personal preferences. Personal, project-specific notes go in `CLAUDE.local.md` at the project root, which you add to `.gitignore` — that is lesson `02-hierarchy-imports`.

### What belongs in it

The docs give a usefully concrete trigger list. Add something to `CLAUDE.md` when:

- Claude makes the same mistake a second time.
- A code review catches something Claude should have known about this codebase.
- You type the same correction into chat that you typed last session.
- A new teammate would need the same context to be productive.

Keep it to facts Claude should hold in every session: build and test commands, conventions, project layout, "always do X" rules. Move a multi-step procedure to a skill; move something that only matters for one area to a path-scoped rule.

Three qualities decide how reliably the file is followed:

- **Size.** Target under 200 lines. Longer files consume more context and reduce adherence. Claude Code loads a `CLAUDE.md` of up to 4 MiB in full and skips a larger one — but "it loads" is not the same as "it is followed."
- **Structure.** Markdown headers and bullets. Claude scans structure the way a reader does; organised sections beat dense paragraphs.
- **Specificity.** Write instructions concrete enough to verify. "Use 2-space indentation", not "format code properly". "Run `npm test` before committing", not "test your changes".

One more: **consistency**. If two instructions contradict each other, Claude may pick one arbitrarily. Reviewing your memory files for stale and conflicting lines is real maintenance work, not a one-off.

This lesson's worked example prompt is the one you use once the file exists, to check it actually landed:

```text
Without reading any files, tell me in two sentences what this project's
conventions say about fixing a bug that has a test.
```

If the answer comes back specific, the file is loaded. If Claude says it does not know, it is not.

<Callout>
  A useful trick for keeping notes to human maintainers out of Claude's context: block-level HTML
  comments (`<!-- … -->`) in a `CLAUDE.md` are stripped before the content is injected. Comments
  inside code blocks are preserved, and everything is visible again if Claude opens the file with
  the `Read` tool.
</Callout>

### Let `/init` write the first draft

You do not start from a blank file. Run `/init` in a project and Claude analyses the codebase and writes a starting `CLAUDE.md` with the build commands, test instructions and conventions it can discover. If a `CLAUDE.md` already exists, `/init` suggests improvements rather than overwriting it.

`/init` also reads configuration other coding agents left behind — Cursor rules in `.cursor/rules/` or `.cursorrules`, and Copilot rules in `.github/copilot-instructions.md` — and folds the relevant parts into what it generates.

Then refine. `/init` can only write down what it can derive from the code; the valuable half of a `CLAUDE.md` is the half it cannot: the pitfall that bit you last month, the convention that differs from the tool's default, the file nobody is allowed to tidy up.

<CodeBlock title="drafting and checking a project CLAUDE.md">

```text
/init
/memory
/context
```

</CodeBlock>

`/init` drafts, `/memory` opens the file in your editor to refine it, and `/context` shows what actually loaded — look for the list under **Memory files**.

There is also an interactive, multi-phase `/init`: set `CLAUDE_CODE_NEW_INIT=1` and it asks which artifacts to set up (CLAUDE.md files, skills, hooks), explores the codebase with a subagent, asks follow-up questions, and presents a reviewable proposal before writing anything.

### If you already have an AGENTS.md

Claude Code reads `CLAUDE.md`, not `AGENTS.md`. If your repository already uses `AGENTS.md` for another agent, do not duplicate it — create a `CLAUDE.md` that imports it, and add Claude-specific instructions underneath:

<CodeBlock title="CLAUDE.md">

```markdown
@AGENTS.md

## Claude Code

Use plan mode for changes under `src/billing/`.
```

</CodeBlock>

A symlink works too if you have nothing Claude-specific to add — but on Windows creating one needs Administrator privileges or Developer Mode, so prefer the `@AGENTS.md` import there.

<OSTabs>
  <Fragment slot="macos">

```bash
ln -s AGENTS.md CLAUDE.md
```

  </Fragment>
  <Fragment slot="linux">

```bash
ln -s AGENTS.md CLAUDE.md
```

  </Fragment>
  <Fragment slot="windows">

```powershell
# Requires Developer Mode or an elevated shell; the @AGENTS.md import is the portable choice.
New-Item -ItemType SymbolicLink -Path CLAUDE.md -Target AGENTS.md
```

  </Fragment>
</OSTabs>

Note where the files landed. `/init` wrote `./CLAUDE.md` at the repository root, while the before/after pair was captured against `./.claude/CLAUDE.md`. Both are project locations and Claude Code loads both, which is exactly the point of the table earlier in this lesson — but it does mean the two recordings are pointing at two different files, not one.

That middle recording is worth a second look, because it complicates the neat story. `/init` found the `TEACHING SURFACE` convention on its own — the marker is written in the source comments, so reading the code was enough. What `/init` cannot reach is anything that is not written down anywhere: the decision made in a meeting, the pitfall that bit you once, the reason a rule exists. That is the half of a `CLAUDE.md` only you can write, and it is why step 5 exists.

<Callout>
  All three recordings answer in Turkish, and the prompt never asked for it. That is not a glitch in
  the capture: the machine that produced it has a user-scope `~/.claude/CLAUDE.md` asking for
  Turkish answers, and a user-scope instruction loads into every session in every project. It is the
  clearest possible demonstration that memory files you forgot about are still shaping every answer
  — and it is exactly what lesson `02-hierarchy-imports` is about. Your own runs will answer in
  whatever language your own memory files ask for.
</Callout>

The two runs are byte-for-byte the same command. The only thing that changed between them is a file on disk.

## Anti-patterns

**Writing a `CLAUDE.md` that describes the codebase.** Directory layouts, dependency lists and architecture overviews are things Claude derives by reading the repository — and they go stale the moment someone moves a folder. `/doctor` will actively propose trimming them. _Fix:_ keep pitfalls, rationale and conventions that differ from tool defaults; delete the tour.

**Letting it grow past 200 lines.** More lines is not more adherence; it is more context spent and, past a point, less adherence. _Fix:_ split by area into `.claude/rules/` (lesson `03-rules`) so instructions load only when Claude touches matching files.

**Two rules that contradict each other.** "Prefer `async/await`" in the root file and "use `.then()` chains" in a subdirectory file is not a subtle nuance Claude will resolve for you — it may pick either. _Fix:_ read your memory files end to end when you add to them, and delete the loser.

**Putting a procedure in it.** "To cut a release: bump the version, run the changelog script, tag, push, then…" is a skill. In `CLAUDE.md` it costs context in every session, including the hundreds that never cut a release. _Fix:_ move it to a skill that loads on demand.

**Assuming the file is loaded because it exists.** Wrong directory, an exclusion pattern, a typo in the filename — plenty of ways for it to be sitting there unread. _Fix:_ `/context`, and look under **Memory files**. If it is missing, Claude cannot see it.

**Treating it as a guarantee.** "It says right there in CLAUDE.md" is not an argument the runtime accepts. _Fix:_ for anything that must be true, add the hook or the permission rule as well.

  can derive from the codebase and keeps pitfalls, rationale and conventions. The trim check
  requires Claude Code v2.1.206 or later.
</Callout>
