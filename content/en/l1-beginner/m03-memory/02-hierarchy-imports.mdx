## Objectives & prerequisites

By the end of this lesson you can:

- Name the four `CLAUDE.md` scopes — managed policy, user, project, local — and say where each file lives on your OS.
- Explain the load order, and why "concatenated" is a more accurate word than "overridden".
- Use `@path` imports to pull another file into a `CLAUDE.md`, and say what they cost.
- Know when the external-import approval dialog appears, and why.
- Skip an irrelevant ancestor `CLAUDE.md` with `claudeMdExcludes`.

**Prerequisites.** Lesson `01-claude-md`. A scratch folder you can create files in — this lab does not use the sandbox repository.

<WhenNotToUse>
  Reach for `@path` imports to organise a `CLAUDE.md`, never to shrink it: imported files are
  expanded and loaded into context at launch alongside the file that references them, so splitting
  200 lines across five imports costs exactly the same context as 200 lines in one file. If your
  problem is size rather than tidiness, path-scoped rules are the mechanism that actually helps
  (lesson `03-rules`). And do not use `claudeMdExcludes` to mute a rule you disagree with in your
  own project — that is a conversation with your team, not a settings key.
</WhenNotToUse>

## Concept

### Four places a CLAUDE.md can live

Claude Code looks in four scopes. The table is in load order, broadest first, so a project instruction lands in context after a user instruction.

| Scope                | Location                                                                                                                                                 | What it is for                                 | Shared with             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ----------------------- |
| Managed policy       | macOS `/Library/Application Support/ClaudeCode/CLAUDE.md` · Linux and WSL `/etc/claude-code/CLAUDE.md` · Windows `C:\Program Files\ClaudeCode\CLAUDE.md` | Organisation-wide instructions, deployed by IT | Everyone on the machine |
| User instructions    | `~/.claude/CLAUDE.md`                                                                                                                                    | Your preferences, in every project             | Just you, everywhere    |
| Project instructions | `./CLAUDE.md` or `./.claude/CLAUDE.md`                                                                                                                   | Team-shared project standards                  | Your team, via git      |
| Local instructions   | `./CLAUDE.local.md`                                                                                                                                      | Your personal notes for this project           | Just you, this project  |

An organisation can skip the file entirely and put the text straight into `managed-settings.json` under the `claudeMd` key. It behaves like a managed `CLAUDE.md`: it loads before user and project files, and it is honoured only in managed and policy settings — setting `claudeMd` in user, project or local settings does nothing.

### They are concatenated, not overridden

This is the part people get wrong. All discovered files are concatenated into context; a later file does not replace an earlier one.

Claude Code loads `CLAUDE.md` and `CLAUDE.local.md` from your working directory **and every directory above it**. Run Claude in `foo/bar/` and it picks up `foo/bar/CLAUDE.md`, `foo/CLAUDE.md` and any `CLAUDE.local.md` beside them. Across the tree, content is ordered from the filesystem root down to your working directory, so instructions closer to where you launched Claude are read last. Within one directory, `CLAUDE.local.md` is appended after `CLAUDE.md` — your personal notes are the last thing Claude reads at that level.

"Read last" is not the same as "wins". Where two instructions genuinely contradict each other, the docs say Claude may pick one arbitrarily — reviewing your memory files and deleting the loser is the only reliable fix. What the ordering does give you is a documented place in the sequence, and the lab below shows a run where the last-read file is the one Claude both followed and named: a `CLAUDE.local.md` saying `make ship-dev` against an imported project convention saying `make ship`.

`CLAUDE.md` files in **subdirectories below** your working directory are treated differently: they are not loaded at launch. They load on demand, when Claude reads a file in that subdirectory.

This lesson's worked example prompt is the one that makes the hierarchy visible without any guesswork:

```text
Without reading any files, answer in two sentences: which release command
applies on this machine, and which memory file does that instruction come from?
```

Asking Claude to name its own source turns an invisible mechanism into something you can check.

### `@path` imports

A `CLAUDE.md` can pull in another file with `@path/to/import`. Imported files are expanded and loaded at launch, alongside the file that references them.

- Relative and absolute paths both work. **Relative paths resolve against the file containing the import**, not your working directory.
- Imports can nest, to a maximum depth of four hops.
- Import parsing skips markdown code spans and fenced code blocks. To mention a path without importing it, wrap it in backticks: `` `@README` `` stays literal text, while `@README` outside backticks imports the file.

<CodeBlock title="CLAUDE.md">

```text
See @README for project overview and @package.json for available npm commands for this project.

# Additional Instructions
- git workflow @docs/git-instructions.md
```

</CodeBlock>

Imports are also the answer to a specific worktree problem. A gitignored `CLAUDE.local.md` exists only in the worktree where you made it. To carry personal instructions across every worktree of a repository, import a file from your home directory instead:

<CodeBlock title="CLAUDE.local.md">

```text
# Individual Preferences
- @~/.claude/my-project-instructions.md
```

</CodeBlock>

<Callout>
  That home-directory import is an **external** import: its path resolves outside your working
  directory. The first time Claude Code meets external imports in a project it shows an approval
  dialog listing the files, because a project file is something other people can commit. Decline and
  the imports stay disabled and the dialog does not come back. Imports in user-scope files
  (`~/.claude/CLAUDE.md`, `~/.claude/rules/`) are files you wrote yourself, so outside Cowork
  sessions on the desktop they load without a dialog.
</Callout>

### Loading memory from `--add-dir` directories

`--add-dir` gives Claude access to a directory outside your main working directory, but **by default its `CLAUDE.md` files are not loaded**. Opt in with an environment variable:

<OSTabs>
  <Fragment slot="macos">

```bash
CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../shared-config
```

  </Fragment>
  <Fragment slot="linux">

```bash
CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../shared-config
```

  </Fragment>
  <Fragment slot="windows">

```powershell
$env:CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD = "1"
claude --add-dir ../shared-config
```

  </Fragment>
</OSTabs>

That loads `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/rules/*.md` and `CLAUDE.local.md` from the additional directory.

### Skipping files with `claudeMdExcludes`

In a monorepo, "every directory above you" can mean several other teams' instructions. `claudeMdExcludes` skips files by path or glob. Patterns are matched against **absolute** file paths, and arrays merge across settings layers. Put it in `.claude/settings.local.json` when the exclusion is yours alone:

<CodeBlock title=".claude/settings.local.json">

```json
{
  "claudeMdExcludes": ["**/monorepo/CLAUDE.md", "/home/user/monorepo/other-team/.claude/rules/**"]
}
```

</CodeBlock>

Two limits worth knowing. Managed policy `CLAUDE.md` files **cannot** be excluded — that is the point of managed policy. And exclusions apply only to user, project and local memory files.

### What survives `/compact`

When a long session compacts, the project-root `CLAUDE.md` and unscoped rules are re-injected from disk, as is auto memory. Nested `CLAUDE.md` files in subdirectories and rules with `paths:` frontmatter are reloaded as Claude reads files they apply to — so an instruction that "disappeared" after compaction was probably given only in conversation, or lives in a nested file that has not been re-triggered yet.

## Anti-patterns

**Splitting a big `CLAUDE.md` into imports to save context.** It does not save any. Imported files load at launch, expanded, in full. _Fix:_ if you want less context, use path-scoped rules; use imports for organisation and for sharing one file between agents.

**Writing an import path relative to your working directory.** Relative import paths resolve against the file containing the import. Get that wrong in `.claude/CLAUDE.md` and `@notes/x.md` points at `.claude/notes/x.md`. _Fix:_ read the path as if you were standing in the importing file's directory.

**Committing `CLAUDE.local.md`.** It is meant to be personal and gitignored; committed, it becomes an unreviewed project instruction that also happens to be the last one read. _Fix:_ add it to `.gitignore` the moment you create it.

**Expecting a gitignored `CLAUDE.local.md` in every worktree.** It exists only where you made it. _Fix:_ import a home-directory file from it, and accept the external-import dialog once.

**Blaming the prompt for an answer your user-scope file caused.** A standing preference in `~/.claude/CLAUDE.md` applies in every project, forever, including the ones where it makes no sense. _Fix:_ when a result surprises you, run `/context` and read what is actually loaded before rewriting the prompt.

**Reaching for `claudeMdExcludes` against a managed file.** Managed policy `CLAUDE.md` cannot be excluded by any setting. _Fix:_ if the instruction is wrong, that is a conversation with whoever deploys it.

<Callout variant="changed">
  Excluding a rules file you reach through a symlink now works whether the pattern matches the path
  under `.claude/rules/` or the link target — either one excludes the file. Before v2.1.239, only a
  pattern matching the link target worked.
</Callout>
