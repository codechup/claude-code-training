## Objectives & prerequisites

By the end of this lesson you can:

- Start a session in a real project and give Claude a task it can verify itself.
- Watch the full loop happen: read the failing tests, find the cause, edit the source, re-run the tests.
- Read the TUI — the prompt bar, the permission-mode indicator, the task checklist, the transcript viewer.
- Use the handful of keys that matter on day one: `Esc`, `Shift+Tab`, `Ctrl+O`, `Ctrl+T`, `Ctrl+C`, `Ctrl+D`, `!`, `@`, `?`.
- Reproduce the same work headlessly with `claude -p`, so you have a capture you can paste into a PR.

**Prerequisites.** Lessons `02-install` and `03-authenticate`: `claude --version` prints a version and `claude auth status` exits 0. For the lab repository you also need `git` and the Node.js version its `package.json` declares in `engines` — Node.js 24 or later at the time of writing.

<WhenNotToUse>
  Do not make your first session a large, unverifiable refactor of a repository you care about. The
  loop's value comes from the check at the end, and a first session is also when you are least able
  to tell a good result from a confident one. Do not start in a directory with uncommitted work you
  cannot afford to lose, either — start where `git status` is clean, so `git diff` tells you exactly
  what changed. And if you only want to read code rather than change it, you do not need a session
  at all: `claude -p "…"` answers and exits.
</WhenNotToUse>

## Concept

### What a first session should look like

A good first task has three properties: it is small, it is in a repository you can throw away, and **it comes with its own check**. A failing test is the ideal shape — Claude can run it before, make a change, and run it again, and neither of you has to take the other's word for anything.

The lab repository is built for exactly this. At the tag `lesson/m01-04-start`, `npm test` fails three times: `addTask()` in `src/store.ts` accepts an empty title and a negative priority without complaint, so two unit tests and one API test that expect a rejection all fail.

### The one example prompt

```text
npm test fails with three failures. Find the cause, fix it in src/, and run npm test again
to prove it passes.
```

Read what that does and does not say. It names the symptom (`npm test` fails), the scope (`src/`), and the proof (`npm test` passes). It does not name the file, the function or the fix — that is the part you are delegating.

### Reading the TUI

When you run `claude` in a project, you get a full-screen terminal interface. Four things on it earn your attention on day one:

- **The prompt bar** at the bottom, where you type. A `/` at the start opens commands and skills, `@` triggers file-path autocomplete, `!` runs a shell command directly and adds its output to the session, and `?` on empty input toggles the shortcut help panel.
- **The permission-mode indicator.** `Shift+Tab` cycles permission modes (on Windows, `Alt+M` when the runtime does not enable VT input mode). Which mode you are in decides whether Claude asks before each edit — the subject of a whole lesson in the next module.
- **Claude's task checklist**, toggled with `Ctrl+T`: what it thinks the remaining steps are.
- **The transcript viewer**, toggled with `Ctrl+O`: the full scrollback of the session, including tool calls you scrolled past.

The keys worth memorising first:

| Key         | What it does                               |
| ----------- | ------------------------------------------ |
| `Esc`       | Interrupt Claude, or close a dialog        |
| `Esc` `Esc` | Clear the input draft, or rewind           |
| `Ctrl+C`    | Interrupt, or clear input                  |
| `Ctrl+D`    | Exit the session                           |
| `Shift+Tab` | Cycle permission modes                     |
| `Ctrl+O`    | Toggle the transcript viewer               |
| `Ctrl+T`    | Toggle Claude's task checklist             |
| `Ctrl+R`    | Reverse-search command history             |
| `Ctrl+L`    | Redraw or clear the screen                 |
| `Ctrl+G`    | Open the current input in your text editor |

You do not have to stop Claude to steer it: typing a correction and pressing `Enter` while a tool is running queues the message, and `Esc` stops the action outright.

Multi-line input has four routes, because terminals disagree: `\` then `Enter` works everywhere, `Ctrl+J` works in any terminal without configuration, `Shift+Enter` is native in iTerm2, WezTerm, Ghostty, Kitty, Warp, Apple Terminal and Windows Terminal, and `Option+Enter` works on macOS once you enable Option as Meta.

### The same session, headlessly

Everything above has a non-interactive twin. `claude -p "…"` runs the task and exits, which is what you want when you need a capture for a pull request, or when you are running the same task ten times to compare models. The transcripts below were produced that way — this course never publishes reconstructed output.

Three things in that recording are worth stopping on.

**The answer is in Turkish.** The machine that captured it has global Claude Code preferences asking for Turkish, so the model answered in Turkish — the same effect lesson `01-what-claude-code-is` documents. Your standing memory and settings files shape every session, including a headless one you expected to be stateless, and that is worth knowing on day one.

**One change fixed three tests.** Two of the failures were unit tests on `addTask()`; the third was an API test asserting `POST /tasks` returns 400 rather than 201 for an empty title. The API layer already translated `InvalidTaskError` into a 400 — it simply never received one. That is the kind of thing a session finds quickly and a reader guesses wrongly.

**The diff is four lines** — one line replaced, three added. Reading it takes ten seconds and is the only step that actually verifies the work. Do it every time.

### The headless equivalent

<CodeBlock title="the same task, non-interactively">

```bash
claude -p "npm test fails with three failures. Find the cause, fix it in src/, and run npm test again to prove it passes." \
  --model sonnet \
  --max-turns 12 \
  --output-format text \
  --permission-mode acceptEdits \
  --allowedTools "Read,Edit,Glob,Grep,Bash(npm test)"
```

</CodeBlock>

`--allowedTools` is the part people leave off. A headless session has nobody to answer a permission prompt, so anything not granted up front is denied and the run cannot finish the job. Dropping that one flag from the command above gives this instead — every turn spent, nothing changed, exit code 1:

## Anti-patterns

**Prompting before you have looked.** Running `npm test` yourself first costs ten seconds and gives you the vocabulary to judge the answer. _Fix:_ read the failure, then delegate the cause.

**Letting a test be edited to make it pass.** A task phrased as "make the tests pass" invites exactly that. _Fix:_ scope the change ("fix it in `src/`") and check `git diff` for test-file edits.

**Accepting "all tests pass" without running them.** The claim is cheap; the output is not. _Fix:_ run `npm test` in your own shell after leaving the session.

**Starting in a dirty repository.** If `git status` was not clean before, `git diff` afterwards cannot tell you what Claude changed. _Fix:_ commit or stash first.

**Reaching for `Ctrl+C` to steer.** Interrupting throws away the tool call in flight. _Fix:_ type the correction and press `Enter` — the message is queued and delivered without stopping the run. Use `Esc` when you genuinely want the action to stop.

<Callout variant="changed">
  The word-motion keys (`Alt+B`, `Alt+F`, `Alt+D`, `Ctrl+W`) follow readline conventions in Claude
  Code v2.1.261 and later. The `keybindingFlavor` setting that used to turn them on is deprecated
  and now has no effect.
</Callout>
