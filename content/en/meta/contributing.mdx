This site is open source under the MIT licence (D052) and the whole of it — lessons, components,
the plan tooling, the CI configuration — lives at
[github.com/codechup/claude-code-training](https://github.com/codechup/claude-code-training).
Corrections are genuinely welcome: the material describes a tool that changes every few weeks, and
the fastest way for a wrong sentence to be fixed is for the person who spotted it to say so.

This page describes what actually happens to a contribution, so you can judge how much effort a
given change is worth before you spend it.

## The quickest useful thing: report it

If you have found something wrong — a command that no longer exists, a flag that was renamed, a
broken link, a Turkish sentence that reads badly — an issue is enough. Open one at
[github.com/codechup/claude-code-training/issues](https://github.com/codechup/claude-code-training/issues)
with:

- the page URL (or the file path under `content/`),
- what it says and what it should say,
- and, where you have one, a link to the official documentation that settles it.

That last item is worth more than the rest combined. This project's rule is that facts come from
[`research/feature-inventory.md`](https://github.com/codechup/claude-code-training/blob/main/research/feature-inventory.md)
or from a documentation page fetched at the time of writing, never from memory (D004, D093), so a
report carrying a URL can be acted on immediately, and one without a source has to be researched
before anything changes.

Every lesson page carries an **Edit this page on GitHub** link in its footer, which drops you
straight into the right file (D063). For a typo, that link plus GitHub's web editor is the entire
workflow.

**Security issues are the exception.** Do not open a public issue for a vulnerability — email
`security@codechup.com` as
[`SECURITY.md`](https://github.com/codechup/claude-code-training/blob/main/SECURITY.md) describes.

## The part of the workflow that is not yours

Internally, this repository coordinates parallel Claude Code sessions through plan files: a
session claims a `plans/PNN-slug.md` work order, gets exclusive ownership of a set of paths, and
works in its own git worktree. That contract is
[`plans/README.md`](https://github.com/codechup/claude-code-training/blob/main/plans/README.md),
and the mechanics are taught in
[m18 — Coordinating parallel sessions](/en/l4-master/m18-multi-session/).

As an outside contributor you do not claim a plan, and you should not add, edit or renumber one.
The plan set is curated by the maintainers, claims are announced by pushing a branch, and
[`STATE.md`](https://github.com/codechup/claude-code-training/blob/main/STATE.md) is generated by
`node tools/plan/cli.ts state` rather than written. What this means in practice is a boundary
rather than a barrier:

| Area                                                                                                  | Who changes it           | Your route                                                                         |
| ----------------------------------------------------------------------------------------------------- | ------------------------ | ---------------------------------------------------------------------------------- |
| `content/**` for an already-published lesson                                                          | Anyone                   | Open a PR directly                                                                 |
| `src/**`, `scripts/**`, `e2e/**`                                                                      | Anyone                   | Open a PR directly                                                                 |
| A lesson that does not exist yet                                                                      | A content plan           | Open an issue proposing it — the curriculum decides whether it is in scope         |
| `plans/**`, `STATE.md`                                                                                | Maintainer sessions only | Describe the change in an issue                                                    |
| [`docs/CURRICULUM.md`](https://github.com/codechup/claude-code-training/blob/main/docs/CURRICULUM.md) | Its owning plan          | Raise it in an issue; the curriculum is authoritative and is not edited in passing |
| [`DECISIONS.md`](https://github.com/codechup/claude-code-training/blob/main/DECISIONS.md)             | The project owner        | Propose it in an issue; a recorded decision is never re-litigated in a PR          |

The practical rule is the same one internal sessions follow: if a change makes you guess at a
product, curriculum or design decision, the guess is the problem. Say what the ambiguity is and
let it be decided, rather than encoding an answer in a pull request.

## Opening a pull request

1. **Fork and branch.** `main` is protected and takes squash merges from pull requests only.
2. **Install and set up the hooks.**

   ```bash
   npm ci
   sh scripts/install-hooks.sh
   ```

   The second command installs a `pre-commit` hook that runs the public-hygiene check and a
   `pre-push` hook that refuses a direct push to `main`. It is one command and it will save you a
   round trip through CI.

3. **Make the change**, keeping to the conventions the surrounding files already follow. The three
   that catch newcomers out:
   - **Design comes from tokens.** No hex, `rgb()` or named colour literal exists anywhere outside
     `src/styles/tokens.css`, and `scripts/check-raw-colors.mjs` enforces it.
   - **No inline `<script>` bodies.** The site is served with a `script-src 'self'` Content
     Security Policy and no nonces, so every script must be an external same-origin file.
   - **English and Turkish are twins.** Every file under `content/en/` has a counterpart at the
     mirrored path under `content/tr/`, and the reverse. If you add an English page, add the
     Turkish file too; a `draft: true` stub with a one-paragraph summary is acceptable and is what
     the internal workflow does until the translation wave reaches it.

4. **Run the gate locally.** These are the same commands CI runs, in the order that fails fastest:

   ```bash
   npm run typecheck
   npm run lint
   npm run gate
   npm test
   npm run build
   node scripts/check-public-hygiene.mjs
   node scripts/check-raw-colors.mjs
   ```

   If your change touches rendered pages, add `npx playwright test`, which runs the accessibility,
   shell, lesson and search suites with axe.

5. **Commit in the conventional style.** `type(scope): summary`, with `type` one of
   `feat|fix|docs|chore|test|refactor|ci|build` and `scope` naming the area (`content`, `i18n`,
   `design`, `ci`, `deploy`, `plans`). Internal commits end with the plan id in parentheses; an
   outside contribution has no plan id and simply leaves it off.

6. **Fill in the pull-request template.**
   [`.github/PULL_REQUEST_TEMPLATE.md`](https://github.com/codechup/claude-code-training/blob/main/.github/PULL_REQUEST_TEMPLATE.md)
   has six sections — **Plan**, **What changed**, **How to try it**, **Evidence**, **Definition of
   Done** and **Handoff notes**. Leave the Plan section blank or write "external contribution";
   the rest applies to you exactly as it applies to a maintainer session. Under **Evidence**,
   paste the real output of the commands you ran, and attach screenshots at 390 px and 1280 px for
   anything visual.

## What your PR is checked against

CI is [`ci.yml`](https://github.com/codechup/claude-code-training/blob/main/.github/workflows/ci.yml)
and it has to be green before anything merges:

| Job          | What it runs                                                                                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `quality`    | typecheck, ESLint + Prettier, the public-hygiene guard, the raw-colour guard, the plan self-check, the content gate, `gitleaks` over the full history, unit tests with a 70 % line-coverage floor, and the production build |
| `e2e`        | Playwright with axe against the built site                                                                                                                                                                                  |
| `links`      | `lychee` over the Markdown and MDX files your PR changed                                                                                                                                                                    |
| `lighthouse` | Lighthouse CI against the built site                                                                                                                                                                                        |

A content change gets one more layer. Every lesson is passed through two read-only Claude Code
subagents before it merges (D071): a
[`fact-checker`](https://github.com/codechup/claude-code-training/blob/main/.claude/agents/fact-checker.md),
which reports each factual claim as supported, contradicted or unverifiable against the official
documentation, and a
[`reviewer`](https://github.com/codechup/claude-code-training/blob/main/.claude/agents/reviewer.md),
which checks template order, the sources block, hygiene and language parity. Neither can edit
anything; they report, and the author decides. You are welcome to run them yourself before opening
the PR — they are in the repository — but you are not expected to.

Three rules are not negotiable, and a PR that breaks one will be asked to change rather than
argued with:

- **No fabricated output.** Every command shown in a lesson was run, and every transcript under
  `content/_shared/transcripts/` is a real capture with a provenance header, trimmed but never
  edited (D070, D093, D099). If you did not run it, say so — that is always an acceptable answer.
- **Nothing private in a public repository.** No hosting addresses, no absolute server paths, no
  SSH details, no secrets, not even as an illustrative example. Deploy targets are GitHub secrets.
  See
  [`.claude/rules/public-hygiene.md`](https://github.com/codechup/claude-code-training/blob/main/.claude/rules/public-hygiene.md).
- **Case studies are anonymous or fictional (D026).** Examples never name a real third-party
  project or its infrastructure.

## Contributing a translation

Turkish is a translation of the English source, never an independent rewrite (D016). If the
English is wrong, the English gets fixed first and the Turkish then follows.
[`.claude/rules/i18n.md`](https://github.com/codechup/claude-code-training/blob/main/.claude/rules/i18n.md)
is the binding checklist; its two most-missed points are that slugs are never translated — the
language switcher depends on English and Turkish sharing them — and that technical terms stay in
English (`hook`, `skill`, `subagent`, `worktree`, `permission mode`, …) with a Turkish gloss on
first use, rather than being given invented Turkish equivalents. Diacritics must be correct: ç, ğ,
ı, İ, ö, ş, ü.

Another language is a bigger conversation than a pull request. Open an issue first: two languages
are a decision the site is built around, and a third one has consequences for navigation, search
indexing, the content gate and every future lesson.

## Licensing

The repository is MIT-licensed
([`LICENSE`](https://github.com/codechup/claude-code-training/blob/main/LICENSE)), and that covers
the course content as well as the code (D052). Opening a pull request means your contribution is
offered under the same licence, and that you have the right to offer it. There is no separate
contributor agreement to sign.

Practically, that cuts both ways, and both directions are intended. Anything you contribute can be
copied, translated, taught from and sold on by anyone, with attribution to the copyright notice.
And anything already here — the plan CLI, the hooks, the content gate, the rule files, the lesson
text — you may lift into your own project on the same terms. Several of the patterns this site
teaches are easier to adopt by copying the file than by reading about it, which is
[the point of the page next door](/en/meta/how-this-site-was-built/).

Do not paste text you do not have the right to contribute. Quoting a documentation page with a
link and a `verified_at` date is exactly how the sources system is meant to be used; pasting
someone else's lesson into this one is not.
