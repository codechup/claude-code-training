## Objectives & prerequisites

By the end of this lesson you can:

- State precisely what Anthropic does and does not do about the MCP servers you connect.
- Name the four risks a connected server introduces: code execution, prompt injection through tool results, credential exposure, and context leakage.
- Keep a credential out of a shared config, and prove it with `claude mcp get`.
- Scope a server's tools with permission rules and `--allowedTools`, and explain when trust verification does not happen.
- Read the administrator side: `managed-mcp.json`, `allowedMcpServers`/`deniedMcpServers`, `allowManagedMcpServersOnly`, and what a blocked server looks like to a user.

**Prerequisites.** The rest of this module. Level 2's permissions material helps.

<WhenNotToUse>
  This lesson is not a substitute for your organisation's review process, and none of these controls
  make an untrusted server safe to run. If you cannot say who wrote a server, what it talks to, and
  what happens when it is compromised, the answer is not "add it with a narrow allowlist" — it is
  "do not add it". The controls below reduce blast radius; they do not establish trust.
</WhenNotToUse>

## Concept

### What you are trusting

Start with the sentence that should shape everything else. From the security docs, on MCP:

> We encourage either writing your own MCP servers or using MCP servers from providers that you trust. […] Anthropic reviews connectors against its listing criteria before adding them to the Anthropic Directory, but does not security-audit or manage any MCP server.

Directory listing is a review, not an audit, and it says nothing at all about a server you found on npm. A stdio server is a program you have agreed to run on your machine, with your environment, on every session start. A remote server is a third party you are handing queries — and sometimes credentials — to.

### The four risks

**Code execution.** `claude mcp add … -- npx -y some-package` runs whatever that package resolves to, now and at every future startup, with your user's privileges. `@latest` means "whatever they publish next".

**Prompt injection through tool results.** Everything a server returns enters the conversation. A malicious or compromised server — or a benign server relaying an attacker-controlled issue title, page or row — can carry instructions aimed at the model. The docs are explicit that servers which fetch external content can expose you to prompt injection risk. Claude Code's defences here are real but partial: the permission system, context-aware analysis of the full request, a separate context window for web fetches, and command-injection detection. The docs' own summary is the right posture — while these protections significantly reduce risk, no system is completely immune.

**Credential exposure.** A token in `.mcp.json` is a token in version control. `claude mcp get` prints configured headers back in plain text. A DSN on the command line lands in `~/.claude.json` and in shell history.

**Context leakage.** Whatever a tool returns is in the transcript: rows from a database, a page of an internal wiki, a customer's email address. That is a data-handling decision, not a technical one.

### The controls, from cheapest to strongest

**Trust verification.** First-time codebase runs and new MCP servers require trust verification, and a project-scoped `.mcp.json` prompts for approval before its servers are used — the prompt exists so a repository you clone cannot launch processes on your machine without your consent. Two gaps to know by heart: trust verification is **disabled when running non-interactively with the `-p` flag**, and in `claude -p`, Agent SDK and cloud sessions project-scoped servers load without asking. Automation is where this control is absent, which is exactly where it would matter most. Keep a server out with `disabledMcpjsonServers`, `--setting-sources`, or `--strict-mcp-config`.

**Secrets by reference.** Never a literal. `${VAR}` and `${VAR:-default}` expand in `command`, `args`, `env`, `url` and `headers`; a missing variable produces a named warning and no value in the output.

**Least privilege at every layer.** A fine-grained token instead of a classic one (lesson 03). A read-only database user _and_ a read-only server configuration (lesson 05). And on the Claude Code side, tool-level rules: MCP tools are named `mcp__<server>__<tool>`, so they can be allowed or denied like any other tool, in `permissions` or with `--allowedTools` on a headless run.

**Removal.** Each connected server takes space in the context window because its tool names and server instructions load into every session — and each one is a dependency. Removing servers you no longer use keeps that space free, and shrinks the attack surface for nothing.

### If you are writing a server

Two annotations are worth knowing. `_meta["anthropic/requiresUserInteraction"]: true` on a tool makes Claude Code show that tool's permission prompt on **every** call, even in `acceptEdits`, `auto` and `bypassPermissions` modes, with no "don't ask again" option, and allow rules do not skip it; in `dontAsk` mode the call is denied instead. Use it where the prompt is the point — a consent or access-grant step where auto-approval would mean no human ever agreed. And `_meta["anthropic/maxResultSizeChars"]` raises a specific tool's result threshold, up to a hard ceiling of 500,000 characters, for tools whose output is genuinely large.

### The administrator side

Organisations do not have to rely on individual judgement. Claude Code offers a spectrum, deployed through managed settings:

| Pattern          | What it does                                              | Configure                                                |
| ---------------- | --------------------------------------------------------- | -------------------------------------------------------- |
| Disable MCP      | No servers load at all                                    | `managed-mcp.json` with an empty server map              |
| Fixed deployment | Everyone gets the same servers and can add none           | `managed-mcp.json` with the servers you want             |
| Approved catalog | Users add from a published list; anything else is blocked | `allowedMcpServers` + `allowManagedMcpServersOnly: true` |
| Soft allowlist   | An allowlist users can broaden in their own settings      | `allowedMcpServers` alone                                |
| Denylist only    | Block known-bad servers, allow everything else            | `deniedMcpServers`                                       |

`managed-mcp.json` is a standalone file at a system path — `/Library/Application Support/ClaudeCode/managed-mcp.json` on macOS, `/etc/claude-code/managed-mcp.json` on Linux and WSL, `C:\Program Files\ClaudeCode\managed-mcp.json` on Windows — deployed by MDM, Group Policy or equivalent, and it cannot be delivered through server-managed settings. When it is present, Claude Code loads only the servers it defines, and `claude mcp add` fails with `Cannot add MCP server: enterprise MCP configuration is active and has exclusive control over MCP servers`.

Three details that decide whether a policy actually holds:

- Matching is by `serverUrl` (exact or with `*` wildcards), `serverCommand` (every argument, in order, exactly) or `serverName`. **`serverName` is not a security control** — the name is a label the user chose, so anyone can call any server `github`. Enforce with `serverCommand` or `serverUrl`.
- The denylist always wins, and always merges from every settings scope. The allowlist merges from every scope too — so a user can broaden it — unless `allowManagedMcpServersOnly: true` is set in a managed source.
- `allowedMcpServers` **unset** means all servers allowed; set to an empty array `[]` means none. They are different states.

Finally, know what a user sees, because two of these are silent. A blocked `claude mcp add` reports `Cannot add MCP server "<name>": server is explicitly blocked by enterprise policy` or `… not allowed by enterprise policy`. But a previously configured server that becomes blocked **silently disappears** from `/mcp` and `claude mcp list` with no warning. Tell affected users which servers are blocked when you roll out a restriction. To see what your organisation actually uses, configure OpenTelemetry export and set `OTEL_LOG_TOOL_DETAILS=1` to include MCP server and tool names in tool events.

This lesson's example prompt is an audit, not a task:

```text
Read .mcp.json and list every server it defines: transport, what it connects to,
which credentials it needs, and whether any value is a literal secret rather than
a ${VAR} reference. Do not connect to anything.
```

Put the two captures side by side. The only difference in the file is `EXAMPLE-TOKEN-DO-NOT-COMMIT` becoming `${REPORTING_MCP_TOKEN}`. The difference in what a terminal, a screen share, a bug report and a git history now contain is total.

And notice what the second capture's warning does _not_ say. It names the field and the variable — `[reporting] mcpServers.reporting: Missing environment variables: REPORTING_MCP_TOKEN` — and prints no value. Claude Code applies the same discipline elsewhere: it redacts credential-like text from failure details, never includes the expanded server URL in them, and quotes scope-conflict endpoints with `${VAR}` references unexpanded.

The third capture is the audit itself, and it makes a distinction worth stealing: the fallback in `${REPORTING_MCP_URL:-https://mcp.example.com/mcp}` is a literal, but it is a literal **endpoint**, not a literal credential. A default URL in a shared config is fine and often useful. A default token never is — which is why the token in the fixed file has no `:-default` at all, and why the missing-variable warning is the correct outcome rather than a nuisance.

## Anti-patterns

**"It is in the Directory, so it is audited."** Anthropic reviews connectors against listing criteria before adding them to the Directory, but does not security-audit or manage any MCP server. _Fix:_ do your own review, and prefer servers you or your organisation wrote.

**Pinning nothing.** `npx -y package@latest` runs whatever the publisher pushes next, on every session start, on every machine that has your config. _Fix:_ pin a version you reviewed and update deliberately. (The docs' own examples use `@latest` for convenience; convenience is not the constraint you are optimising for here.)

**Relying on the trust prompt in automation.** Trust verification is disabled with `-p`, and project-scoped servers load without asking in headless, SDK and cloud sessions. _Fix:_ `--strict-mcp-config` with an explicit `--mcp-config`, or `disabledMcpjsonServers`, in anything that runs unattended.

**A `serverName` allowlist.** The name is a label the user picked; anyone can call their server `github`. _Fix:_ `serverCommand` or `serverUrl` entries for anything you rely on for enforcement.

**Treating tool output as trusted.** A row, an issue title or a page fetched through a server is attacker-influenceable text arriving in your model's context. _Fix:_ review commands before approval, do not pipe untrusted content directly to Claude, prefer read-only scopes, and keep the risky work in a sandbox or VM.

**Keeping servers you stopped using.** Every one costs context and remains a dependency you have to trust. _Fix:_ `claude mcp remove`, and re-add when you next need it.
