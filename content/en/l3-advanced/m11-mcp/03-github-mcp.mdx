## Objectives & prerequisites

By the end of this lesson you can:

- Add GitHub's remote MCP server with a fine-grained personal access token passed as a header.
- Tell the three remote-server statuses apart — `✔ Connected`, `! Needs authentication`, `✘ Failed to connect` — and get the failure detail out of `claude mcp get`.
- Decide when a GitHub MCP server earns its place over a `gh` command in a Bash call.
- Keep the token out of anything you commit.

**Prerequisites.** Lessons 01 and 02. A clone of the lab repository at `lesson/m11-03-start`.

<Callout>
  This lab deliberately does **not** authenticate against a real GitHub account and creates nothing
  on GitHub. You will add the server exactly as the docs describe, with a token placeholder, and
  read the real status Claude Code reports. To use it for real afterwards, swap in your own token —
  the commands do not change.
</Callout>

<WhenNotToUse>
  You already have a GitHub client: `gh`. If the work is "read this PR", "open an issue", "list my
  review requests", a Bash call to `gh` is faster, needs no extra server in context, and leaves a
  command in the transcript you can audit at a glance. The MCP server earns its keep when the task
  weaves GitHub into other systems — read the issue, query the database it describes, then open the
  PR — because Claude can then move between them without you brokering each step. It is also the
  wrong tool when your token would have to be broader than the task: a server with write access to
  every repository is a bigger blast radius than one `gh` invocation you approved.
</WhenNotToUse>

## Concept

### The server and its credential

GitHub's remote MCP server is an HTTP server that authenticates with a GitHub personal access token passed as a header. Get one from your GitHub token settings — generate a **fine-grained** token with access only to the repositories you want Claude to work with — then add the server:

<CodeBlock title="add the GitHub MCP server">

```bash
claude mcp add --transport http github https://api.githubcopilot.com/mcp/ \
  --header "Authorization: Bearer YOUR_GITHUB_PAT"
```

</CodeBlock>

Replace `YOUR_GITHUB_PAT` with the token. Two properties of that command matter more than they look:

`claude mcp add` saves the configuration without validating credentials. A placeholder is accepted at add time and the server fails to connect later. So the `Added …` line means "written to disk", never "authenticated".

The header is stored, and `claude mcp get` prints it back in full. The `add` command masks it in its own output — the capture below shows `"Authorization": "[REDACTED]"` — but `get` does not. Treat the config file as a credential store, and never put a literal token into a `.mcp.json` you commit; use `${GITHUB_TOKEN}` and let the environment supply it (lesson 02).

### Reading the status

Once added, `claude mcp list` health-checks each server. For a remote server there are three answers you will meet constantly:

| Status                   | What it means                                               | What to do                                                     |
| ------------------------ | ----------------------------------------------------------- | -------------------------------------------------------------- |
| `✔ Connected`            | The server answered and its tools were listed               | Nothing                                                        |
| `! Needs authentication` | Reachable, but it wants a browser sign-in you have not done | `/mcp` → Authenticate, or `claude mcp login <name>`            |
| `✘ Failed to connect`    | It answered with an error, or did not answer                | Read the failure detail on the status line or `claude mcp get` |

The distinction between the last two is precise and worth internalising. A server you have not signed in to is flagged for OAuth. But for a server whose `Authorization` header **you** configured, a `401` or `403` while connecting does _not_ flag it for sign-in: the credential to fix is the one you configured, so Claude Code reports the connection as failed instead. If you configured a header and the server rejects it, Claude Code does not silently fall back to OAuth.

Since v2.1.219, `claude mcp list` appends the failure detail to the status line and `claude mcp get <name>` shows it on an `Issue:` line — the HTTP status or error code plus any error text the server returned. Claude Code redacts credential-like text from that detail and never includes the expanded server URL, which can carry secrets.

### Working through it

With the server connected, GitHub work is described, not scripted. This lesson's example prompt:

```text
Review PR #456 and suggest improvements
```

Other shapes from the docs: `Create a new issue for the bug we just found`, `Show me all open PRs assigned to me`. Tool calls appear in Claude's output labelled with the server name, which is how you confirm the answer came through the server.

Claude Code also exposes anything the server publishes as **resources** through `@` mentions — `Can you analyze @github:issue://123 and suggest a fix?` — and any **prompts** it publishes in the `/` menu, for example `/mcp__github__pr_review 456`.

Two observations from that recording.

The failure text is the _server's_, not Claude Code's: `HTTP 400: Error POSTing to endpoint: bad request: Authorization header is badly formatted`. GitHub rejected the token's shape before it ever checked whether the token existed. That is exactly the kind of detail that used to be invisible — before v2.1.219 both commands showed only the bare failure status.

And the two servers in the last capture differ in one thing only: whether a header was configured. `github` has one, so its rejection is a failed connection you must fix in configuration. `sentry` has none, so its `401` becomes an invitation to sign in.

## Anti-patterns

**Committing the token.** A literal `Bearer ghp_…` in `.mcp.json` is a credential in your git history, and `claude mcp get` prints it back to anyone at the terminal. _Fix:_ `Bearer ${GITHUB_TOKEN}` in the file, the real value in your environment.

**A classic personal access token with every scope.** The server can do whatever the token can do, on every repository the token can reach. _Fix:_ a fine-grained token limited to the repositories the task needs.

**Reading `Added …` as "connected".** Configuration was written; nothing was validated. _Fix:_ always follow with `claude mcp list` and read the status.

**Chasing an OAuth flow for a header failure.** If you configured `headers.Authorization` and the server rejects it, Claude Code will not fall back to OAuth, and re-running sign-in changes nothing. _Fix:_ check the token is valid for the MCP endpoint, or remove the header to use the OAuth flow instead.

**Using the server as a slower `gh`.** One-step GitHub reads do not need a connected server and its context cost. _Fix:_ keep it for tasks that cross systems.
