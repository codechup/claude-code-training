## Objectives & prerequisites

By the end of this lesson you can:

- Connect a database to Claude Code over MCP with DBHub, against SQLite or PostgreSQL.
- Ask a schema question in English and get back the SQL that was actually run.
- Configure the server so it physically cannot write, and prove it by watching it refuse.
- Explain why a read-only credential and a read-only server configuration are two different controls, and why you want both.
- Diagnose the most common silent failure: a relative SQLite path that opens the wrong database.

**Prerequisites.** Lessons 01, 02 and 04 (for `--allowedTools`). A clone of the lab repository at `lesson/m11-05-start`, Node.js 18 or later (`@bytebase/dbhub` runs through `npx`), and Python or any tool that can create a small SQLite file.

<WhenNotToUse>
  Never point a database MCP server at production with a credential that can write. Even read access
  to production is a decision, not a default: the rows come back into a model's context, and
  everything in them is then part of the conversation — customer emails included. Do not use MCP at
  all when a checked-in migration or a saved query answers the question; those are reviewable and
  repeatable, and an ad-hoc agent query is neither. The good case is exploration against a
  development or analytics replica, where "what does this schema even look like" is a real question
  and the answer's blast radius is zero.
</WhenNotToUse>

## Concept

### DBHub

**DBHub** (`@bytebase/dbhub`) is the database server the Claude Code docs use in their PostgreSQL example. It connects Claude to a relational database through a connection string, and it speaks several dialects — the DSN forms it prints in its own help are:

```text
postgres:   postgres://postgres:password@localhost:5432/postgres?sslmode=require
sqlserver:  sqlserver://username:password@localhost:1433/database?sslmode=disable&instanceName=INSTANCE1
sqlite:     sqlite:///path/to/database.db
mysql:      mysql://root:password@localhost:3306/mysql?sslmode=require
mariadb:    mariadb://root:password@localhost:3306/db?sslmode=require
```

The docs' PostgreSQL example passes the DSN on the command line, and pairs it with the rule that matters most:

<CodeBlock title="the documented PostgreSQL shape">

```bash
claude mcp add --transport stdio db -- npx -y @bytebase/dbhub \
  --dsn "postgresql://readonly:pass@prod.db.com:5432/analytics"
```

</CodeBlock>

Note the username. Use a **read-only database user** in the connection string so the queries Claude runs cannot modify data. That is the control your database enforces, and it is the one that survives every bug in every layer above it.

### Two independent read-only controls

There is a second control, in the server rather than the database, and this lesson uses both. DBHub takes a TOML configuration file where you declare your sources and then mark a tool read-only:

<CodeBlock title="dbhub.toml — a read-only SQLite source">

```toml
[[sources]]
id = "labtrack"
dsn = "sqlite:///absolute/path/to/labtrack.db"

[[tools]]
name = "execute_sql"
source = "labtrack"
readonly = true
```

</CodeBlock>

With that in place, the server rejects any statement outside its allow-list before it reaches the database. Belt and braces: the credential says what the connection _may_ do, the server configuration says what this _tool_ may do. Neither replaces the other — a read-only server on a read-write credential is one config edit away from being read-write, and a read-only credential with a permissive server still lets a confused model run an expensive `SELECT` over everything.

### The relative-path trap

SQLite DSNs take an absolute path (`sqlite:///path/to/database.db` — three slashes, then the path). With a relative form such as `sqlite://labtrack.db`, this lesson's recording session observed DBHub connecting to an empty database instead of the seeded one. Nothing errors: the server starts, `claude mcp list` reports `✔ Connected`, and every query returns zero rows — Claude reported that `sqlite_master` was empty and `tasks` did not exist. If Claude tells you your tables do not exist, check the DSN before you check your data.

### Asking in English, reading in SQL

The point of a database server is not that Claude writes SQL — it is that you can ask a question, and still see the SQL. This lesson's example prompt:

```text
Use the db MCP server: list the tables, then run
SELECT title, due_date FROM tasks WHERE done = 0 AND due_date < '2026-09-07'.
Report the SQL and the rows.
```

Asking for the SQL back is the habit worth building. It is your only check that the question you asked is the question that was answered.

The middle capture does the thing that makes this worth doing: the answer contains both the rows and the statement. `SELECT title, due_date FROM tasks WHERE done = 0 AND due_date < '2026-09-07'` is checkable at a glance — you can see that "not done" was read as `done = 0` and that the date bound is the one you meant.

The third capture is the lesson. The server's own words:

```json
{
  "success": false,
  "error": "Read-only mode is enabled. Only the following SQL operations are allowed: select, with, explain, pragma",
  "code": "READONLY_VIOLATION"
}
```

The refusal came from the server, not from the model's judgement and not from Claude Code's permission system. That distinction is the whole design principle of this lesson: a control you can _see refuse_ is worth more than a control you are assured exists. (For the record, on a first attempt with a plainer prompt the model declined to run the `DELETE` on its own — a good instinct, and exactly why the lab has to ask explicitly for the statement to be sent before the server's guard is visible.)

One more thing in the first capture, easy to skim past: `claude mcp get db` prints the full command, including `--config=dbhub.toml`. If the DSN had been on the command line, as in the docs' PostgreSQL example, the database password would be printed there too — which is a reason to prefer the config file.

## Anti-patterns

**A read-write credential "because it is just a dev database".** Dev databases get restored from production. _Fix:_ a read-only database user in the DSN, always, and read-only in the server config as well.

**Putting the DSN with its password on the command line.** It lands in `~/.claude.json`, in `claude mcp get` output, and in your shell history. _Fix:_ a config file the server reads, or `${DB_DSN}` expansion in `.mcp.json`.

**Trusting a relative SQLite path.** It connects, reports healthy, and answers every question about an empty database. _Fix:_ absolute `sqlite:///…` paths.

**Taking the rows without the SQL.** You cannot tell a wrong answer from a right one if you never see the question. _Fix:_ ask for the statement in the same breath as the result.

**Selecting everything into context.** `SELECT * FROM users` on a real table blows through the MCP output limit — Claude Code warns above 10,000 tokens and caps at 25,000 by default — and puts personal data in a transcript. _Fix:_ ask for aggregates and `LIMIT`ed samples, and raise `MAX_MCP_OUTPUT_TOKENS` only deliberately.
