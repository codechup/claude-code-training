## Objectives & prerequisites

By the end of this lesson you can:

- Say what an agentic session does and does not do with `.env` by default, and write the rules that change it.
- Remove the most ordinary secret leak there is: a credential printed to a log.
- Run gitleaks over a checkout with a planted, obviously-fake key and read its finding — with `--redact`, so the scan does not become the leak.
- Write a `PreToolUse` hook that blocks the write _before_ the value lands in a file, and explain why that beats a pre-commit check alone.
- Name the layers, in order, and say what each one catches that the previous one misses.

**Prerequisites.** Lessons `01` and `02` of this module, a clone of the lab repository, Node 24, and [gitleaks](https://github.com/gitleaks/gitleaks) on your `PATH` (8.30.1 was used for the recording below).

<WhenNotToUse>
  A leak guard is not secret management. None of this rotates a credential, scopes it, or gets it
  out of a history that already contains it — if a real secret has been committed, the only remedies
  are rotation and history rewriting, in that order, and neither is in this lesson. Nor is a scanner
  a reason to keep secrets in files: the durable fix is a secret manager or an environment variable
  your process reads at runtime. Treat everything below as the net under the wire, not the wire.
</WhenNotToUse>

## Concept

### What a session does with `.env` by default

Two facts, both from the docs, and they surprise people in opposite directions.

Reading `.env` **and sending credentials to their matching API** is on the auto-mode classifier's _allowed by default_ list. That is deliberate: a tool that cannot read its own configuration cannot run your project.

At the same time, the classifier blocks — by default — printing a live credential or token into the transcript or a file, committing or pushing a change that would send secrets outside the repository when CI runs it, and pushing secrets to a repository known to be public. From v2.1.203 it also blocks content from a sensitive local store, or from a file whose name or path marks it sensitive, entering a commit, a push, PR or issue text, a gist or a package publish, unless you named both the source and the destination — **and the repository being private does not clear it**.

So the default posture is: read your secrets, do not publish them. If you want the first half tightened too, say so with a rule:

<CodeBlock title=".claude/settings.json">

```json
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  }
}
```

</CodeBlock>

Deny rules block in every permission mode, `bypassPermissions` included, and they are evaluated before the auto-mode classifier is consulted.

Under the sandbox there is a second, separate control, because the sandbox governs what a _subprocess_ can reach rather than what a tool call may do:

<CodeBlock title="~/.claude/settings.json — sandbox credential rules">

```json
{
  "sandbox": {
    "enabled": true,
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" },
        { "name": "NPM_TOKEN", "mode": "deny" }
      ]
    }
  }
}
```

</CodeBlock>

`deny` denies the read and unsets the variable before each sandboxed command. There is **no built-in credential deny list** — only what you name is restricted. `mask` goes further: the command sees a per-session sentinel and the sandbox proxy substitutes the real value on requests to the hosts you list in `injectHosts`, so `gh` and `npm` keep working while nothing they log holds the credential. Masking needs `network.tlsTerminate` and is honoured only from user, managed or `--settings` sources — never from a repository's own settings file.

### The layers, in the order they fire

| Layer                       | Fires                           | Catches what the previous misses                                   |
| --------------------------- | ------------------------------- | ------------------------------------------------------------------ |
| `permissions.deny` on reads | Before the tool runs            | The value never enters the session                                 |
| A `PreToolUse` hook         | Before the write lands          | A value Claude assembled itself, going into any file               |
| The auto-mode classifier    | Before a commit, push or upload | The pathway, not just the value — a CI change that will leak later |
| gitleaks pre-commit         | On staged content               | Anything a human typed, or a hook that did not match               |
| gitleaks in CI over history | On push                         | What everything above missed, and what is already committed        |

The interesting column is the third. A scanner looks at content; the classifier reasons about where the data lands, and blocks "arming an automated pathway" — a workflow change that will upload private content when it next runs — even when nothing secret appears in the diff.

Here is this lesson's worked example prompt:

```text
Find every place this repo prints, logs, or commits a credential value, and change
each one to log that the credential is configured without printing it. Do not add
a new dependency.
```

### The hook, in one paragraph

A `PreToolUse` hook is a command Claude Code runs before a tool call, with the call as JSON on stdin. Exit `0` and the call proceeds; exit `2` and it is blocked regardless of anything else; or print `hookSpecificOutput` with a `permissionDecision` of `allow`, `deny`, `ask` or `defer` plus a `permissionDecisionReason` that Claude reads and reacts to. This site's own hook does both — it prints the JSON _and_ exits `2` — which is the belt-and-braces shape worth copying.

**The diff is the actual lesson.** The template literal that interpolated the token into a `[config] using token:` line becomes a plain `console.log("[config] API token configured")`. The token is still read and still returned; only the printing stops. It also removed a `TEACHING SURFACE` comment nobody asked about — read your diffs.

**gitleaks was run with `--redact`.** Without it, the finding prints the secret, and your scan log, your CI output and your terminal scrollback become three new copies of the leak. `Finding: REDACTED / Secret: REDACTED / RuleID: aws-access-token`, exit `1`; after `rm deploy.env`, `no leaks found`, exit `0`. ### The hook, wired up

This site's hook delegates its pattern list to a single script so there is one source of truth, and it scans file writes with the full rule set but shell commands for credential material only — a command that _reads_ a private system is legitimate; a credential landing in a tracked file is not.

<CodeBlock title=".claude/settings.json">

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write|Edit|Bash|PowerShell",
        "hooks": [{ "type": "command", "command": "node .claude/hooks/guard-hygiene.mjs" }]
      }
    ]
  }
}
```

</CodeBlock>

<CodeBlock title=".claude/hooks/guard-secrets.mjs — the minimal shape">

```javascript
#!/usr/bin/env node
import { readFileSync } from 'node:fs';

const input = JSON.parse(readFileSync(0, 'utf8') || '{}');
const tool = input.tool_name ?? '';
const ti = input.tool_input ?? {};

const text = tool === 'Write' ? (ti.content ?? '') : tool === 'Edit' ? (ti.new_string ?? '') : '';
if (!text) process.exit(0);

const RULES = [
  [/\bsk-ant-[A-Za-z0-9_-]{20,}/, 'Anthropic API key'],
  [/\b(?:ghp|gho|ghu|ghs|ghr)_[A-Za-z0-9]{30,}\b/, 'GitHub token'],
  [/\b(?:A3T[A-Z0-9]|AKIA|ASIA|ABIA|ACCA)[A-Z0-9]{16}\b/, 'AWS access key id'],
  [/-----BEGIN (?:RSA |EC |OPENSSH |DSA )?PRIVATE KEY-----/, 'private key material'],
];

for (const [re, why] of RULES) {
  if (!re.test(text)) continue;
  console.log(
    JSON.stringify({
      hookSpecificOutput: {
        hookEventName: 'PreToolUse',
        permissionDecision: 'deny',
        permissionDecisionReason: `Blocked: ${why} in ${ti.file_path ?? tool}. Move it to a secret manager or an environment variable.`,
      },
    }),
  );
  process.exit(2);
}
process.exit(0);
```

</CodeBlock>

Test it without involving Claude at all — the hook is a plain program with a JSON contract:

### Enforcing it for everyone

A hook and a `.gitleaks.toml` in a repository are advice: anyone can delete them. An administrator makes the deny rules non-negotiable with managed settings, which sit above every other level:

<CodeBlock title="managed-settings.json">

```json
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./secrets/**)"],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "allowManagedHooksOnly": true
}
```

</CodeBlock>

`allowManagedPermissionRulesOnly` makes managed settings the only source of permission rules — user, project, local and `--allowedTools` are ignored. The next lesson covers where that file goes on each OS and how to prove it landed.

## Anti-patterns

**Relying on a pre-commit hook alone.** It fires after the value is already in your working tree, your scrollback and, if a background process picked it up, elsewhere. _Fix:_ block at write time with `PreToolUse`, and keep the pre-commit check as the net.

**Running a scanner without `--redact`.** The finding prints the secret into your terminal, your CI log and your artifact store. _Fix:_ `gitleaks ... --redact`, always.

**Committing an `EXAMPLE`-shaped placeholder and calling the clean scan a pass.** Gitleaks' default allowlist skips common placeholder text, so a scan that reports nothing may be telling you about your fixture, not your repo. _Fix:_ verify your guard with a randomly generated value of the right shape.

**Deleting the commit that contained the secret.** Removing it from `HEAD` leaves it in history, in every clone, and in any fork. _Fix:_ rotate the credential first; treat history rewriting as cleanup, not as remediation.

**Denying `Read(./.env)` and stopping there.** The rule does more than you might expect — it also covers the Edit and Write tools on the same path, and the file commands Claude Code recognises in Bash, such as `cat`, `head`, `tail` and `sed`, plus redirection targets. What it does **not** cover is an arbitrary subprocess that opens the file itself, such as a Python or Node script. _Fix:_ pair the permission rule with `sandbox.credentials`, and enable the sandbox for OS-level enforcement.

**Putting a `mask` entry in the repository's `.claude/settings.json`.** Claude Code ignores `mask`, `network.tlsTerminate` and `credentials.allowPlaintextInject` from a repository's settings, because masking authorises the proxy to send your real credential somewhere. _Fix:_ user, managed or `--settings` scope.

<Callout variant="changed">
  A `PreToolUse` hook's older `{"decision": "block"}` JSON is superseded. The current shape is
  `hookSpecificOutput.permissionDecision` with the values `allow`, `deny`, `ask` or `defer`, plus a
  `permissionDecisionReason`; exit code `2` still blocks regardless of the JSON. Verified against
  `hooks.md` for Claude Code 2.1.263.
</Callout>
