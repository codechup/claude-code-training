## Objectives & prerequisites

By the end of this lesson you can:

- Recite the four-step model resolution order for a subagent, and say which step wins in a given situation.
- Explain what `inherit` means, and why it is not the same as omitting `model`.
- Use `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` deliberately, and say which one overrides a pinned agent.
- Read `modelUsage` in the headless JSON envelope to see which models actually ran.
- Decide which of your agents deserve a bigger model and which should be the cheapest thing that works.

**Prerequisites.** Lessons 01–03 of this module, and L2 `m05-models-effort` for the model family and what the aliases mean.

<WhenNotToUse>
  Do not pin a `model` on an agent whose job is genuinely model-agnostic. A pinned agent stops
  following your session: if you switch the main conversation to a stronger model because the work
  got hard, an agent with `model: haiku` keeps answering at Haiku quality and you will blame the
  prompt. Leave `model` out — or set `inherit` — unless the agent has a reason of its own to differ.
  And do not reach for `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` to save money on a normal day: it
  overrides every agent’s deliberate choice, including ones a colleague pinned for a good reason.
</WhenNotToUse>

## Concept

### The resolution order

A subagent's model is decided by the first of these that applies:

1. The per-invocation `model` parameter passed to the `Agent` tool.
2. The subagent definition's `model` frontmatter field — where `inherit` means "the main conversation's model".
3. The `CLAUDE_CODE_SUBAGENT_MODEL` environment variable.
4. The main conversation's model.

Read it top-down and two things fall out. First, an agent file that pins `model: sonnet` **beats** the environment variable — the env var is a default for agents that did not choose, not an override. Second, omitting `model` entirely and writing `model: inherit` end up at the same place only when the env var is unset; with the env var set, omitting `model` lands on step 3 while `inherit` resolves at step 2 to the main model. That difference is invisible until someone exports the variable in CI.

### Forcing one model everywhere

When you do want the env var to win over pinned agents, set its companion:

<CodeBlock title=".claude/settings.json">

```json
{
  "env": {
    "CLAUDE_CODE_SUBAGENT_MODEL": "haiku",
    "CLAUDE_CODE_SUBAGENT_MODEL_FORCE": "1"
  }
}
```

</CodeBlock>

`CLAUDE_CODE_SUBAGENT_MODEL_FORCE` requires Claude Code v2.1.257 or later. It is a blunt instrument, and that is the point: use it for a CI job or a cost experiment where uniformity matters more than any individual agent's judgement, not as a standing setting.

The same two variables also govern agent teams. A teammate's model comes from the spawn prompt, then a subagent definition's `model` (where `inherit` selects the lead's model), then `CLAUDE_CODE_SUBAGENT_MODEL` when it is set to anything other than `inherit`, then the lead's current model — and `_FORCE` applies to teammates too.

### Reading which model actually ran

Guessing is unnecessary. In headless mode, `--output-format json` returns a `modelUsage` map keyed by the canonical model id, with the tokens each one spent:

```text
Use the scout subagent to answer: which functions does src/store.ts export?
```

Run that against an agent with no `model` field, with and without the environment variable, and the map tells you which rule fired. That is the whole lab.

### A cost strategy that survives contact

The useful question is not "which model is best" but "where does a bigger model change the answer". Three rules of thumb hold up:

- **Search and retrieval do not need a big model.** An agent whose job is to find a file, list exports, or grep a convention is doing lookup, not reasoning. Pin it cheap — or leave it unpinned and let a cheap `CLAUDE_CODE_SUBAGENT_MODEL` catch it.
- **Judgement calls do.** A reviewer that has to decide whether a finding is real, or a planner weighing two designs, spends its whole budget on the part a stronger model is better at. Pin those.
- **Volume beats per-call price.** Ten cheap searches usually cost less than one expensive one, but twenty concurrent agents on any model will out-spend a single careful session. The concurrency ceiling (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, default 20) exists for a reason.

The four agents from lesson 03 all pin `model: sonnet`, which is a defensible default for a small project: their work is judgement-shaped, and Sonnet is the general coding model. A `scout`-style lookup agent is the obvious candidate to leave unpinned so a cheaper session default can reach it.

<OSTabs>


  </Fragment>

  </Fragment>
  <Fragment slot="windows">

```powershell
$env:CLAUDE_CODE_SUBAGENT_MODEL = 'haiku'
claude -p "Use the scout subagent to answer: which functions does src/store.ts export?" --model sonnet --max-turns 4 --output-format json
Remove-Item Env:\CLAUDE_CODE_SUBAGENT_MODEL
```

  </Fragment>

PowerShell has no inline `VAR=value command` prefix, so the variable is set, used and removed as three statements. The captures above were taken with the Bash form.

Run B is the interesting one: `claude-sonnet-5` and `claude-haiku-4-5-20251001` both appear, with Haiku doing the larger share of the output tokens. That split is the subagent running on Haiku while the main conversation stayed on Sonnet — exactly step 3. Run C removes Haiku again with no change to the command except which agent was targeted, which is step 2 winning.

## Anti-patterns

**Assuming the environment variable overrides everything.** It sits at step 3, below the agent's own `model`. Teams discover this when a CI cost cap silently fails to apply to the agents that actually spend. _Fix:_ add `CLAUDE_CODE_SUBAGENT_MODEL_FORCE: "1"`, or remove the pins.

**Pinning every agent to the strongest model "to be safe".** You pay the top rate for lookups whose answer a cheap model gets exactly right. _Fix:_ pin only the agents whose output is a judgement.

**Writing `model: inherit` and expecting it to follow the env var.** `inherit` resolves at step 2 to the main conversation's model, so it _bypasses_ step 3. _Fix:_ omit `model` when you want the env var to be able to reach the agent.

**Judging the model from the answer's tone.** Model identity is in `modelUsage`, not in how confident the prose sounds. _Fix:_ read the envelope.

**Fanning out twenty agents to save wall-clock time.** Running several sessions or subagents at once multiplies token usage; it does not divide the work for free. _Fix:_ delegate what genuinely parallelises, and keep the count small.

<Callout variant="changed">
  `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` — the switch that lets the environment variable override an
  agent’s own `model` — requires Claude Code v2.1.257 or later. On older versions a pinned agent
  always wins.
</Callout>
