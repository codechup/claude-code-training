## Objectives & prerequisites

By the end of this lesson you can:

- Write a `.claude/agents/<name>.md` file from memory: the two required fields, the body, and the fact that the body becomes the agent's system prompt.
- Name every optional frontmatter field and the values it accepts.
- Choose between the allowlist (`tools`) and the denylist (`disallowedTools`), including the MCP wildcard and `Agent(...)` forms.
- Say which of the five scopes wins when the same agent `name` exists in more than one, and why a nested `.claude/agents/` closest to the working directory takes precedence.
- Explain the five silent-skip rules that make a file in `agents/` disappear without an error.

**Prerequisites.** Lesson 01 of this module, and a repository you can add files to. If you have done L2 `m06-skills`, the frontmatter-plus-body shape will look familiar — a subagent file is the same idea for a different unit of work.

<WhenNotToUse>
  A custom agent is a reusable role, not a one-off instruction. If you will run the task once, say
  it in your prompt instead — a file you write, forget and never delete becomes stale context that
  Claude keeps reading. Do not define an agent whose only difference from `general-purpose` is a
  longer prompt with no tool, model or permission change: that is a skill (L2 `m06-skills`), and
  skills compose with everything else. And do not use an agent to enforce a security boundary you
  care about: `tools` and `permissionMode` shape one delegated worker, while the permission rules in
  your settings apply to the whole session.
</WhenNotToUse>

## Concept

### The file

A subagent is a Markdown file with YAML frontmatter. The frontmatter is the configuration; the body is the agent's system prompt.

<CodeBlock title=".claude/agents/code-reviewer.md">

```markdown
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.
```

</CodeBlock>

Only `name` and `description` are required. `name` is lowercase letters and hyphens, must be unique, cannot start with `-` and cannot contain `:` — and it is the value your hooks receive as `agent_type`. `description` is what Claude reads when deciding whether to delegate here, so write it as a trigger ("Use after making a change, before it is committed"), not as a job title.

### Every field

| Field             | Required | Values                                                                                     |
| ----------------- | -------- | ------------------------------------------------------------------------------------------ |
| `name`            | yes      | lowercase letters, hyphens                                                                 |
| `description`     | yes      | string — when Claude should delegate here                                                  |
| `tools`           | no       | tool names, `Agent(type)`, `mcp__<server>` patterns — allowlist; inherits all if omitted   |
| `disallowedTools` | no       | tool names, `mcp__<server>` patterns — denylist applied to the inherited or specified list |
| `model`           | no       | `sonnet`, `opus`, `haiku`, `fable`, a full ID such as `claude-opus-5`, or `inherit`        |
| `permissionMode`  | no       | `default`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`, `plan`, `manual`         |
| `maxTurns`        | no       | positive integer — cap before the agent returns partial output                             |
| `skills`          | no       | list of skill names preloaded into context at startup                                      |
| `mcpServers`      | no       | server names, or inline definitions                                                        |
| `hooks`           | no       | hook definitions scoped to this subagent                                                   |
| `memory`          | no       | `user`, `project`, `local` — persistent memory for cross-session learning                  |
| `background`      | no       | `true` — keep the agent in the background even when Claude asks for the foreground         |
| `effort`          | no       | `low`, `medium`, `high`, `xhigh`, `max`                                                    |
| `isolation`       | no       | `worktree` — run in a temporary git worktree with its own copy of the repository           |
| `color`           | no       | `red`, `blue`, `green`, `yellow`, `purple`, `orange`, `pink`, `cyan` — display colour      |
| `initialPrompt`   | no       | string auto-submitted as the first turn when the agent runs as the main session agent      |
| `experimental`    | no       | `{cacheTtl: "5m" \| "1h"}`                                                                 |

That is the complete list as of Claude Code 2.1.263. Four of these get their own lesson later in this module: `model` (lesson 04), `background` and `isolation` (lesson 05), and `effort` interacts with the model choice.

### Tools: allowlist or denylist

Omit `tools` and the agent inherits everything a subagent can use. Two ways to narrow it:

```yaml
tools: Read, Grep, Glob, Bash # allowlist — nothing else exists for this agent
```

```yaml
disallowedTools: Write, Edit # denylist — everything else stays
```

MCP servers take patterns: `disallowedTools: mcp__github` removes every tool from that server, and `mcp__*` removes all MCP tools. You can also restrict which subagents this agent may spawn:

```yaml
tools: Agent(worker, researcher), Read, Bash
```

The allowlist is the honest default for a reviewer or a researcher: an agent with no `Edit`, `Write` or `Bash` cannot quietly "fix" the thing it was asked to describe. The denylist is better when you want a mostly-capable worker minus one hazard.

`permissionMode` sets the mode inside the agent, defaulting to the main conversation's. `plan` makes it read-only; `bypassPermissions` skips every check and should be treated the way you treat that flag anywhere else.

### Where the files live, and who wins

| Location             | Scope             | Priority    |
| -------------------- | ----------------- | ----------- |
| Managed settings     | Organisation-wide | 1 (highest) |
| `--agents` CLI flag  | Current session   | 2           |
| `.claude/agents/`    | Current project   | 3           |
| `~/.claude/agents/`  | All projects      | 4           |
| A plugin's `agents/` | Where enabled     | 5 (lowest)  |

When the same `name` exists in more than one scope, the higher priority wins. For nested `.claude/agents/` directories inside a project, the definition **closest to the working directory** wins — the same rule path-scoped rules follow.

The session-scoped form takes JSON on the command line, which is how CI defines an agent without committing a file:

```bash
claude --agents '{"code-reviewer":{"description":"Expert code reviewer","prompt":"You are a senior code reviewer...","tools":["Read","Grep","Glob","Bash"],"model":"sonnet"}}'
```

### Why your file is being ignored

Claude Code skips a file in an `agents/` directory **without reporting it** when any of these hold:

1. There is no `name` field in the frontmatter.
2. The opening `---` is not on the first line.
3. The `name` starts with `-` or contains `:`.
4. There is a `name` but no `description`.
5. The YAML does not parse.

Plugin subagents are the one exception: they load under their filename even without a `name`. If an agent you wrote never gets picked, walk that list before anything else — a blank line above the frontmatter is the most common cause, and it produces no error at all.

### What the agent starts with

A non-fork subagent begins with its own system prompt plus environment details, Claude's delegation message, your full `CLAUDE.md` hierarchy, a git-status snapshot, the full text of anything listed in `skills`, and a roster of its named siblings it can reach with `SendMessage`. It does **not** get the conversation history, your output-style preference, auto-memory (unless `memory` is set), or previous skill invocations.

`memory` is the exception that makes an agent learn across sessions. `memory: project` stores under `.claude/agent-memory/<name>/` (shareable in git), `user` under `~/.claude/agent-memory/<name>/`, and `local` under `.claude/agent-memory-local/<name>/`. The agent receives instructions to read and write it, plus the first 200 lines or 25 KB of its `MEMORY.md`.

Here is this lesson's worked prompt — the one you type after writing the file, to check the harness sees it:

```text
Use the scout subagent to answer: which functions does src/store.ts export?
```

The agent file used in that capture:

```markdown
---
name: scout
description: Answers a one-line factual question about this repository. Read-only, no model pinned.
tools: Read, Grep, Glob
---

You answer one narrow question about the `labtrack` repository and stop.
Reply with at most three lines: the answer first, then the `file:line` evidence.
Do not review, refactor or suggest improvements.
```

## Anti-patterns

**A `description` that describes the agent instead of the trigger.** "A code reviewer" tells Claude nothing about when to delegate. _Fix:_ write the condition — "Use after making a change, before it is committed."

**A blank line before the frontmatter.** The opening `---` must be on line 1 or the file is skipped with no message. _Fix:_ check line 1 first whenever an agent seems not to exist.

**Inheriting every tool for a read-only role.** Omitting `tools` gives a "reviewer" `Edit`, `Write` and `Bash`, and sooner or later it will use them. _Fix:_ allowlist `Read, Grep, Glob` and let the body say plainly that it cannot fix anything.

**Putting the task in the body.** The body is a standing system prompt for every invocation; the specific file or diff belongs in the delegation prompt. _Fix:_ body = role and method, prompt = this task.

**Assuming the agent can see the conversation.** It gets your `CLAUDE.md`, not your chat. _Fix:_ state the task fully, or use a fork (lesson 05).

**Duplicating an agent at user and project scope and wondering which ran.** Project (`.claude/agents/`) beats user (`~/.claude/agents/`), and a nested directory closer to the working directory beats both. _Fix:_ keep one definition, or make the names distinct.
