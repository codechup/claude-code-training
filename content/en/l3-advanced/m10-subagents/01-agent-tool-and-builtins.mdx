## Objectives & prerequisites

By the end of this lesson you can:

- Say what a subagent is in one sentence, and name the single thing it buys you that a longer prompt cannot.
- Describe what the `Agent` tool does with its inputs — `subagent_type`, `prompt`, `description`, `name`, `run_in_background`, `model`, `isolation` — and what comes back.
- Name the six built-in subagents and say what each is for: `Explore`, `Plan`, `general-purpose`, `claude`, `statusline-setup`, `claude-code-guide`.
- Explain why `Explore` and `Plan` are read-only, why they skip your `CLAUDE.md` and git status, and why neither can be resumed.
- Prove a delegation actually happened, from the headless JSON envelope, instead of taking Claude's word for it.

**Prerequisites.** A working Claude Code install (L1 `m01-start`), comfort with the built-in tools (L1 `m02-interact`), and a repository you can run a read-only session in. No configuration is needed: the built-in agents ship with Claude Code.

<WhenNotToUse>
  Delegation costs a round trip and a fresh context window, and the subagent hands back only a text
  summary — the parent never sees the intermediate tool calls. So do not delegate a single-fact
  lookup when you already know the file, symbol or line: reading it yourself is cheaper and the
  answer is exact. Do not delegate work whose intermediate state you need to keep steering (a
  refactor you want to correct halfway through), because you cannot reach inside a running one-shot
  agent to redirect it. And do not delegate to make a slow task fast: several agents at once
  multiply token usage rather than dividing the work for free.
</WhenNotToUse>

## Concept

### What a subagent actually is

A subagent is a **delegated worker with its own context window** that does a side task and returns a single text result to the conversation that spawned it. The official comparison of the parallel-work approaches puts it plainly: reach for a subagent when "a side task would flood your main conversation with search results, logs, or file contents you won't reference again."

That is the whole economics of it. A codebase sweep that reads forty files to answer one question costs forty files' worth of your context if you do it inline, and one paragraph if a subagent does it. The tool calls happen inside the subagent's window; only the conclusion crosses back.

Two consequences follow, and both surprise people:

- **You do not see the work.** The parent gets the result, not the transcript. If you need to audit how an answer was reached, open the subagent's transcript from `/tasks` — do not expect it in your own scrollback.
- **The subagent does not see your conversation.** A non-fork subagent starts with its own system prompt, Claude's delegation message, your `CLAUDE.md` hierarchy, a git-status snapshot, any preloaded skills, and a roster of its named siblings. It does **not** get your conversation history, your output-style preference, or your auto-memory. Everything it needs has to be in the prompt or in the files.

### The Agent tool

Delegation happens through one tool, `Agent`. Its inputs are:

| Input               | What it does                                                                 |
| ------------------- | ---------------------------------------------------------------------------- |
| `subagent_type`     | Which agent to spawn — a built-in name or one of your own                    |
| `prompt`            | The instructions the subagent starts from                                    |
| `description`       | A short human-readable label for the task                                    |
| `name`              | An optional name; with agent teams enabled, a named call launches a teammate |
| `run_in_background` | Asks for concurrent execution; the placement rules in lesson 05 decide       |
| `model`             | A per-invocation model override                                              |
| `isolation`         | Isolation mode, e.g. `worktree`                                              |
| `team_name`         | Accepted for agent teams, and ignored as of v2.1.178                         |

The `Agent` tool itself needs no permission (the tools reference lists it as `Permission required: No`) — the subagent's own tools are still permission-checked inside it. You almost never write an `Agent` call yourself; you ask in plain language and Claude picks the agent:

```text
Use the Explore subagent to find where the CLI persists tasks to disk.
Report the file and function only.
```

You can also be explicit with an @-mention — `@agent-code-reviewer`, or picking `@"code-reviewer (agent)"` from the typeahead — or start a whole session as one agent with `claude --agent code-reviewer`.

Nesting is allowed: a subagent can spawn its own subagents, three layers deep by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, default `3`; at the limit, subagents lose the `Agent` tool). Up to 20 subagents run at once by default (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`).

### The six built-ins

Claude Code ships six subagents you never have to define.

| Agent               | Model                                                             | Tools                                     | What it is for                                        |
| ------------------- | ----------------------------------------------------------------- | ----------------------------------------- | ----------------------------------------------------- |
| `Explore`           | Inherits from the main conversation, capped at Opus on Claude API | Read-only — `Write` and `Edit` are denied | Fast codebase exploration and search                  |
| `Plan`              | Inherits from the main conversation                               | Read-only                                 | Research during plan mode, before a plan is presented |
| `general-purpose`   | `CLAUDE_CODE_SUBAGENT_MODEL` if set, else the main model          | All tools available to subagents          | Complex multi-step tasks that explore _and_ act       |
| `claude`            | Follows the model resolution order                                | —                                         | Catch-all for tasks that fit no specialised agent     |
| `statusline-setup`  | Sonnet                                                            | —                                         | Configuring `/statusline`                             |
| `claude-code-guide` | Haiku                                                             | —                                         | Questions about Claude Code's own features            |

Three properties of `Explore` and `Plan` are worth memorising, because they explain most of the confusion about them:

1. **They are read-only.** They cannot edit, write or change anything. That is what makes them safe to fan out.
2. **They skip your `CLAUDE.md` files and the git status snapshot.** Every other subagent loads both. `Explore` and `Plan` deliberately do not — they start cheap.
3. **They cannot be resumed.** They are one-shot. If you need to continue a conversation with an agent, use `general-purpose` or one of your own.

`Explore` also takes a thoroughness level — quick, medium, or very thorough — so "search these three directories" and "sweep the whole repo for every naming convention" are the same tool at different settings.

### Turning them off

Built-ins are subject to the same permission machinery as everything else. Deny one agent, or all delegation:

<CodeBlock title=".claude/settings.json">

```json
{
  "permissions": {
    "deny": ["Agent(Explore)", "Agent(my-custom-agent)"]
  }
}
```

</CodeBlock>

From the CLI, `claude --disallowedTools "Agent(Explore)"` blocks one agent and `claude --disallowedTools "Agent"` blocks every subagent. `CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS=1` removes the two read-only built-ins specifically.

### Where subagents sit among the parallel options

Subagents are one of four ways to run work in parallel, and the official comparison is worth internalising before you reach for the heaviest one:

- **Subagents** — delegated workers inside one session; results return to the caller.
- **Agent view** (`claude agents`, research preview) — background sessions you dispatch and check on later, each moved into its own worktree under `.claude/worktrees/` before it edits anything.
- **Agent teams** — coordinated sessions with a shared task list and direct messaging; experimental and disabled by default.
- **Dynamic workflows** — a script that runs many subagents and cross-checks their results.

This module is about the first one. The rest of the level meets the others.

## Anti-patterns

**Delegating a lookup you could do in one `Read`.** A subagent costs a spawn, a fresh context and a summarisation step. For "what does `saveToDisk` do", opening the file wins on both speed and precision. _Fix:_ delegate breadth (many files, unknown location), not depth (one known file).

**Expecting the subagent to know what you just discussed.** A non-fork subagent gets no conversation history — only its prompt, your memory files and the repo. The classic failure is a prompt like "fix the bug we talked about". _Fix:_ restate the task in full, or use a fork (lesson 05) when the context genuinely matters.

**Trusting the narration instead of the envelope.** "I've delegated this to a subagent" is model prose. _Fix:_ check `subagent_stats.by_type` in `--output-format json`, or `/tasks` in an interactive session.

**Using `Explore` for work that has to change something.** It is read-only by construction, so it will report rather than fix, and you will read the report as a failure. _Fix:_ use `general-purpose` or a custom agent with write tools when the task ends in an edit.

**Asking to resume `Explore` or `Plan`.** They are one-shot and cannot be resumed. _Fix:_ pick `general-purpose` or a custom agent from the start when you expect a follow-up round.
