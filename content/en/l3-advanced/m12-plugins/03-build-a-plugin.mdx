## Objectives & prerequisites

By the end of this lesson you can:

- Convert an existing `.claude/skills/` skill and a `.claude/settings.json` hook into a plugin, following the official migration steps.
- Write a plugin `hooks/hooks.json` and address a bundled script through `${CLAUDE_PLUGIN_ROOT}`.
- Explain why a hook copied out of `.claude/hooks/` needs one line changed before it works inside a plugin.
- Load a plugin under development with `--plugin-dir`, without installing it, and reload it with `/reload-plugins`.
- Prove a plugin skill really runs, headlessly, with a command you can put in CI.

**Prerequisites.** Lessons `01-plugin-anatomy` and `02-marketplaces`. The `commit-msg` skill from `m06-skills` and the `format-on-save` hook from `m07-hooks` — both are already in the lab repository at this lesson's tag. Node 24 and a clone of the lab repository.

<WhenNotToUse>
  Do not convert a `.claude/` setup to a plugin while you are still changing it every day. The
  official advice is to start standalone for quick iteration and convert when you are ready to
  share, and the reason is concrete: a plugin adds a manifest to keep in sync, a namespace prefix on
  every skill, a version to bump, and a distribution channel. If the answer to "who else needs
  this?" is "nobody yet", the conversion is work you are doing early. And do not convert a hook
  whose whole job is enforcing one repository's own conventions — that hook belongs to that
  repository, not to a package.
</WhenNotToUse>

## Concept

### What migration actually changes

The docs summarise the conversion in four rows:

| Standalone (`.claude/`)       | Plugin                           |
| ----------------------------- | -------------------------------- |
| Only available in one project | Can be shared via marketplaces   |
| Files in `.claude/commands/`  | Files in `plugin-name/commands/` |
| Hooks in `settings.json`      | Hooks in `hooks/hooks.json`      |
| Must manually copy to share   | Install with `/plugin install`   |

Two of those rows are mechanical file moves. The third — hooks moving from `settings.json` to `hooks/hooks.json` — keeps the **same JSON shape**: you copy the `hooks` object out of your settings file into a file whose top-level key is `hooks`. The fourth is the whole point.

After migrating, remove the originals from `.claude/` to avoid duplicates. Note the asymmetry the docs flag: project and user `.claude/agents/` definitions **override** same-named plugin agents, so a plugin agent only takes effect once the original is gone. Plugin skills are namespaced, so `/commit-msg` and `/labtrack-tools:commit-msg` both remain available — nothing overrides anything, you just have two.

### The plugin we are building

`labtrack-tools` bundles one skill and one hook from earlier in the course:

```text
plugins/labtrack-tools/
  .claude-plugin/plugin.json   manifest — name, description, version, author
  skills/commit-msg/SKILL.md   copy of .claude/skills/commit-msg (m06-03)
  hooks/hooks.json             registers the hook below
  hooks/format-on-save.mjs     copy of .claude/hooks/format-on-save.mjs (m07-03)
  README.md                    what it is and how to try it
```

The manifest is the four-field shape from lesson `01`:

<CodeBlock title="plugins/labtrack-tools/.claude-plugin/plugin.json">

```json
{
  "name": "labtrack-tools",
  "description": "The m06/m07 example skill and hook (commit-msg, format-on-save), packaged as an installable plugin for the m12-03-build-a-plugin lab.",
  "version": "1.0.0",
  "author": {
    "name": "CodeChup Claude Code Academy"
  }
}
```

</CodeBlock>

### `hooks/hooks.json` and the root variable

The hook configuration is the `hooks` object you would have written in `settings.json`, with one difference that is not optional:

<CodeBlock title="plugins/labtrack-tools/hooks/hooks.json" highlight="9">

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/format-on-save.mjs\""
          }
        ]
      }
    ]
  }
}
```

</CodeBlock>

`${CLAUDE_PLUGIN_ROOT}` resolves to the plugin's installation directory. It has to, because installing a plugin **copies it into a cache location** — the path you developed at is not the path it runs from. A relative `./hooks/format-on-save.mjs` would resolve against the user's project and fail on every machine but yours.

### The one line of the hook that must change

This is the part that catches people. The `m07` hook computes the repository root from its own file location:

```javascript
const root = join(dirname(fileURLToPath(import.meta.url)), '..', '..');
```

That works when the script lives at `.claude/hooks/` inside the repository. Inside a plugin it walks up into the plugin's own cache directory, so `node_modules/prettier` is never found and the hook silently does nothing — the worst failure mode, because everything looks fine.

A plugin hook has no fixed path relative to the project it is installed into, so it takes the project root from the hook payload instead. `PostToolUse` receives `{tool_name, tool_input, tool_response, cwd, ...}` as JSON on stdin:

<CodeBlock title="plugins/labtrack-tools/hooks/format-on-save.mjs (the changed lines)">

```javascript
// Unlike the project-local hook, a plugin hook has no fixed path relative to the project
// it's installed into — use the project root PostToolUse itself reports (`cwd`).
const root = input.cwd ?? process.cwd();
const abs = isAbsolute(filePath) ? filePath : resolve(root, filePath);
const rel = relative(root, abs).replace(/\\/g, '/');
if (rel.startsWith('..') || rel.length === 0) return; // not inside the project
```

</CodeBlock>

The rest of the hook is unchanged, including the rule that every path exits 0: `PostToolUse` is not a blocking event, and formatting must never interrupt a session.

### Testing without installing

`--plugin-dir` loads a plugin directly from a directory, with no marketplace and no install:

```bash
claude --plugin-dir ./plugins/labtrack-tools
```

Repeat the flag to load several at once, and pass a `.zip` archive instead of a directory if that is what you have. A `--plugin-dir` plugin whose name matches an installed marketplace plugin **takes precedence for that session**, which is how you test a change to a plugin you already have installed. The exception is a plugin that managed settings force-enable or force-disable — `--plugin-dir` cannot override those. Loaded this way, the plugin's identity is `<name>@inline`.

As you edit, `/reload-plugins` picks up changes without restarting: plugins, skills, agents, hooks, plugin MCP servers and plugin LSP servers.

This lesson's example prompt is the conversion itself, delegated:

```text
Package .claude/skills/commit-msg and .claude/hooks/format-on-save.mjs as a
plugin at ./plugins/labtrack-tools. Keep the skill's frontmatter as-is, register
the hook through hooks/hooks.json, and make every bundled path work after an
install — then run claude plugin validate on the result and show me the output.
```

Three things in those recordings are worth naming.

The `--json` report is the shape lesson `04` builds a CI check on: `success`, `strict`, `target`, `manifest` and a `contents` array. Here `contents` is empty and `manifest` carries empty `errors`, `warnings` and `notes` — a clean manifest, and nothing said about the components, because validation reads manifests.

The headless run passes `--allowedTools "Bash(git diff:*),Bash(git status:*)"`. The skill's own `allowed-tools` frontmatter already declares those, but the lab clone has not been trusted, so the session ignores the project's `permissions.allow` entries and says so in its first line. That warning is real and worth reading: **an untrusted workspace drops the project's allow rules**, so a headless run needs its permissions on the command line.

And the prompt is the slash command itself — `/labtrack-tools:commit-msg cli` — not a description of it. `commit-msg` sets `disable-model-invocation: true`, so Claude will never reach for it on its own; the only way to fire it is to invoke it. `--append-system-prompt "Reply in English."` is there because the machine that made this recording has global preferences that answer in another language, exactly as `m01-start/01` describes.

### One honest note about installing this plugin here

The lab repository already wires `.claude/hooks/format-on-save.mjs` directly in its own `.claude/settings.json`. Installing `labtrack-tools` **in that same repository** therefore runs Prettier twice per `Write` or `Edit`. It is harmless — formatting an already-formatted file is a no-op — but it is the kind of thing a plugin should say out loud in its README rather than let a user discover. In a project that does not already have the hook, installing the plugin is exactly the `m07-03` outcome, delivered as a package instead of a hand-copied file.

## Anti-patterns

**Copying the hook script without changing how it finds the project.** A hook that derives the repository root from `import.meta.url` lands in the plugin cache after an install and silently does nothing. _Fix:_ read `cwd` from the hook payload.

**A relative path in `hooks.json`.** `node ./hooks/format-on-save.mjs` works in your working copy and nowhere else. _Fix:_ `node "${CLAUDE_PLUGIN_ROOT}/hooks/format-on-save.mjs"`.

**Leaving the originals in `.claude/` after migrating.** You now have two copies drifting apart, and a plugin agent that never takes effect because the project definition overrides it. _Fix:_ delete the originals once the plugin works, and say so in the commit.

**Editing the plugin and wondering why nothing changed.** Skills reload live; hooks, `.mcp.json`, agents and output styles do not. _Fix:_ run `/reload-plugins` after changing anything but a `SKILL.md`.

**Testing only by reading the code.** A plugin that validates, loads and lists its components can still have a skill Claude never picks or a hook whose matcher never fires. _Fix:_ invoke the skill by its namespaced name and trigger the hook's event, then check the debug log for which hooks matched and how they exited.

**Reaching for `../` to share code between two plugins.** Installation copies each plugin directory; files outside it are not copied. _Fix:_ duplicate the file, or share it within a marketplace with a symlink.
