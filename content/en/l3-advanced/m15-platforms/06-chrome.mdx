## Objectives & prerequisites

By the end of this lesson you can:

- Install the Claude in Chrome extension, start a session with `--chrome`, and check the connection with `/chrome`.
- Explain what site-level permissions are, where they live, and what happens when they are missing.
- Predict which browser calls prompt in plan mode and which do not.
- Drive a local web app: navigate, read the console, fill a form, upload a file, save a screenshot to disk.
- Say what the tab-group cleanup rules do when a session ends, and why a recorded GIF needs review before sharing.

**Prerequisites.** Google Chrome, Microsoft Edge or another Chromium browser (Brave, Arc, Vivaldi, Opera); the Claude in Chrome extension version 1.0.36 or higher; Claude Code installed; and a **direct Anthropic plan** (Pro, Max, Team or Enterprise) signed in with `/login`. A checkout of `lesson/m15-06-start` and a way to serve the lab repository's HTTP API locally.

<WhenNotToUse>
  Chrome integration is not available in WSL, is not available through third-party providers (Amazon
  Bedrock, Google Cloud's Agent Platform, Microsoft Foundry), and is deliberately kept off when you
  authenticate with an API key or a `claude setup-token` long-lived token — the browser extension
  cannot authenticate with those credentials, so `--chrome` is ignored. Beyond availability: do not
  reach for the browser when the site has an API you could call instead, when a test framework would
  be faster and repeatable, or when the task would have Claude act inside an account whose actions
  you cannot cheaply undo. Claude shares your browser's login state — every session you are signed
  into is reachable — so the blast radius of a bad instruction is your real accounts, not a sandbox.
</WhenNotToUse>

## Concept

### Your browser, not a headless one

The whole point is that Claude drives **your** Chrome, with **your** logged-in sessions, in a visible window in real time. That means it can work inside Google Docs, Gmail, Notion or any internal tool you are signed into without an API connector — and it means the same reach is available to a badly phrased instruction. When Claude hits a login page or a CAPTCHA it pauses and asks you to handle it manually.

Claude opens new tabs for browser tasks and the extension collects them into a **Chrome tab group** tied to your session. What happens to that group when the session ends depends on how it ends:

- `/clear` closes the group, open pages included — unless work that survives the clear is still running.
- Switching sessions with `/resume`, exiting Claude Code, or a `/clear` while surviving work is running: the group closes **only if it holds nothing but empty new tabs**, so pages you may still be reading stay open.

The first launch shows a one-time dialog explaining the integration and how site permissions work; press Enter. To avoid the flag every time, run `/chrome` and select **Enabled by default** — but note the trade-off the docs are explicit about: **enabling Chrome by default in the CLI increases context usage, because browser tools are always loaded.** In the VS Code extension no flag is needed at all; Chrome is available whenever the extension is installed.

`/chrome` is your control panel: connection status, permissions, **Reconnect extension**, and **Select browser…** when more than one is connected. The integration is working when the status panel shows `Status: Enabled` and `Extension: Installed`.

If Claude needs the browser and the extension is not detected, it shows a one-per-session prompt titled "Claude wants to use your browser" with three choices — **Install extension** (guided setup, then "Continue with browser tools"), **Not now**, **Don't ask again**.

### Site permissions are the real gate

**Site-level permissions are inherited from the Chrome extension**, and you manage them in the extension's settings. This is not a formality: without permission for a site, Claude cannot act on it, even with `--chrome` on and the extension connected. In an interactive session you will usually see a permission dialog instead, starting with `Claude in Chrome wants to`, offering an option to allow all actions on that site for the session.

### Plan mode splits reads from writes

In plan mode, browser calls that only **read** the page or browser state run without a prompt; calls that **change** state prompt for approval.

| Read-only, no prompt                                                                            | State-changing, prompts                                                |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `read_page`, `get_page_text`, `find`, reading console messages or network requests, screenshots | clicks, typing, navigation, tab and window management, recording a GIF |

The subtlety: an otherwise read-only call **also** prompts when it sets a state-changing input flag — `createIfEmpty` on `tabs_context_mcp`, `clear` on the console and network readers, `save_to_disk` on a screenshot. And a `browser_batch` runs without a prompt only when _every_ action inside it is read-only.

To see the actual tool list, run `/mcp`, select `claude-in-chrome`, then **View tools**.

### What it is good at

Live debugging (read console errors and DOM state, then fix the code that caused them), design verification, web app testing, authenticated web apps, data extraction, task automation, file uploads and GIF recording. The pattern that pays for itself is the loop: build, open, observe, fix — without leaving the terminal.

This lesson's worked example prompt is that loop in one sentence:

```text
Start the API on localhost:3000, open it in the browser, submit the task form
with an empty title, and tell me what the console logs and what the page shows.
```

The docs name three restrictions on uploads. **Permissions:** Claude can upload a file only when the session is allowed to **read** it, so a `Read` deny rule blocks the upload too. **Size:** a single upload can include up to **10 MB** of files in total. **Hard links:** Claude refuses files that have multiple hard links, which is common inside package-manager stores like `node_modules` — copy the file and upload the copy.

On console reading, the docs' advice is specific and good: **tell Claude what patterns to look for** rather than asking for all console output, because logs are verbose and they land in your context window.

### Troubleshooting, briefly

- **Extension not detected**: check `chrome://extensions`, check `claude --version`, check Chrome is running, run `/chrome` → **Reconnect extension**, then restart both. The first time you enable the integration, Claude Code writes a native messaging host configuration file that Chrome reads at startup — so if detection fails on the first attempt, restart Chrome.
- **Browser not responding**: a modal dialog (`alert`, `confirm`, `prompt`) blocks browser events. Dismiss it manually and tell Claude to continue.
- **Connection drops in a long session**: the extension's service worker goes idle. `/chrome` → **Reconnect extension**.
- **Windows**: named pipe conflicts (`EADDRINUSE`) mean another process holds the pipe — restart Claude Code and close other sessions using Chrome.

## Anti-patterns

**"Read the console and tell me what you see."** Console logs are verbose and every line lands in your context window. _Fix:_ name the pattern — an error string, a status code, a component prefix.

**Leaving `--chrome` on by default and wondering where the context went.** Browser tools are loaded on every session when the default is enabled. _Fix:_ turn the default off and pass `--chrome` when you need it.

**Assuming a session-scoped "allow all actions on this site" is small.** Claude shares your browser's login state, so that site is your real, signed-in account. _Fix:_ grant per-site permissions deliberately in the extension, and prefer a test account for anything destructive.

**Sharing a recorded GIF without watching it.** The recording captures everything visible in the browser, including account details on logged-in pages. _Fix:_ review before it leaves your team.

**Reaching for the browser when an API exists.** A page interaction is slower, flakier and less reproducible than a request. _Fix:_ use the browser for what only a browser can do — real rendering, real login state, real console.

**Debugging "browser not responding" by restarting everything.** Nine times out of ten a JavaScript modal is blocking page events. _Fix:_ dismiss the dialog, then tell Claude to continue.
