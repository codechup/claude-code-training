## Objectives & prerequisites

By the end of this lesson you can:

- Say exactly what breaks when Claude Code runs inside tmux, and add the three `~/.tmux.conf` lines that fix it.
- Explain why `/terminal-setup` must be run in the host terminal, not inside tmux or screen.
- Start several sessions side by side with `claude --worktree` and `--tmux`, and say what each flag does.
- Keep a session alive across a dropped SSH connection, and know when Remote Control or a background session is the better answer.
- Decide between a multiplexer, `claude --bg`, Desktop parallel sessions and cloud sessions for a given job.

**Prerequisites.** A terminal, `tmux` installed (`tmux -V`), and a git repository. On Windows this means running inside WSL, since tmux is not a PowerShell program; Claude Code's own tmux guidance assumes a `~/.tmux.conf`, which is the POSIX side of a Windows machine. Lesson `05-remote-control-mobile` is useful background: the two solve overlapping problems differently.

<WhenNotToUse>
  A multiplexer is a terminal window manager, not a scheduler and not a supervisor. Reach for
  something else when you want work that continues with your machine off (a cloud session), when you
  want to steer a running session from your phone (Remote Control), when you want a session detached
  from any terminal at all with a Claude-managed id (`claude --bg`, then `claude attach`), or when
  the reason you want two panes is that two tasks would collide in one working tree — in that case
  the fix is a worktree, not a pane. And do not add tmux to a local desktop workflow just to see two
  sessions: Desktop's sidebar and the split view already do that with git isolation per session.
</WhenNotToUse>

## Concept

### What tmux breaks, and the fix

Claude Code works in any terminal without configuration — but **inside tmux, two things break by default**:

1. `Shift+Enter` submits instead of inserting a newline.
2. Desktop notifications and the progress bar never reach the outer terminal; tmux swallows them.

Three lines fix both:

<CodeBlock title="~/.tmux.conf">

```bash
set -g allow-passthrough on
set -s extended-keys on
set -as terminal-features 'xterm*:extkeys'
```

</CodeBlock>

Then apply them to the running server without restarting it:

<CodeBlock title="apply without restarting tmux">

```bash
tmux source-file ~/.tmux.conf
```

</CodeBlock>

`allow-passthrough` lets notifications and progress updates reach the outer terminal. The two `extended-keys` lines let tmux distinguish `Shift+Enter` from plain `Enter`.

Two related gotchas:

- **`Shift+Enter` inside tmux needs this configuration even when the outer terminal already supports it.** Ghostty, Kitty, iTerm2, WezTerm, Warp, Apple Terminal and Windows Terminal all handle `Shift+Enter` natively — but not through tmux without the lines above.
- **Run `/terminal-setup` in the host terminal, not inside tmux or screen**, because it writes to the host terminal's configuration file. (`/terminal-setup` does detect iTerm2 even from inside tmux, for the clipboard setting it enables there.)

If you would rather not configure anything, `Ctrl+J` inserts a newline in every terminal with no setup, as does typing `\` then `Enter`.

Notifications are worth a second line. Claude Code sends desktop notifications by default only in Ghostty, Kitty and iTerm2. Everywhere else, set `preferredNotifChannel` to `"terminal_bell"`:

<CodeBlock title="~/.claude/settings.json">

```json
{
  "preferredNotifChannel": "terminal_bell"
}
```

</CodeBlock>

The desktop notification does reach your local machine over SSH, so a remote session can still alert you — provided passthrough is on.

### Sessions side by side

The reason to want several sessions at once is almost never "more panes". It is that two tasks would fight over the same working tree. Claude Code has a first-class answer:

<CodeBlock title="a session in its own git worktree">

```bash
claude --worktree
claude --worktree api-refactor
```

</CodeBlock>

And, on top of that, a flag that lays the worktree's session out in a multiplexer:

Read that carefully: **`--tmux` requires `--worktree`.** It uses iTerm2 native panes when available; `--tmux=classic` forces traditional tmux. So the shape is `claude --worktree <name> --tmux`, not `--tmux` on its own.

Doing it by hand is the same idea with more typing, and it is worth doing once so you understand what the flag automates:

<CodeBlock title="two sessions, two worktrees, one tmux session">

```bash
git worktree add ../lab-api feature/api
git worktree add ../lab-cli feature/cli
tmux new-session -d -s cc -n api -c ../lab-api
tmux new-window -t cc -n cli -c ../lab-cli
tmux send-keys -t cc:api 'claude' Enter
tmux send-keys -t cc:cli 'claude' Enter
tmux attach -t cc
```

</CodeBlock>

This lesson's worked example prompt is the kind of task that earns a second worktree — one you would not want interleaved with anything else in the same tree:

```text
Rename the pagination helper across the whole codebase and update every call
site and test. Do not touch anything outside src/ and test/.
```

### Surviving a dropped connection

This is the classic reason to reach for tmux, and the Remote Control documentation names it explicitly: **to keep a session running on a remote machine after you disconnect from SSH, start it inside `tmux` or `screen`.** Remote Control runs as a local process — close the terminal or quit the client and the session goes offline within seconds. A multiplexer keeps the process alive; `tmux attach` brings you back to it.

The two combine well. Start `claude remote-control` inside tmux on the remote box, detach, close the laptop, and drive the session from your phone: tmux keeps the process alive, Remote Control gives you the interface.

### The alternatives, honestly

| You want                                                 | Reach for                                      |
| -------------------------------------------------------- | ---------------------------------------------- |
| Two tasks that must not share a working tree             | `claude --worktree` (optionally with `--tmux`) |
| A session that survives your SSH connection dropping     | tmux or screen on the remote machine           |
| A detached session with an id you can reattach to        | `claude --bg`, then `claude attach <id>`       |
| To drive a running local session from a phone or browser | Remote Control                                 |
| Work that continues with your machine off                | A cloud session                                |
| Parallel sessions with git isolation and a GUI           | The Desktop app's sidebar                      |

`claude --bg` deserves a mention because it solves the "keep it running" half without a multiplexer at all: it starts the session in the background and prints an id that `claude attach`, `logs`, `stop` and `rm` take, and `claude agents` lists them. If all you wanted was detachment, that is simpler than tmux.

One more terminal note that belongs here: if the display flickers or the scroll position jumps while Claude works, `/tui fullscreen` switches to the fullscreen renderer and saves the preference. Inside a multiplexer that often matters more than it does in a bare terminal.

## Anti-patterns

**Adding panes instead of worktrees.** Two sessions in one working tree will overwrite each other's edits, no matter how the terminal is arranged. _Fix:_ `claude --worktree`, and add `--tmux` only if you also want the layout.

**Passing `--tmux` on its own.** It requires `--worktree`. _Fix:_ `claude --worktree <name> --tmux`.

**Running `/terminal-setup` inside tmux.** It writes to the host terminal's configuration file and cannot see it from inside the multiplexer. _Fix:_ run it in the host terminal once, then use tmux.

**Blaming Claude Code when notifications stop inside tmux.** tmux swallows them without `allow-passthrough on`. _Fix:_ the three config lines, plus `preferredNotifChannel: "terminal_bell"` if your terminal is not Ghostty, Kitty or iTerm2.

**Using tmux as a scheduler.** It keeps a process alive; it does not start work, retry it, or run it when you are away. _Fix:_ cloud routines or Desktop scheduled tasks for scheduled work; `claude --bg` for detachment with a managed id.

**Reaching for tmux to "watch two sessions" on your own desktop.** Desktop's sidebar and split view already do that, with a git worktree per session. _Fix:_ use the surface built for it, and keep tmux for remote and SSH work.
