## Objectives & prerequisites

By the end of this lesson you can:

- Connect Claude Code to your own Chrome, and check the connection with `/chrome`.
- Say what the integration actually is — your real browser, your real logins — and what follows from that.
- Predict which browser calls prompt you in plan mode and which run silently.
- Ask for a GIF recording of a browser run, and know what ends up inside it.
- Diagnose the four errors you will actually hit, and know that WSL is not supported.

**Prerequisites.** Google Chrome, Microsoft Edge, or another Chromium browser (Brave, Arc, Vivaldi, Opera); the Claude in Chrome extension version 1.0.36 or higher; a direct Anthropic plan (Pro, Max, Team or Enterprise); and a session signed in with `/login`. A session authenticated with an API key or a long-lived `claude setup-token` keeps Chrome integration off even when you pass `--chrome`, because the extension cannot authenticate with those credentials. Chrome integration is not supported in WSL, and is unavailable through Amazon Bedrock, Google Cloud's Agent Platform and Microsoft Foundry.

<WhenNotToUse>
  This is your browser, with your cookies and your sessions, driven by an agent. That is exactly
  what makes it useful and exactly what makes it the wrong tool for some jobs. Do not reach for it
  when a deterministic, repeatable check is what you need — a Playwright suite in CI does not depend
  on which tabs you had open. Do not use it where a stray click has real consequences: production
  admin consoles, payment flows, anything that sends mail. Do not use it as a scraper for a site
  with an API, and do not use it when the page's content is untrusted, because a page Claude reads
  can try to instruct it. Enabling Chrome by default also loads the browser tools into every
  session, which costs context you may want elsewhere.
</WhenNotToUse>

## Concept

### What the integration is

Claude Code talks to the Claude in Chrome browser extension. Claude opens new tabs for browser tasks and **shares your browser's login state**, so it can work inside any site you are already signed into — Gmail, Notion, your CRM, an internal dashboard — with no API connector. Actions run in a visible Chrome window in real time, and when Claude hits a login page or a CAPTCHA it stops and asks you to handle it by hand.

The tabs Claude opens are collected into a Chrome tab group tied to your session. When you type `/clear`, Claude Code closes that group, open pages included, unless work that survives the clear is still running. When you switch sessions with `/resume`, exit, or `/clear` while such work is running, it closes the group only if it holds nothing but empty new tabs — so pages you may still be reading stay open.

The first launch shows a one-time dialog explaining the integration and how site permissions work. To avoid the flag every time, run `/chrome` and select **Enabled by default** — at the cost of loading the browser tools into every session, which increases context usage.

`/chrome` is also the panel for everything else: connection status, permissions, **Reconnect extension**, and **Select browser…** when more than one browser is connected. The integration is working when the panel shows `Status: Enabled` and `Extension: Installed`. If Claude needs the browser in an interactive session and the extension is not detected, Claude Code shows a "Claude wants to use your browser" prompt, at most once per session, offering **Install extension**, **Not now** or **Don't ask again**.

This lesson's worked prompt is the documentation's own first example — a navigate, an interaction and a report, in one sentence:

```text
Go to code.claude.com/docs, click on the search box,
type "hooks", and tell me what results appear
```

Read the names and the capability list falls out of them: `navigate` and the `tabs_*` tools for getting somewhere, `computer` for clicking and typing, `read_page` / `get_page_text` / `find` for reading, `form_input` for forms, `read_console_messages` and `read_network_requests` for debugging, `file_upload` and `upload_image` for attachments, `gif_creator` for recordings, and `browser_batch` for running several actions in one call.

### Which calls prompt you

In plan mode the split is between reading and changing:

|                              | Calls                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------- |
| **Read-only** — no prompt    | `read_page`, `get_page_text`, `find`, reading console messages or network requests, taking a screenshot |
| **State-changing** — prompts | clicks, typing, navigation, tab and window management, and recording a GIF                              |

An otherwise read-only call also prompts when it sets a state-changing input flag — `createIfEmpty` on `tabs_context_mcp`, `clear` on the console and network readers, `save_to_disk` on a screenshot. A `browser_batch` runs without a prompt only when every action inside it is read-only.

Site-level permissions are separate and come from the extension itself: manage in the Chrome extension settings which sites Claude may browse, click and type on. Outside plan mode, the first browser action on a site raises a dialog starting `Claude in Chrome wants to`, with an option to allow all actions on that site for the session.

### Recording a GIF

Ask for it in words; the recording is a normal part of the run:

```text
Record a GIF showing how to complete the checkout flow, from adding
an item to the cart through to the confirmation page.
```

Claude records the interaction sequence and saves it as a GIF file. The thing to internalise before you share one: **the recording captures everything visible in the browser**, including account details on logged-in pages. Review it before it leaves your team. And because recording a GIF is a state-changing call, it prompts for approval in plan mode.

Screenshots work the same way — "take a screenshot of the checkout page and save it to disk" — and Claude reports the file path it wrote.

### Uploads

Claude can attach a local file to an upload field on a page; Claude Code reads the file and sends its contents to the browser, so this works in local and remote sessions alike (2.1.211 or later). Three restrictions: a permission rule that denies `Read` on a file also blocks uploading it; a single upload carries at most 10 MB in total; and files with multiple hard links are refused — common inside package-manager stores like `node_modules`, so copy the file and upload the copy.

### When it will not connect

The first time you enable the integration, Claude Code installs a native messaging host configuration file, which Chrome reads at startup — so if the extension is not detected on the first attempt, restart Chrome. If it still fails, check that the host configuration is where the documentation says it should be — a file on macOS and Linux, a registry key on Windows, where the documentation names the parent key rather than the entry inside it:


  </Fragment>
  <Fragment slot="linux">

```bash
ls ~/.config/google-chrome/NativeMessagingHosts/com.anthropic.claude_code_browser_extension.json
```

  </Fragment>
  <Fragment slot="windows">

```powershell
Get-ChildItem 'HKCU:\Software\Google\Chrome\NativeMessagingHosts\'
```

  </Fragment>
</OSTabs>

Edge uses the same filename under its own configuration directory (`~/Library/Application Support/Microsoft Edge/NativeMessagingHosts/`, `~/.config/microsoft-edge/NativeMessagingHosts/`, or `HKCU\Software\Microsoft\Edge\NativeMessagingHosts\`), and every other Chromium browser has its own directory and registry key. The WSL tab is missing on purpose: Chrome integration is not supported in WSL.

The four errors worth memorising:

| Error                                       | Cause                                                                                                        | Fix                                                         |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| `Browser extension is not connected`        | The native messaging host cannot reach the extension, or an organisation IP allowlist rejects the connection | Restart Chrome and Claude Code, then `/chrome` to reconnect |
| Extension shows `Not detected` in `/chrome` | Extension not installed or disabled                                                                          | Install or enable it in `chrome://extensions`               |
| `No tab available`                          | Claude acted before a tab was ready                                                                          | Ask Claude to create a new tab and retry                    |
| `Receiving end does not exist`              | The extension's service worker went idle                                                                     | `/chrome` → **Reconnect extension**                         |

A modal `alert`, `confirm` or `prompt` dialog also blocks browser events entirely: dismiss it by hand, then tell Claude to continue.

## Anti-patterns

**Pointing it at production.** It is your real browser with your real sessions; a misread selector in an admin console is a real change. _Fix:_ drive a local server or a staging site, and keep site permissions in the extension narrow.

**Asking for "all the console output".** Console logs are verbose and they land in your context window. _Fix:_ say what to look for — "check the console for errors during the page load" — as the documentation itself advises.

**Using it as a CI check.** A run that depends on your logged-in browser is not reproducible by anyone else, and it cannot run headless on a build machine. _Fix:_ use Chrome for exploration and debugging; write the durable check in Playwright.

**Sharing a GIF without watching it.** The recording captures everything visible, including account details on a logged-in page. _Fix:_ open it and look at every frame before it leaves your team.

**Leaving Chrome enabled by default and wondering where the context went.** The browser tools load into every session when the default is on. _Fix:_ turn the default off and pass `--chrome` when you need it.

**Trying it inside WSL.** It is not supported there, and no amount of reconnecting fixes that. _Fix:_ run Claude Code natively on the host when you need the browser.

<Callout variant="changed">
  Sessions authenticated with an API key or a `claude setup-token` token now keep Chrome integration
  off even when you pass `--chrome`. Before 2.1.216 such a session could enable it, and every
  attempt to reach the extension failed with a 403.
</Callout>
