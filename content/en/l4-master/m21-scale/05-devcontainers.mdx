## Objectives & prerequisites

By the end of this lesson you can:

- Add Claude Code to an existing dev container with the official Dev Container Feature, and say what the version tag on it pins.
- Keep authentication across rebuilds by mounting a volume at `~/.claude` **and** setting `CLAUDE_CONFIG_DIR` — and explain why the volume alone is not enough.
- Deliver organisation policy into a container through `/etc/claude-code/managed-settings.json` and `containerEnv`, and say why the Dockerfile route is not tamper-proof.
- State the security boundary honestly: what `--dangerously-skip-permissions` inside a container does and does not protect.
- Write a corporate launcher that satisfies the `CLAUDE_CODE_PROCESS_WRAPPER` contract, and name the processes it does not reach.

**Prerequisites.** Docker and a dev-container-capable editor if you want to run the lab; the previous lesson's managed settings and network configuration; `m14-security` for permission modes.

<WhenNotToUse>
  A dev container is worth its weight when a team needs one identical toolchain, or when you want
  Claude's commands to run somewhere other than your host. It is not a substitute for the permission
  system: the official warning is blunt — with `--dangerously-skip-permissions`, a dev container
  does not stop a malicious project exfiltrating anything reachable inside it, including the Claude
  Code credentials in `~/.claude`. Use containers with repositories you trust, and never mount host
  secrets such as `~/.ssh` or cloud credential files into one. If you want fewer prompts without
  removing the review step, auto mode is the feature you actually want. And the corporate launcher
  in the second half is only for organisations that genuinely mandate one — on Windows the variable
  is ignored entirely.
</WhenNotToUse>

## Concept

### Adding Claude Code to a dev container

A dev container is a Docker container defined by your repository, which an editor that supports the [Dev Containers spec](https://containers.dev/) connects to: you edit files as usual, but the terminal, language servers and build tools run inside the container. Claude Code installs into any of them through the official Dev Container Feature.

<CodeBlock title=".devcontainer/devcontainer.json">

```json
{
  "image": "mcr.microsoft.com/devcontainers/base:ubuntu",
  "features": {
    "ghcr.io/anthropics/devcontainer-features/claude-code:1.0": {}
  }
}
```

</CodeBlock>

Then rebuild the container — **Dev Containers: Rebuild Container** in the VS Code command palette, or your tool's equivalent — open a terminal inside it and run `claude` to sign in.

The `:1.0` tag pins the _feature's install script_, not the Claude Code release: the feature installs the latest Claude Code, which then auto-updates itself inside the container. If a build fails with `Failed to install Node.js and npm`, add `"ghcr.io/devcontainers/features/node:1": {}` above the Claude Code feature.

What the sign-in looks like depends on your provider. Going to Anthropic, it is a browser sign-in; on Bedrock, the Agent Platform or Foundry, Claude Code uses your cloud credentials with no browser prompt. Pass those in through `containerEnv`, a Codespaces secret, or your cloud's workload identity — **not** by mounting credential files from the host.

### Surviving a rebuild

By default the container's home directory is discarded on rebuild, so everyone signs in again. The trap is that mounting a volume at `~/.claude` is not sufficient on its own: the OAuth account, personal MCP servers and per-project trust live in `~/.claude.json`, a separate file _outside_ that directory. Mount the volume and point `CLAUDE_CONFIG_DIR` at the same path so that file is written inside it too.

<CodeBlock title="devcontainer.json (remoteUser is the container's non-root user)">

```json
"mounts": ["source=claude-code-config,target=/home/<user>/.claude,type=volume"],
"containerEnv": { "CLAUDE_CONFIG_DIR": "/home/<user>/.claude" }
```

</CodeBlock>

Replace `<user>` with your container's `remoteUser` — the official example uses the `node` user. To keep state per project instead of one volume shared across repositories, put `${devcontainerId}` in the source name. In GitHub Codespaces `~/.claude` survives a stop and start but is cleared by a rebuild, so the same configuration applies; to carry authentication across codespaces, store an `ANTHROPIC_API_KEY` or a `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` as a Codespaces secret.

### Policy inside the container

A container is a convenient place to apply policy, because the same image runs on every machine. Claude Code reads `/etc/claude-code/managed-settings.json` on Linux at the highest precedence in the settings hierarchy — above anything an engineer sets in `~/.claude` or the project's `.claude/`.

<CodeBlock title="Dockerfile">

```dockerfile
RUN mkdir -p /etc/claude-code
COPY managed-settings.json /etc/claude-code/managed-settings.json
```

</CodeBlock>

Be honest about what that achieves: the Dockerfile lives in the repository, so anyone with write access can change or remove that step. For policy engineers cannot bypass, deliver managed settings through server-managed settings or your MDM instead.

Environment variables for every session in the container go in `containerEnv`:

<CodeBlock title="devcontainer.json">

```json
"containerEnv": {
  "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC": "1",
  "DISABLE_AUTOUPDATER": "1"
}
```

</CodeBlock>

Two consequences worth stating. `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` also disables feature-flag evaluation, so Remote Control and everything else that depends on feature-flag fetching stops working in that container. And because the feature always installs the latest release, a build you need to be reproducible should install a pinned version from the Dockerfile — `npm install -g @anthropic-ai/claude-code@X.Y.Z` — with `DISABLE_AUTOUPDATER` set, instead of using the feature.

For MCP servers inside the container, define them at project scope in a `.mcp.json` at the repository root, install any stdio server binaries in the Dockerfile, and add remote server domains to your egress allowlist.

### Egress, and the honest security boundary

You can limit the container's outbound traffic to the domains Claude Code needs — the network-access table from the previous lesson is the list. The reference container in the `anthropics/claude-code` repository includes an `init-firewall.sh` that does this, and adds the `NET_ADMIN` and `NET_RAW` capabilities through `runArgs` because running a firewall inside a container needs them. Neither the script nor those capabilities are required by Claude Code itself; you can leave them out and use your own network controls.

Because the container runs Claude Code as a non-root user and confines command execution, `--dangerously-skip-permissions` becomes viable for unattended work — the CLI refuses the flag when launched as root, so confirm `remoteUser` is a non-root account. Understand what you give up: no review of tool calls, Claude can still modify any file in the bind-mounted workspace (which appears on your host), and it can reach anything the container's network policy allows. Pair it with egress restrictions, or use auto mode instead. To stop engineers using the flag at all, set `permissions.disableBypassPermissionsMode` to `"disable"` in managed settings.

### Corporate launchers

Some organisations require every process on a workstation to start through a mandatory launcher that applies the sandbox, network controls or credential injection their security posture depends on. A launcher that wraps the `claude` command on `PATH` misses most of what Claude Code starts, because those processes start from the binary's direct path without a `PATH` lookup.

`CLAUDE_CODE_PROCESS_WRAPPER` (v2.1.208+), or the `processWrapper` setting (v2.1.210+), covers them: the background service, every agent view session including warm standby ones, sessions respawned after an update or a crash, and Claude Code's self-relaunch to finish an update. Remote Control's session processes and agent-teams' split-pane teammate sessions are covered too, but only on v2.1.210 or later — that version gate applies to both the environment variable and the setting.

<CodeBlock title="/usr/local/sbin/corp-launcher">

```bash
#!/bin/sh
# Your organisation's setup: enter the sandbox, apply
# network controls, or inject credentials.
exec "$@"
```

</CodeBlock>

The contract is strict, and Claude Code refuses to start a process rather than starting it unwrapped when the launcher cannot run. End with `exec "$@"`. Do not reorder, absorb or prepend arguments. Pass every inherited environment variable through — the per-session auth tokens, the model and provider selection, and the wrapper variable itself all travel there, so a launcher that rebuilds the environment from an allowlist breaks the sessions it starts. Reach `exec` within about three seconds each time. Tolerate being invoked from inside itself. Print nothing before the `exec`.

Some processes are outside it: a session you start yourself in a terminal, an installed background service whose unit predates the configuration, the first process of a `claude-cli://` deep link, the `--worktree`-plus-`--tmux` relaunch, and the Claude in Chrome native-messaging host. **On Windows the variable is ignored entirely** — the contract depends on `exec` — so count Windows machines as unwrapped when you plan a rollout. Run `/status` and look at the **Self-exec** entry, or `claude daemon status`, to see the resolved launch command; after deploying the setting, `claude daemon stop --any` so the next background session starts a supervisor that honours it.

Do not confuse it with `CLAUDE_CODE_SHELL_PREFIX`, which wraps the shell commands Claude runs _on your behalf_ and passes each as a single shell-quoted string. A launcher written for one does not work as the other.

Here is this lesson's worked example prompt, for auditing a container definition you inherited:

```text
Read .devcontainer/devcontainer.json and the Dockerfile, and tell me whether a rebuild
would sign me out, whether managed settings are actually enforced, and what egress is allowed.
```

That failure is the single most likely thing to go wrong on a first devcontainer build, and it is worth reading closely. The Claude Code feature installs Node.js itself when the base image does not provide it — `mcr.microsoft.com/devcontainers/base:ubuntu` does not — and when that install fails, the feature prints the exact `features` block that fixes it. ## Anti-patterns

**Mounting a volume at `~/.claude` and calling authentication persistent.** `~/.claude.json` — the OAuth account, personal MCP servers, per-project trust — lives outside that directory, so rebuilds still sign you out. _Fix:_ set `CLAUDE_CONFIG_DIR` to the same path as the mount.

**Treating a Dockerfile-delivered `managed-settings.json` as enforcement.** It sits in the repository, so anyone with write access can edit or delete the `COPY`. _Fix:_ use server-managed settings or your MDM for policy engineers must not bypass.

**Mounting `~/.ssh` or cloud credential files into the container for convenience.** The documented warning is explicit that a container does not stop exfiltration of anything reachable inside it. _Fix:_ pass short-lived, repository-scoped credentials through `containerEnv`, a Codespaces secret, or workload identity.

**Assuming the container is the security boundary for `--dangerously-skip-permissions`.** Claude can still write every file in the bind-mounted workspace — which is on your host — and reach whatever the network policy allows. _Fix:_ restrict egress as well, or use auto mode and keep the review step.

**Pinning the feature tag and expecting a pinned CLI.** `:1.0` pins the install script; the feature installs the latest release and it then auto-updates. _Fix:_ `npm install -g @anthropic-ai/claude-code@X.Y.Z` in the Dockerfile plus `DISABLE_AUTOUPDATER=1`.

**Wrapping `claude` on `PATH` and reporting the launcher rollout complete.** Self-spawned processes never consult `PATH`, and on Windows `CLAUDE_CODE_PROCESS_WRAPPER` is ignored altogether. _Fix:_ deliver `processWrapper` through settings, run `claude daemon stop --any`, and count Windows machines as unwrapped.
