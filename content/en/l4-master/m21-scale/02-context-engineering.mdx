## Objectives & prerequisites

By the end of this lesson you can:

- List what loads into the context window before you type your first word, and name the three layers a request is ordered into.
- Read `/context` and say which category is costing you.
- Choose deliberately between `/compact`, `/compact <instructions>`, `/clear`, `/rewind` and `/autocompact <tokens>`.
- Say what survives compaction and what does not — including the five-file re-read, the skill-body caps, and which rules come back.
- Decide when to delegate a read to a subagent, using the honest trade-off: a leaner main context, paid for with a second cold context window.

**Prerequisites.** `m10-subagents` (what a subagent is and how to invoke one) and `m03-memory` (`CLAUDE.md`, rules, auto memory). The previous lesson's scoping techniques shrink the _starting_ size of context; this one is about what happens to it as a session runs.

<WhenNotToUse>
  Do not engineer context in a session that is going fine. Compaction is not free — it discards
  detail and rebuilds the conversation cache — so a `/compact` reflex every few turns costs more
  than it saves. Do not delegate a read to a subagent when the file is small or when you will need
  the full contents later in the same session: the subagent returns a summary, not the file, and its
  own context starts cold. And do not treat `/clear` as a fix for a bad answer; it is a fix for a
  session that has moved on to unrelated work.
</WhenNotToUse>

## Concept

### What is in the window before you type

A session is never blank. Before your first prompt, the window already holds the system prompt (core instructions, tool definitions, and any output style or `--append-system-prompt` text), `CLAUDE.md`, auto memory, MCP tool names and skill descriptions, plus environment information — working directory, platform, shell, OS version, git status. Your own setup adds to that.

As Claude works, each file read adds to context, path-scoped rules load alongside the files they match, and a hook can add to it too — a `SessionStart` hook’s stdout goes into context before your first prompt.

Claude Code orders every request into three layers so that the parts that rarely change come first:

| Layer           | Content                                           | Changes when                                                           |
| --------------- | ------------------------------------------------- | ---------------------------------------------------------------------- |
| System prompt   | Core instructions, tool definitions, output style | The set of loaded tool definitions changes, or Claude Code is upgraded |
| Project context | `CLAUDE.md`, auto memory, unscoped rules          | Session starts, or after `/clear` or `/compact`                        |
| Conversation    | Your messages, Claude's responses, tool results   | Every turn                                                             |

That ordering is a caching decision, and the next lesson is entirely about what it buys you. Here it explains a behaviour that otherwise looks like a bug: **editing your project-root `CLAUDE.md` mid-session does not apply.** It is read once at session start and held; the new content loads on the next `/clear`, `/compact` or restart. The same is true of output style.

### Seeing your own numbers

`/context` prints a live breakdown by category, with optimisation suggestions and the list of `CLAUDE.md` and auto-memory files that loaded. `/memory` opens those files to edit. Both are interactive-only — there is no headless equivalent, as the second transcript below shows. In a script, the token counts come from the `usage` object in `claude -p … --output-format json` instead.

### Acting before the window fills

Claude Code compacts automatically as you approach the limit, so a full window never ends a session. You have five ways to get ahead of it:

<CodeBlock title="in a session">

```text
/compact focus on the auth bug fix   # summarise now, keeping what you name
/rewind                              # then "Summarize from here" / "Summarize up to here"
/autocompact 500k                    # compact earlier: set how full the window gets first
/clear                               # switching to unrelated work
```

</CodeBlock>

`/autocompact <tokens>` writes the [`autoCompactWindow`](https://code.claude.com/docs/en/settings-reference.md) setting to your user settings. Auto-compaction itself is turned off or on with `autoCompactEnabled`; `DISABLE_AUTO_COMPACT` turns it off for one session, and the manual `/compact` keeps working when it is off. For one session, the `--autocompact` CLI flag takes precedence over that setting, and `CLAUDE_CODE_AUTO_COMPACT_WINDOW` takes precedence over both.

The fifth way is to not put the content in your window at all — delegate the reading to a subagent, which is the second half of this lesson.

If what you need is a bigger window rather than a shorter conversation, Fable 5.1, Fable 5, Sonnet 5, Opus 4.6 and later, and Sonnet 4.6 support a 1 million token context window; Sonnet 5 runs at 1M with no `[1m]` variant to select. Compaction works the same way at the larger limit.

### What survives compaction

Compaction replaces the message history with a summary. What happens to a piece of content depends on how it got there:

| Mechanism                                | After compaction                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| System prompt and output style           | Unchanged; not part of message history                                                      |
| Project-root `CLAUDE.md`, unscoped rules | Re-injected from disk                                                                       |
| Auto memory                              | Re-injected from disk                                                                       |
| The plan Claude wrote in plan mode       | Re-injected from disk                                                                       |
| Rules with `paths:` frontmatter          | Reloaded as Claude reads files they match                                                   |
| Nested `CLAUDE.md` in subdirectories     | Reloaded as Claude reads files in that subdirectory                                         |
| Files Claude read or edited              | Claude Code re-reads up to five, most recently modified first                               |
| Invoked skill bodies                     | Re-injected, capped at 5,000 tokens per skill and 25,000 tokens total; oldest dropped first |
| Context that hooks added earlier         | Summarised with the rest of the conversation                                                |
| `SessionStart` hooks matching `compact`  | Claude Code runs them and adds their output                                                 |

Three consequences follow directly. A file over 5,000 tokens comes back after the re-read as a path reference rather than its content — shown as `Referenced file` instead of `Read` — though its rules still reload. A rule that must persist across compaction should drop its `paths:` frontmatter or move into the project-root `CLAUDE.md`. And because skill bodies are truncated from the end, the instructions that matter most belong at the top of `SKILL.md`.

Since v2.1.198 the summarisation request inherits the session's extended-thinking configuration — it reasons with thinking on when your session has it on. That affects only how the summary is produced.

### Delegating a read to a subagent

A subagent runs in its own context window. It reads what it needs there and returns only its answer, so the file contents never enter your conversation. From your side, the call and the result are two appended messages.

That is the well-known half. The honest half is the cost. Here is this lesson's worked example prompt, run two ways against a directory of seven files:

```text
Read every .ts file in large/src/notifications/ and give me a one-line summary of each.
```

Done directly, that is seven reads landing in your context. Delegated to the built-in `Explore` subagent, the reads land in the subagent's context and one summary comes back. The measured result from the lab below: **8,596 tokens added to the main conversation's cache directly, versus 1,185 through the subagent** — and **$0.064 versus $0.128 in total cost.** The delegation kept the main window seven-eighths cleaner and cost roughly twice as much, because the subagent starts from a cold prefix of its own.

So the rule is not "always delegate". It is: delegate when the main session's context is the scarce resource — a long session you need to keep going, a read whose contents you will never need again — and read directly when the session is short or you will want the file later anyway.

## Anti-patterns

**Editing `CLAUDE.md` and expecting the running session to pick it up.** It was read at session start and held in memory; the edit lands on disk and changes nothing until `/clear`, `/compact` or a restart. _Fix:_ make the edit, then `/clear`, or state the new instruction in the prompt for the rest of this session.

**Compacting mid-task.** The summary keeps what the automatic pass guesses is important, which in the middle of a task is rarely what you were about to need. _Fix:_ compact at a natural break, or pass instructions — `/compact focus on the auth bug fix`.

**Using `/compact` to abandon a bad path.** Compaction summarises the wrong turn along with everything else. _Fix:_ `/rewind` back to before it. Rewinding truncates to a prefix that already exists rather than building a new one.

**Delegating everything to subagents to "save context".** Each subagent starts cold and is billed accordingly; the lab measured roughly double the cost for one small directory. _Fix:_ delegate reads whose contents you will not need again, in sessions where the main window is the constraint.

**Writing the important part at the bottom of a `SKILL.md`.** After compaction, skill bodies are re-injected but truncated from the end, capped at 5,000 tokens each and 25,000 in total. _Fix:_ put the instructions that must survive at the top of the file.

**Trusting a `paths:`-scoped rule to hold across a long session.** It lives in message history, so compaction summarises it away and it only comes back when a matching file is read again. _Fix:_ for a rule that must always apply, drop `paths:` or move it into the project-root `CLAUDE.md`.
