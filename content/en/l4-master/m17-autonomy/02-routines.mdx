## Objectives & prerequisites

By the end of this lesson you can:

- Say what a routine is — a saved prompt, repositories, an environment and connectors — and where it runs.
- Attach each of the three trigger types: a schedule (recurring or one-off), an API endpoint, and a GitHub event with filters.
- Fire a routine over HTTP with a bearer token and explain how the `text` payload reaches the run.
- Write a routine prompt that is safe to run unattended, because a routine has no permission prompts at all.
- Manage routines from the CLI with `/schedule`, and diagnose the common "Unknown command" failure.

**Prerequisites.** Lesson 1 (`/loop`), a claude.ai account on Pro, Max, Team or Enterprise, and the Claude GitHub App if you want a GitHub trigger. Routines are in **research preview**: behaviour, limits and the API surface may change.

<WhenNotToUse>
  A routine runs in the cloud against a fresh clone, with no permission prompts and every connector
  you leave attached — so it is the wrong home for anything that needs your local files, your local
  MCP servers, or a human's judgement mid-run. It is also the wrong tool below an hour: the minimum
  schedule interval is one hour, and expressions that run more often are rejected. And if the work
  is already a CI job triggered by a push, GitHub Actions is the simpler place for it; a routine
  earns its keep when the trigger is a clock, an alert, or a repository event your pipeline does not
  cover.
</WhenNotToUse>

## Concept

### What a routine is

A routine is a saved Claude Code configuration — a prompt, one or more repositories, a cloud environment and a set of connectors — packaged once and run automatically. Routines execute on Anthropic-managed cloud infrastructure, or on your organisation's self-hosted environment when routed there, so they keep working with your laptop shut.

They are available on Pro, Max, Team and Enterprise plans, and you create and manage them at `claude.ai/code/routines`, in the Desktop app's **Code** tab, or from the CLI with `/schedule` (also available as `/routines`). All three surfaces write to the same cloud account. Team and Enterprise Owners can disable routines org-wide with the **Routines** toggle in admin settings, which stops existing routines and blocks new ones.

Two properties shape everything else in this lesson:

- **Routines run autonomously.** There is no permission-mode picker and no approval prompts during a run. The session can run shell commands, use skills committed to the cloned repository, and call any connector you included.
- **Routines act as you.** They belong to your individual claude.ai account, are not shared with teammates, and count against your account's daily run allowance. Commits and pull requests carry your GitHub user; Slack messages or Linear tickets use your linked accounts.

That is the whole guardrail story: what a routine can reach is decided by the repositories you select, the environment's network access and variables, and the connectors you leave attached. Scope each to what the routine actually needs.

### The three triggers

A routine can carry any combination of triggers, added or removed at any time from the **Select a trigger** section of its edit form.

| Trigger      | Starts the routine when                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------ |
| **Schedule** | A recurring cadence comes due — hourly, daily, weekdays, weekly — or a one-off timestamp arrives |
| **API**      | Someone POSTs to the routine's per-routine endpoint with its bearer token                        |
| **GitHub**   | A pull request or release event matches on a connected repository                                |

**Schedules.** Times are entered in your local zone and converted, so the routine runs at that wall-clock time wherever the infrastructure sits. Runs may start a few minutes late due to a stagger that is consistent per routine. For an interval the presets do not offer — every two hours, the first of each month — pick the closest preset and then run `/schedule update` in the CLI to set a cron expression. The minimum interval is one hour; anything more frequent is rejected. A one-off schedule fires once, then auto-disables and shows as **Ran**; one-off runs do not count against the daily routine cap.

**API triggers.** POSTing to the routine's `/fire` endpoint starts a new session and returns its URL. The body takes an optional `text` field for run-specific context — an alert body, a failing log. It is freeform: send JSON and the routine receives it as a literal string.

<CodeBlock title="fire a routine (the trigger id is a placeholder; the token comes from the environment)">

```bash
curl -X POST https://api.anthropic.com/v1/claude_code/routines/trig_01ABCDEFGHJKLMNOPQRSTUVW/fire \
  -H "Authorization: Bearer $CLAUDE_ROUTINE_TOKEN" \
  -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"text": "Sentry alert SEN-4521 fired in prod. Stack trace attached."}'
```

</CodeBlock>

A success returns the new session's ID and URL:

```json
{
  "type": "routine_fire",
  "claude_code_session_id": "session_01HJKLMNOPQRSTUVWXYZ",
  "claude_code_session_url": "https://claude.ai/code/session_01HJKLMNOPQRSTUVWXYZ"
}
```

The token is generated after the routine is saved, shown **once**, and cannot be retrieved later — store it in your alerting tool's secret store, and rotate or revoke it from the same modal. The endpoint ships under the `experimental-cc-routine-2026-04-01` beta header while routines are in research preview; breaking changes ship behind new dated header versions, and the two most recent previous versions keep working.

The security detail worth memorising: **`text` does not reach the routine as instructions.** It arrives wrapped in a `<routine-fire-payload>` block labelled as untrusted data, with Claude told not to follow instructions inside it unless the routine's own prompt says to. So a routine that should act on the payload must opt in — "Investigate the alert described in the routine-fire-payload block" — otherwise the text is inert context. The same wrapping applies to text supplied with **Run now**.

**GitHub triggers.** The Claude GitHub App must be installed on the repository, whichever surface you configure from. Two event categories are supported, and within each you pick a specific action or all of them:

| Event        | Triggers when                                                                 |
| ------------ | ----------------------------------------------------------------------------- |
| Pull request | A PR is opened, closed, assigned, labeled, synchronized, or otherwise updated |
| Release      | A release is created, published, edited, or deleted                           |

Pull-request filters narrow which PRs start a session; **all** conditions must match. The fields are author, title, body, base branch, head branch, labels, is-draft and is-merged, each paired with an operator: equals, contains, starts with, is one of, is not one of, or matches regex. `matches regex` tests the **entire** field, so use `.*hotfix.*` to match a title containing `hotfix`, or use `contains` instead.

Claude Code does not reuse sessions across events: two PR updates produce two independent sessions. During the research preview, webhook events are subject to per-routine and per-account hourly caps, and events beyond the limit are dropped until the window resets.

### Repositories, branches and connectors

Each repository is cloned on every run, starting from its default branch unless the prompt says otherwise. Claude pushes to branches prefixed `claude/`, which are always accepted. When your prompt directs a push elsewhere, Claude Code checks first and rejects it if the branch is protected, if someone else has an open PR from it, or if it carries commits authored by someone other than you.

Connectors are the claude.ai integrations on your account — MCP servers you added locally with `claude mcp add` live on your machine and do not appear. All connected connectors are included by default when you create a routine; remove the ones it does not need, because Claude can use every tool from an included connector, **writes included**, without asking during a run. A server declared in a committed `.mcp.json` travels with the clone instead.

The environment controls network access, environment variables and the setup script. The **Default** environment uses **Trusted** access, allowing only the default allowlist; requests to other hosts fail with `403` and `x-deny-reason: host_not_allowed`. Connector traffic routes through Anthropic's servers, so connectors work without allowlist changes.

### Managing routines from the CLI

`/schedule` creates scheduled routines conversationally, and takes a description directly: `/schedule daily PR review at 9am`, or a one-off like `/schedule in 2 weeks, open a cleanup PR that removes the feature flag`. Then `/schedule list`, `/schedule update` and `/schedule run`. You can also ask about history — "why did my nightly review do nothing this morning?" — and Claude lists recent runs with status and links, and reads a run's log to explain tool errors, permission denials and the final result (v2.1.227 or later). Adding a GitHub trigger from the CLI needs v2.1.225 or later; API triggers must be added on the web, since the CLI cannot create or revoke tokens.

If `/schedule` goes missing, the cause is almost always authentication: routines require a claude.ai subscription login. The command menu shows `No commands match "/schedule"` while you type, and submitting it returns `Unknown command: /schedule` — with one exception. Authenticated with a **Console API key**, or with an **Anthropic profile** that has feature-flag fetching enabled, you get a different message instead: `/schedule is available with Claude for Enterprise — ask your admin about migrating from API-key access`. A cloud-provider login such as Bedrock, Google Cloud's Agent Platform or Microsoft Foundry still gives you `Unknown command`. `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `apiKeyHelper` take precedence over a claude.ai login, so remove them first; a profile or federation credential takes precedence too. The remaining causes are being inside a Claude Code on the web session, an organisation policy disabling Claude Code on the web, or an Owner having turned routines off.

### Reading a run

A green status in the run list means the session started and exited without an infrastructure error. **It does not mean the task succeeded.** Blocked network requests, missing connector tools and task-level failures all show up inside the run, not in the status dot. Open the run — it is a full session — to read what Claude actually did.

## Anti-patterns

**A vague prompt.** A routine has no one to ask. "Improve the codebase" produces a different, unreviewable run every night. _Fix:_ write a self-contained prompt that states the task, the evidence of success, and what must not change.

**Leaving every connector attached.** Every included connector's tools — writes included — are available with no approval during the run. _Fix:_ remove the ones the routine does not need, at creation and at every edit.

**Trusting the green status.** A run that started and exited cleanly still shows green after a blocked network call did nothing useful. _Fix:_ open the run and read the transcript before you believe it.

**Treating fire text as instructions.** Anyone holding the bearer token can send `text`. If your prompt is written to "do what the payload says", a leaked token is a remote-code-execution primitive. _Fix:_ keep the routine's own prompt authoritative and reference the payload as data to investigate.

**Posting on success.** A routine that reports "all good" every night trains the whole team to ignore it, so the one night it says something real gets ignored too. _Fix:_ stay silent when there is nothing to report.

**Expecting sub-hourly schedules.** The minimum interval is one hour, and more frequent expressions are rejected. _Fix:_ use `/loop` inside a session, a desktop task, or a CI schedule for anything faster.
