## Objectives & prerequisites

By the end of this lesson you can:

- Run a multi-phase workflow end to end against a real repository, headlessly and reproducibly.
- Design a pipeline whose middle phase is a cheap, read-only gate between "an agent thinks there is a bug" and "an agent edited the file".
- Prove from the run's own artefacts — the journal, the persisted script, the JSON envelope — how many agents ran, which ran together, and what it cost.
- Decide, from evidence, whether the extra phase paid for itself.

**Prerequisites.** Lessons `01-workflows` and `02-ultracode`. A clone of the lab repository and Node 24. The lab runs headlessly, so nothing here needs an interactive terminal.

<WhenNotToUse>
  This pipeline shape earns its cost when a false positive would be expensive — an unwanted edit, a
  wrong fix committed on a Friday — and when the review can be split into independent lenses. It is
  the wrong shape for a change you already understand (just make it), for a repo whose test suite
  already tells you the answer in three seconds, and for anything where you want to inspect each
  stage before the next: a workflow takes no input once it starts, so a pipeline that needs your
  sign-off between review and fix should be two workflows, not one.
</WhenNotToUse>

## Concept

### Why three phases and not one

A single "review and fix this file" agent conflates two failure modes. A false-positive finding
becomes a real, unwanted code change; and there is no checkpoint between the model's opinion and the
edit. Splitting **review** from **verify** inserts a cheap, read-only gate: the verifier re-reads the
actual file, rather than trusting the reviewer's description of it, and only findings that survive
reach a phase that can write anything.

The pipeline you build here:

1. **Review** (read-only). One agent reads `src/store.ts`, lists candidate correctness bugs, each
   with a stable id, a `file:line` pointer and a one-line summary. It answers into a JSON schema, so
   the next phase gets fields, not prose.
2. **Verify** (read-only, independent, in parallel). Two agents receive the same candidate list and
   independently re-check each one against the file and `BUGS.md`, returning `confirmed` or
   `rejected` with a reason. Two verifiers, not one, so a single agent's misreading does not decide.
3. **Fix** (write access, scoped). Only findings both verifiers confirmed reach it; it applies the
   minimal change, runs `npm test` and `npm run typecheck` after each one, and stops if either goes
   red.

The lab runs phases 1 and 2 for real, read-only, and leaves phase 3 as a scoped extension — which is
also the honest ordering: run the read-only slice first, look at what it costs and what it found,
then decide whether to give an agent write access.

### The shape of the script

Claude writes the script; you describe the task. The script it wrote for this exact task is the one
`01-workflows` dissected — `phase('Find')`, one `agent()` with a findings schema, then
`phase('Verify')` and a `parallel([...])` of two schema-shaped verifier agents, with the confirmed
set computed by intersecting the two verdict maps in plain JavaScript. Note where the intersection
happens: **in the script**, not in an agent. Consensus logic is exactly the kind of thing that should
be code you can read, not a judgement you have to trust.

The one worked example prompt for this lesson is the one the lab runs:

```text
Use a workflow with exactly 3 agents to review src/store.ts in this repo for
correctness bugs: one agent lists candidate findings with file:line pointers,
then two agents independently verify each candidate against the file and
BUGS.md and mark it confirmed or rejected. Do not edit any file. Wait for the
workflow to finish and report the confirmed findings only.
```

Three constraints in that prompt do real work: **exactly 3 agents** bounds the run, **do not edit any
file** keeps the whole thing read-only, and **wait for the workflow to finish** asks the session to
report the finished result — a workflow runs in the background by design, so say what you want back.

Four things in those recordings deserve a second look.

**The journal is the proof, not the summary.** Six lines, three agent ids: one `started`/`result`
pair for the finder, then two `started` lines back to back — the parallel verifiers — and their two
results. A model's claim that it "ran three agents" is not evidence; this file is.

**`subagent_stats.spawned` is 0.** The envelope's subagent counters stayed empty even though three
agents did the work. The docs do not describe how workflow agents appear in those counters, so take
this as an observation from this run rather than a documented rule — but a useful one: if you are
asserting in CI that delegation happened, assert on the run directory and the journal, not on
`subagent_stats`.

**`modelUsage` lists two models.** The session ran with `--model sonnet`, and the envelope recorded
usage under both `claude-sonnet-5` and `claude-fable-5-1` for a total of $0.94 against $0.03 for the
plain headless question in `02-ultracode`. The Agent SDK reference says `modelUsage` carries per-model
totals for every model call made through the query pipeline, "including the main loop, subagents, and
internal calls such as compaction and Workflow agents", and `workflows.md` says workflow agents follow
the same model-selection order as subagents; which stage of this run used the second model is not
something the envelope alone tells you. Read it as: orchestration is not free, and its cost is not all on the model you
named.

**The report came back in Turkish.** The machine that produced this recording has global Claude Code
preferences asking for Turkish answers, and a workflow's final report is written by your session like
any other answer. The finding itself is right — `src/store.ts:63`, both verifiers `confirmed`, cross
-checked against `BUGS.md`'s B1 — but the language is a reminder that your standing memory reaches
into orchestrated runs too.

### Extending it to a fix phase

Once the read-only slice does what you expect, add the third phase — deliberately, and scoped:

<CodeBlock title="the fix phase, added to the prompt">

```text
...then, for each confirmed finding only, apply the minimal fix to the file
named in that finding, run npm test and npm run typecheck after each change,
and stop immediately if either goes red.
```

</CodeBlock>

Give the run `--permission-mode acceptEdits` and add `Edit`, `Bash(npm test)` and
`Bash(npm run typecheck)` to `--allowedTools`.
Two rules keep it safe: the fix agent may only touch the files named in confirmed findings, and a red
suite stops the pipeline rather than triggering a fix-the-fix loop. If you would not let a colleague
push the change unreviewed, do not let phase 3 run unattended either.

## Anti-patterns

**A verifier that rubber-stamps.** If every finding comes back `confirmed`, the phase is decoration.
_Fix:_ make the verifier re-read the file at the given line rather than judging the reviewer's
description, and check its verdicts against a case you know is not a bug.

**One verifier.** A single second opinion that agrees with the first is the same opinion twice when
both read the same prose. _Fix:_ two independent verifiers, and compute the intersection in the
script.

**A fix phase with unscoped tools.** An agent with `Edit` and no boundary wanders into files nobody
reviewed. _Fix:_ scope the tools, and name the files it may touch in the finding it is acting on.

**No stop condition.** A pipeline that keeps fixing after the suite goes red will happily fix its own
fix. _Fix:_ stop on red and hand it back to a person.

**Believing the summary over the artefacts.** The final report is a model's account of the run.
_Fix:_ read `journal.jsonl`, the persisted script and `git status` — all three exist precisely so you
do not have to take the summary's word.

<Callout variant="changed">
  In `claude -p` there is never a workflow approval dialog; the run starts only if the `Workflow`
  call passes ordinary permission evaluation. That is why the lab passes `--allowedTools
  "Workflow,Read,Grep,Glob"` — an allow rule naming `Workflow` approves every workflow, and
  `Workflow(<name>)` approves one saved workflow by name. Verified against `workflows.md` for 2.1.263.
</Callout>
