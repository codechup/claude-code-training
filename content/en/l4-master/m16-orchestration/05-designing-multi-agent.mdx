## Objectives & prerequisites

By the end of this lesson you can:

- Pick between a subagent, a skill, an agent team and a workflow for a given task, and defend the choice in one sentence.
- Write a role as a job plus an output shape, and say why the shape is the contract.
- Decide what belongs in a prompt and what belongs in the script.
- Name the failure modes that only appear with several agents — rubber-stamping, unscoped writes, replay cost, non-determinism, coordination overhead — and the design that prevents each.
- Size a run: how many agents, how big a task, and where the human sign-off goes.

**Prerequisites.** Lessons `01-workflows` through `04-pipeline-lab`. This lesson has no new API in it: it is about the decisions you make before you write the prompt.

<WhenNotToUse>
  Do not design a pipeline for a problem you have not yet solved once by hand. Orchestration
  multiplies whatever your process already is: if the review criteria are vague, five agents produce
  five vague reviews and a synthesis that averages them. And do not orchestrate to feel thorough —
  more agents means more tokens, more coordination and more surface for one bad hand-off to poison
  the result. A single well-prompted session with a test suite beats a badly designed team every
  time.
</WhenNotToUse>

## Concept

### Choose the primitive first

Four mechanisms can run a multi-step task, and the deciding question is who holds the plan and where
intermediate results live.

- **Subagent** — a worker Claude spawns for a side task whose intermediate output you never want to
  see. Cheapest. Choose it when only the result matters.
- **Skill** — instructions Claude follows in its own context. Choose it when the work is a procedure,
  not a fan-out.
- **Agent team** — peer sessions with a shared task list, supervised by a lead, able to challenge
  each other. Choose it when the value comes from discussion between the workers — competing
  hypotheses, cross-layer work — and you are willing to pay for it.
- **Workflow** — a script the runtime executes, holding the loop, the branching and the intermediate
  results. Choose it when the same step runs across many items, when the orchestration itself should
  be repeatable, or when you want a quality pattern (cross-checking, adversarial review) applied the
  same way every time.

A blunt heuristic that follows from the docs' own numbers: a handful of long-running peers is a team;
dozens to hundreds of agents per run is a workflow; a few delegated tasks per turn is a subagent.

### A role is a job plus an output shape

The pipeline in `04-pipeline-lab` has three roles, and each one is a single job:

| Role   | Job                                              | Sees                         | May write            | Returns                                                |
| ------ | ------------------------------------------------ | ---------------------------- | -------------------- | ------------------------------------------------------ |
| Review | Find candidate correctness bugs                  | The file, `BUGS.md`          | Nothing              | `{ findings: [{ id, file, line, summary, details }] }` |
| Verify | Re-check each candidate independently            | The candidate list, the file | Nothing              | `{ verdicts: [{ id, verdict, reason }] }`              |
| Fix    | Apply the minimal change for a confirmed finding | The confirmed findings       | Only the named files | The change plus a test result                          |

The `schema` on an `agent()` call is not decoration: it is the **contract** between stages. Prose
hand-offs force the next agent to re-derive structure before it can act, and a re-derivation is a
place to be wrong. A stable `id` field matters as much as the rest — it is what lets a downstream
stage join two agents' answers together without matching on text.

Note what the roles do _not_ share: the verifier does not receive the reviewer's reasoning as
authority, only its claims. Independence is the whole point of the phase.

### Put the decisions in the script

Once two agents have answered, something has to decide what "both agreed" means. That belongs in the
script, in plain JavaScript, where you can read it, diff it between runs and rerun it — not in a
fourth agent's judgement. The generated script from the lab does exactly this, intersecting the two
verdict maps and passing on only the findings both marked `confirmed`.

The general rule: **agents for judgement that needs a model, code for logic that does not.**
Filtering, joining, counting, thresholding, deduplicating and ordering are code. Reading a file and
forming an opinion about it is an agent.

The runtime pushes you the same way. A script cannot touch the filesystem or the shell, cannot load
modules, and cannot call `Date.now()`, `Math.random()` or a no-argument `new Date()` — those throw,
so that a relaunched run repeats the same `agent()` calls. Determinism in the orchestration is a
feature: it is what makes a resumed run replay rather than re-guess.

### Design the hand-offs, and the failures

Every hand-off is a place where a run quietly goes wrong. The five that matter:

**Rubber-stamping.** A verifier that reads the reviewer's description instead of the file confirms
everything. _Design against it:_ give the verifier the pointer, not the argument; make it re-read;
and run a control case you know is clean.

**Unscoped writes.** A fix agent with `Edit` and no boundary edits files nobody reviewed. _Design
against it:_ scope tools per role, name the files in the finding, and stop on a red test rather than
letting a fix-the-fix loop start.

**Replay cost.** When an agent fails mid-fan-out, relaunching returns the completed agents _before_
it from cache but reruns it and everything that started after it — so a failure at the front of a
wide fan-out is expensive. _Design against it:_ keep fan-outs of expensive agents narrow, put cheap
discovery first, and let `agent()`'s `null` result be handled (`pipeline()` keeps the `null` in the
array) rather than crashing the script.

**Coordination overhead.** For teams, the docs are concrete: start with 3–5 teammates, aim for 5–6
tasks each, and expect diminishing returns — three focused teammates often outperform five scattered
ones. Two teammates editing the same file overwrite each other; nothing arbitrates. _Design against
it:_ disjoint file ownership, and self-contained tasks that produce a clear deliverable.

**No place for a human.** A workflow takes no input once it starts. If a stage genuinely needs your
sign-off, it is a boundary between two workflows, not a phase inside one.

### Sizing and cost, deliberately

Set a size guideline (`small` is fewer than 5 agents, `medium` fewer than 15, `large` fewer than 50)
and remember it is advice to Claude, not a cap; the runtime's caps — 16 concurrent agents, 4,096
items per `parallel()`/`pipeline()` call, 1,000 agents per run — are the real ceiling. Run a small
slice first: one directory, one narrow question. Ask for a smaller model on stages that do not need
the strongest one, since workflow agents follow the same model-selection order as subagents.

One efficiency detail worth designing for: agents in the same run can read each other's prompt cache
when they match on model, effort level, agent type, tools, output schema and working directory. In a
fan-out, Claude Code holds all but the first agent until the first response begins — capped by
`CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`, 5,000 ms by default — so the rest read the cached prefix.
Practically: **make the agents in one fan-out identical except for their input.** Ten agents with ten
different tool lists throw that away.

## Anti-patterns

**Roles that overlap.** "Reviewer" and "second reviewer" with the same prompt produce correlated
opinions and cost twice as much. _Fix:_ give each role a different lens (security, performance, test
coverage) or a different job (find, verify, fix) — never the same job twice.

**A synthesis agent that is really a filter.** Spawning an agent to merge two lists is paying a
context window for an intersection. _Fix:_ merge in the script; use an agent for synthesis only when
it must weigh, rank or explain.

**Prompts that carry structure.** "Report findings as a numbered list" is a schema written in the
weakest possible way. _Fix:_ pass a `schema` and let the runtime enforce the shape.

**A fan-out of heterogeneous agents.** Different tools, models or schemas per agent throw away the
shared prompt-cache prefix and pay for the same preamble many times. _Fix:_ keep a fan-out uniform;
vary the input, not the configuration.

**Designing for the happy path.** Agents fail, get stopped, and hit API errors; `agent()` then
resolves to `null`, and a relaunch reruns everything downstream of the failure. _Fix:_ handle `null`,
keep expensive fan-outs narrow, and put cheap stages first.

**Orchestrating away a missing checkpoint.** If what you actually want is to look at the findings
before anything is changed, no amount of phases inside one workflow gives you that. _Fix:_ two
workflows, with you in between.

<Callout variant="changed">
  Agent teams are experimental and off by default (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), and
  they cannot be nested — teammates cannot spawn teammates, and only the lead manages the team. Any
  design you read from 2025-era material that assumes explicit team creation is out of date: the
  `TeamCreate`/`TeamDelete` tools no longer exist as of 2.1.178.
</Callout>
