## Objectives & prerequisites

By the end of this lesson you can:

- Say what a dynamic workflow is in one sentence, and name the one thing that separates it from subagents, skills and agent teams: who holds the plan.
- Read a generated workflow script and point at `export const meta`, `phase()`, `agent()`, `parallel()`, `pipeline()`, `log()` and the JSON schema that shapes an agent's answer.
- Explain where a run's script and per-agent logs are written, and open them yourself.
- List the runtime's hard limits — concurrency, list size, agent cap — and the three things a script may not do.
- Get a workflow to start in a headless run by allowing the `Workflow` tool.

**Prerequisites.** Subagents (L3 `m10-subagents`) — a workflow orchestrates them, so the worker primitive should already be familiar. Headless mode (L3 `m13-headless-ci`) for the lab's `claude -p` capture. Dynamic workflows are available on all paid plans, with Anthropic API access, and on Amazon Bedrock, Google Cloud's Agent Platform and Microsoft Foundry; on Pro, turn them on from the **Dynamic workflows** row in `/config`.

<WhenNotToUse>
  A workflow is a batch job: it takes no input once it starts, and only an agent's permission prompt
  can pause it. So do not reach for one when you want to steer as the work happens, when a stage
  needs your sign-off before the next begins (run each stage as its own workflow instead), or when
  the task is small enough that one conversation can hold it — the orchestration itself costs
  agents, tokens and wall-clock time that a single delegated subagent does not. And do not use one
  to get a job done "in parallel" that is actually sequential: a script that runs one agent, waits,
  then runs the next has bought you a file you can rerun, not speed.
</WhenNotToUse>

## Concept

### Who holds the plan

Subagents, skills, agent teams and workflows can all run a multi-step task. The official comparison
turns on one question — who decides what runs next:

|                                 | Subagents                      | Skills                       | Agent teams                            | Workflows                            |
| ------------------------------- | ------------------------------ | ---------------------------- | -------------------------------------- | ------------------------------------ |
| What it is                      | A worker Claude spawns         | Instructions Claude follows  | A lead agent supervising peer sessions | A script the runtime executes        |
| Who decides what runs next      | Claude, turn by turn           | Claude, following the prompt | The lead agent, turn by turn           | The script                           |
| Where intermediate results live | Claude's context window        | Claude's context window      | A shared task list                     | Script variables                     |
| What's repeatable               | The worker definition          | The instructions             | The team definition                    | The orchestration itself             |
| Scale                           | A few delegated tasks per turn | Same as subagents            | A handful of long-running peers        | Dozens to hundreds of agents per run |
| Interruption                    | Restarts the turn              | Restarts the turn            | Teammates keep running                 | Resumable in the same session        |

A workflow **moves the plan into code**. With the other three, Claude is the orchestrator and every
intermediate result lands in a context window. A workflow script holds the loop, the branching and
the intermediate results itself, so Claude's context holds only the final answer. That is also what
makes a repeatable quality pattern possible: independent agents can adversarially review each
other's findings before anything is reported, which is the shape you will build in `04-pipeline-lab`.

The one worked example prompt for this lesson — you describe the task, never the script:

```text
use a workflow to review every file changed in this PR for correctness issues,
then merge the per-file findings into one ranked summary
```

### Three ways a workflow starts

1. **A bundled or saved command.** `/deep-research <question>` ships with Claude Code: it fans web
   searches across several angles, cross-checks the sources, votes on each claim and returns a cited
   report with claims that did not survive filtered out. It needs the `WebSearch` tool available,
   and it runs only when you invoke it. Workflows you save yourself become commands the same way.
2. **You ask, in a prompt you type.** Include the keyword `ultracode`, or ask in your own words
   ("use a workflow"), and Claude writes a script for that one task. Lesson `02-ultracode` covers
   the keyword's rules — including the routes where it deliberately does not fire.
3. **`ultracode` effort.** `/effort ultracode` makes Claude plan a workflow for every substantive
   task in the session. Also lesson 02.

### The script

The file Claude writes is plain JavaScript with top-level `await`: a `meta` block first, then a body
that orchestrates subagents. You rarely edit it, but you should be able to read it. Here is the
first half of a real one, generated for this lesson's lab:

`export const meta` must be the first statement and a plain object literal with a `name` and a
`description`; an optional `phases` array groups agents under named stages in the progress view. If
`meta` contains anything but literal values — a variable, a call, a spread — Claude Code drops the
workflow from `/` autocomplete.

The body has five calls and one global:

| Call                     | What it does                                                                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `agent(prompt, options)` | Spawns one subagent and resolves to its result. `schema` shapes that result as JSON; `label` and `phase` place it in the progress view |
| `pipeline(items, fn)`    | Runs one agent per item in a list                                                                                                      |
| `parallel([...])`        | Runs a set of agent tasks at the same time and waits for all of them                                                                   |
| `phase(title)`           | Groups the agents that follow under a title in the progress view                                                                       |
| `log(message)`           | Shows a message above the phases                                                                                                       |
| `args`                   | The input passed to a saved workflow, as a real value — `undefined` when none was passed                                               |

Two details in that snippet are worth naming. The **schema is the contract** between stages: the
verifiers are handed a list built from the finder's structured answer, not from its prose, so a
downstream stage can rely on the fields being there. And an `agent()` call resolves to `null` if you
stop it mid-run or it hits an unrecoverable API error — `pipeline()` keeps that `null` in the
results array, which is why generated scripts so often end with `.filter(Boolean)`.

### How a run executes

The runtime executes the script in an isolated environment, separate from your conversation, in the
background — your session stays responsive. Every run writes its script to a file under your
session's directory in `~/.claude/projects/`, and Claude receives the path, so you can ask for it:

<Transcript
  src="content/_shared/transcripts/m16-orchestration/01-workflows/02-run-dir.txt"
  range="2-27"
/>

That listing is from a real three-agent run: the script under `workflows/scripts/`, the run's own
JSON beside it, and under `subagents/workflows/<run-id>/` a `journal.jsonl` plus one transcript and
one metadata file per agent. Claude can only start a workflow from a script file the session is
already allowed to read — for a script kept outside your working directory, add its directory with
`/add-dir` or a Read allow rule first.

While a run is going, `/workflows` lists running and completed runs; select one and press Enter for
its progress view, which shows each phase with agent counts, token totals and elapsed time. `p`
pauses or resumes, `x` stops the selected agent (or the whole run), `r` restarts a running agent, and
`s` saves the run's script as a command.

### Limits the runtime enforces

| Constraint                                                                     | Why                                                                                                            |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| No mid-run user input                                                          | Only agent permission prompts can pause a run. For sign-off between stages, run each stage as its own workflow |
| No direct filesystem or shell access from the script                           | Agents read, write and run commands; the script coordinates agents                                             |
| No module loading — a script containing `import()` fails before the run starts | The body is plain JavaScript. Work that needs a library goes inside an agent's task                            |
| Up to 16 concurrent agents, fewer with fewer CPUs available                    | Bounds local resource use                                                                                      |
| Up to 4,096 items in a single `parallel()` or `pipeline()` call                | A silent cap would drop part of the workload                                                                   |
| 1,000 agents total per run                                                     | Prevents runaway loops                                                                                         |

`Date.now()`, `Math.random()` and a no-argument `new Date()` all **throw** inside a script, so that a
relaunched run repeats the same `agent()` calls. Pass a timestamp in through `args` instead.

### Saving, sharing and permissions

Press `s` on a run in `/workflows` to save its script as a command, in `.claude/workflows/` (shared
with everyone who clones the repo) or `~/.claude/workflows/` (yours, in every project). It then runs
as `/<name>`; if a project and a personal workflow share a name, the project one wins. To share
across teams, put the script in a plugin's `workflows/` directory — a plugin called `acme-tools`
with a script whose `meta.name` is `release-audit` runs as `/acme-tools:release-audit`. Before you
edit a saved script, run the `/workflow-authoring` bundled skill, which loads the script-writing
reference Claude works from (Claude Code 2.1.248 or later), and `/reload-skills` to pick the edited
version up in the current session.

In the CLI, Claude Code asks before a run starts — showing the planned phases, with **Yes, run it**,
a per-workflow "don't ask again", **View raw script** and **No**. In `claude -p` and the Agent SDK
there is no prompt at all: the `Workflow` call goes through ordinary permission evaluation, so a run
starts only if something approves it. `Workflow` in your allow rules approves every workflow, and
`Workflow(<name>)` approves one saved workflow by name. That is exactly what the lab does.

## Anti-patterns

**Writing the script yourself first.** The workflow is Claude's output, not your input: you describe
the task and the runtime persists the script it wrote. _Fix:_ describe the task, let the run happen,
then save or edit the script it produced — that is the supported iteration loop, and
`/workflow-authoring` exists for the editing half.

**Passing prose between stages.** A verifier that reads a previous agent's paragraph has to
re-derive the structure before it can check anything. _Fix:_ give the producing `agent()` call a
`schema`, and build the next stage's input from the fields.

**Assuming a workflow started because you asked.** In `claude -p` and the SDK there is no approval
dialog; without an allow rule the `Workflow` call is just another tool call that can be denied, and
Claude will quietly do the task turn by turn instead. _Fix:_ check `permission_denials` and whether
the run actually produced a script directory, rather than trusting the summary.

**Expecting to steer mid-run.** There is no mid-run user input, and a stopped agent counts as
failed, so relaunching reruns it and everything that started after it. _Fix:_ split a process that
needs your sign-off into one workflow per stage.

**Reaching for timestamps or randomness in the script.** They throw, on purpose — a relaunch has to
replay the same `agent()` calls. _Fix:_ pass the value in through `args`.
