## Objectives & prerequisites

By the end of this lesson you can:

- Explain why a written plan file, rather than a conversation, is what lets several independent sessions work one project.
- Name every required key in a plan file's YAML frontmatter and say what each one is for.
- List the ten fixed body sections in order, and say which question each one answers for a session that has never seen the project before.
- Use milestones and `depends_on` to express the order work must happen in, without hand-scheduling anybody.
- Read a real plan file with `node tools/plan/cli.ts show PNN` and tell, from its frontmatter alone, whether you are allowed to claim it.

**Prerequisites.** Level 3, and comfort with git and YAML. This module is taught on this website's own repository — every command below was run against a throwaway clone of `codechup/claude-code-training`, which is public, so you can clone it and follow along.

<WhenNotToUse>
  A plan system is overhead, and overhead only pays when several sessions execute work nobody is
  watching turn by turn. Skip it when one person drives one session at a time: a conversation, plan
  mode and a checklist are lighter and lose nothing. Skip it for work whose shape you do not know
  yet — exploration cannot be written as a work order, so explore first and write the plan
  afterwards. And skip it when the work is small enough to describe in a sentence: a plan file that
  takes longer to write than the change it orders is a tax, not a tool. The threshold to watch for
  is not project size but the number of contexts: the moment a second session has to pick up work
  the first one started, everything the first session knew and did not write down is gone.
</WhenNotToUse>

## Concept

### Why the plan is a file

Claude Code's own guidance is to separate planning from implementation, and to make the artefact a written one: "have Claude interview you first … then write a complete spec to `SPEC.md`", after which "start a fresh session to execute it. The new session has clean context focused entirely on implementation, and you have a written spec to reference." The docs describe the most useful specs as **self-contained**: "they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works."

Scale that idea from one spec to a whole project and you get a plan system. This repository has 48 of those specs under `plans/`, one per unit of work, and the rule that makes them work is the rule the docs already imply: a session resumes **from repository state alone**. Nothing that matters lives in a chat log, in someone's memory, or in a message between two people.

That rule is what makes the plans parallel-safe. The official comparison of parallel approaches puts it plainly — worktrees give each session a separate checkout, cross-session messaging lets sessions pass findings, and agent teams need you to "partition the work so each teammate owns a different set of files". A plan file is where that partition is written down.

Here is the prompt this lesson is built around. Notice that it never explains the project: everything the session needs is already on disk.

```text
Read STATE.md and plans/P33-l4-m16-orchestration.md. If you were the session
claiming P33, what would you do first, and which files may you not touch?
```

### The frontmatter

Every plan file is `plans/PNN-slug.md` and opens with YAML frontmatter. These keys are required:

| Key              | What it carries                                                |
| ---------------- | -------------------------------------------------------------- |
| `id`             | `PNN` — must equal the file's prefix                           |
| `title`          | One line, reused as the PR title `[PNN] <title>`               |
| `milestone`      | `M0`–`M4` — which wave of the project this belongs to          |
| `status`         | `todo`, `in_progress`, `blocked`, `review` or `done`           |
| `owner`          | `null`, or the free-form name of the session holding the claim |
| `branch`         | `plan/NN-slug` — the branch this plan's work happens on        |
| `model_hint`     | `haiku`, `sonnet`, `opus` or `fable` — advice, not a gate      |
| `effort_hint`    | `low`, `medium`, `high`, `xhigh` or `max`                      |
| `depends_on`     | Plan ids that must be `done` before this one may be claimed    |
| `owned_paths`    | The globs this plan may create or modify — and nothing else    |
| `shared_paths`   | Files it may touch append-only, with care                      |
| `estimate`       | `S` (≤ half a day), `M` (≤ a day), `L` (≤ two days)            |
| `updated_at`     | RFC3339 UTC, bumped by every status change                     |
| `open_questions` | Doc conflicts and product questions for the owner              |

Two of those keys do the real coordination work. `depends_on` must form a directed acyclic graph, so "what can start now" is computable rather than negotiated. `owned_paths` is never empty, and the tool refuses to let two active plans own overlapping paths — which is the subject of lesson 03.

`updated_at` is set by the tool, not by hand. So is `status`. A plan file you edit by hand in those fields is a plan file that lies to the generator.

### The ten sections

The body is fixed, in this order, and no section is dropped:

1. **Goal** — one paragraph: what exists when this is done, and why that matters.
2. **Context** — what to read _before_ working: doc paths, section names, the decisions this plan leans on, and what already exists in the repo.
3. **Scope** — an `In:` list and an `Out:` list. The `Out:` list is the one that prevents scope creep.
4. **Deliverables** — the exact files and directories to create or change.
5. **Acceptance criteria** — testable bullets, each naming the command to run and the expected result.
6. **Steps** — ordered and concrete.
7. **Tests required** — the named suites that must exist and pass.
8. **Non-goals / pitfalls** — what a low-effort session must not do.
9. **Verification** — how a reviewer checks the result in under ten minutes.
10. **Handoff notes** — filled in by the executing session at the end. Lesson 05 is entirely about this one.

Read that list as a set of questions a stranger would otherwise have to ask you: _What am I building? What should I read first? What is out of scope? How will I know it worked? What must I not touch? What did the last session learn?_ Every question you leave unanswered is a question that becomes a message, and every message needs somebody awake to answer it.

The sections are also mechanically checkable, which is why the CLI can print them:

<CodeBlock title="Read a plan's frontmatter and section headings">

```bash
node tools/plan/cli.ts show P13
```

</CodeBlock>

### Milestones and dependencies

`milestone` groups plans into waves — in this repository, `M0` is infrastructure and design, `M1` the first English levels, `M2` the parallel Turkish and Advanced/Master wave, `M3` the rest, `M4` launch hardening. Milestones are for humans reading progress; `depends_on` is for the tool deciding what is claimable.

Keep them honest and they answer two different questions. The milestone table tells you how far along the project is. The dependency graph tells you what a session may start right now. Neither is a schedule, and neither names a person.

<Callout>
  A plan file is not a ticket. A ticket says what someone wants; a plan file says what a session
  should read, build, prove and avoid, in enough detail that nobody has to be online to answer a
  follow-up question. If your plan file would leave a competent stranger with a question, that
  question is the missing section.
</Callout>

## Anti-patterns

**A plan that describes the outcome but not the reading list.** Without `Context`, every session rediscovers the same five documents, differently. _Fix:_ name the exact files and section headings, and say why each one matters.

**No `Out:` list.** Scope stated only as `In:` invites a session to "just also" fix the adjacent thing, which puts it in another plan's files. _Fix:_ write the `Out:` list first; it is usually easier and it is what a reviewer checks.

**Acceptance criteria that cannot fail.** "The lesson is good" is not testable. _Fix:_ name the command and the expected output — the docs' own rule is to give the agent a check it can run, because "without a check it can run, 'looks done' is the only signal available."

**Hand-editing `status`, `owner` or `updated_at`.** The generator derives project state from those fields; edit them by hand and the derived view is wrong for everyone else. _Fix:_ go through `node tools/plan/cli.ts claim` / `status`.

**Guessing a product decision because the plan was vague.** A plan that forces a guess is a broken plan, and the guess becomes an unrecorded decision the next session cannot see. _Fix:_ write the question into `open_questions` and take the most conservative reading.

**Empty `owned_paths`.** A plan that owns nothing owns everything, which is how two sessions end up editing one file. _Fix:_ the tool rejects it — keep it that way.
