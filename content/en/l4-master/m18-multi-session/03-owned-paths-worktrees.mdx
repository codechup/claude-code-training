## Objectives & prerequisites

By the end of this lesson you can:

- Partition a project into disjoint `owned_paths` and explain why prefix overlap, not exact equality, is the test that matters.
- Predict what the plan tool does when two plans claim the same path — at claim time and at check time — and read both refusals.
- Create one git worktree per plan and run several Claude Code sessions in them without their edits colliding.
- Choose between a worktree you create with git, Claude Code's `--worktree` flag, and a subagent with `isolation: worktree`.
- Apply the append-only rules to files no single plan can own, and know when a needed file means the plan is wrong rather than the rule.

**Prerequisites.** Lessons 01 and 02 of this module, and working knowledge of `git worktree`.

<WhenNotToUse>
  Isolation costs disk, setup and attention: every worktree is a fresh checkout that needs its own
  dependency install, and a session in one cannot see the work in another until it lands on a
  branch. Do not reach for it when the sessions are reading rather than writing — several read-only
  sessions in one checkout collide with nothing. Do not use it to paper over a partition you have
  not actually made: two sessions editing the same file in two worktrees produce a merge conflict
  instead of a lost edit, which is better but still a failure of planning. And do not isolate work
  that must see each other's changes as they happen; that is one session, or a pipeline, not two.
</WhenNotToUse>

## Concept

### Partition first, isolate second

The docs are direct about the ordering. Under "Do the tasks touch the same files?" the parallel-agents page says to isolate the work with worktrees — but for agent teams, which do not isolate teammates, it says to "partition the work so each teammate owns a different set of files."

Partitioning is the real move. A worktree stops one session's edit from overwriting another's; it does not stop two sessions from independently deciding to rewrite the same function in two branches, which you discover at merge time. `owned_paths` is where the partition is written down, before either session starts.

In this repository, one content plan owns three globs and nothing else:

<CodeBlock title="plans/P35-l4-m18-multi-session.md (excerpt)">

```yaml
owned_paths:
  - content/en/l4-master/m18-multi-session/**
  - content/tr/l4-master/m18-multi-session/**
  - content/_shared/transcripts/m18-multi-session/**
shared_paths:
  - content/_shared/sources.json
```

</CodeBlock>


### Overlap is computed on prefixes

Two globs overlap when the static part of one — everything before the first wildcard — is a prefix of the other's. So `content/en/l1-beginner/**` overlaps `content/en/l1-beginner/m01-start/runtime.test.ts`, while `content/en/l1-beginner/**` and `content/en/l2-intermediate/**` do not.

That definition is conservative on purpose: it flags a parent-and-child pair as a conflict even though a careful human might argue they could coexist. In a system where nobody is watching, "might be fine" is not a property you want to depend on.

### One worktree per plan

A git worktree is a separate working directory with its own files and branch that shares the repository's history and remote with your main checkout. This project's convention is one worktree per plan, in a sibling directory named after the plan number:

<CodeBlock title="Create a worktree for a claimed plan">

```bash
git worktree add ../cct-wt-35 plan/35-l4-m18-multi-session
cd ../cct-wt-35
npm ci
```

</CodeBlock>

Each worktree has its own `node_modules` — a worktree is a fresh checkout, so its development environment has to be initialised there. When the plan's pull request is merged, the worktree goes away:

<CodeBlock title="Clean up after the merge">

```bash
git worktree list
git worktree remove ../cct-wt-35
```

</CodeBlock>

The important social rule has no technical enforcement: **never `cd` into another plan's worktree to borrow a file.** If you need something from it, your plan's `depends_on` is missing that plan — and that belongs in your Handoff notes, not in a copied file.

### Three kinds of isolation

Git worktrees are one of three ways to get an isolated checkout, and they are not interchangeable.

| Mechanism                                         | What it isolates                            | Reach for it when                                                                        |
| ------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `git worktree add <dir> <branch>`                 | A checkout you create and manage yourself   | You want a long-lived, named workspace per plan, on a branch you push and open a PR from |
| `claude --worktree <name>` (`-w`)                 | A session Claude Code creates and cleans up | You want one isolated session now and do not care where the directory lives              |
| `isolation: worktree` in a subagent's frontmatter | A temporary checkout for one subagent       | A delegated agent will edit many files and must not touch the parent session's tree      |

`claude --worktree feature-auth` creates the worktree under `.claude/worktrees/<name>/` at the repository root, on a new branch named `worktree-<name>`, and starts Claude in it; omit the name and Claude Code generates one. The docs suggest adding `.claude/worktrees/` to `.gitignore`. New worktrees branch from the repository's default branch unless you set `worktree.baseRef` to `"head"`, and a `.worktreeinclude` file (using `.gitignore` syntax) copies gitignored files such as `.env` into each new worktree.

You can also ask Claude to work in a worktree mid-session, and it creates one with the `EnterWorktree` tool; `ExitWorktree` leaves it. Entering a path outside the repository's `.claude/worktrees/` directory always asks for your approval first, "because the move takes the session's working directory, write access, and project configuration such as `CLAUDE.md` and settings to that location" — and the docs are explicit that a permission rule or "don't ask again" does not suppress that prompt; only `bypassPermissions` mode skips it.

While a session is isolated, Claude Code enforces the boundary rather than trusting it. It blocks an `Edit`, `Write` or `NotebookEdit` targeting the main checkout; blocks a Bash, PowerShell or Monitor command whose working directory resolves to the main checkout; blocks git redirected back into the main checkout through `git -C`, `--git-dir`, `GIT_DIR`, `GIT_WORK_TREE` or a `cd`; and blocks a command whose shape it cannot verify, telling Claude how to rewrite it.

For a subagent, `isolation: worktree` in the agent's frontmatter gives it "a temporary git worktree … branched by default from your default branch rather than the parent session's `HEAD`", cleaned up automatically when the subagent makes no changes.

<Callout>
  A worktree is not a sandbox. It isolates *files in this repository*; it does not restrict the
  network, other directories, or anything outside the checkout. If you need those limits too, that
  is sandboxing and permissions, which Level 3 covers.
</Callout>

### The files nobody can own

Some files are touched by many plans: a shared source registry, a lockfile, a translations map. They are listed under `shared_paths` and they follow different rules — **append-only, minimal diff**:

- Never reformat or reorder existing content; add your entry and leave everything else byte-identical.
- One logical hunk per shared file, per plan.
- Mention each shared-file change in the pull request body, so a reviewer looks at it deliberately.
- Resolve conflicts by rebasing on `main` and re-running the generator where one exists, not by taking one side wholesale.

And the rule that matters most: **if a plan needs a file that is in neither list, stop.** Either the file belongs in `shared_paths` — ask, in the Handoff notes, for a small follow-up that adds it — or the dependency graph is wrong. Do not "just touch it". This repository's own history is full of open questions that begin exactly there, and each one is a file that did not silently change under another session.

### Reading outside your paths

Ownership constrains writing, never reading. Reading anything in the repository is fine and expected — you cannot write a lesson about a plan system without reading `plans/README.md`.

When the thing you need to read is outside the repository altogether, `--add-dir` adds working directories for Claude to read and edit; the docs note it "grants file access" but that Claude Code "doesn't discover most `.claude/` configuration from these directories", and that `permissions.additionalDirectories` in settings makes the addition persist across sessions. Use it to point a session at a sibling checkout it must read; do not use it to reach into another plan's worktree and edit.

The worktree listing is the picture worth keeping: three directories, three branches, one `.git`. Each session opens one of them and cannot see the others' uncommitted work — which is exactly what you want, because the only channel between them should be a reviewed, merged commit.

## Anti-patterns

**Isolating without partitioning.** Two worktrees, two sessions, same file: you traded a lost edit for a merge conflict. _Fix:_ make `owned_paths` disjoint before you create either worktree — the docs' own advice for agent teams is to partition so each worker owns a different set of files.

**Borrowing a file from another plan's worktree.** It works, right up until that plan's branch changes and your copy is silently stale. _Fix:_ treat the need as a missing `depends_on` and write it into Handoff notes.

**Rewriting a shared file to "clean it up".** A reformat of a shared registry conflicts with every other open branch at once. _Fix:_ append-only, one hunk, no reordering, and call it out in the PR body.

**Reusing one checkout for several sessions "just for a minute".** Two agents editing one tree is the exact failure worktrees exist to prevent, and the second edit usually wins silently. _Fix:_ one checkout per session, always.

**Forgetting that a fresh worktree is a fresh environment.** A worktree has no `node_modules`, no `.env`, no build cache, and a session that assumes otherwise fails confusingly. _Fix:_ run the install, and use `.worktreeinclude` for the gitignored files a session genuinely needs.

**Leaving worktrees behind after the merge.** Stale worktrees accumulate, and a lock left by a killed session can make `git worktree remove` refuse. _Fix:_ `git worktree remove` after the squash merge; `git worktree unlock` first if git refuses because the worktree is locked.
