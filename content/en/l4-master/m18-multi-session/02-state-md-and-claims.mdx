## Objectives & prerequisites

By the end of this lesson you can:

- Say why the project's status file must be **generated** from plan frontmatter and never hand-edited, and what goes wrong when it is not.
- Describe what "claimable" means precisely: `todo` (or stale), all dependencies `done`, and no `owned_paths` overlap with an active plan — and say what a staleness check is measured against.
- Run the whole claim sequence — `next`, `claim`, push the branch — and explain why an unpushed claim does not exist.
- Recognise a stale claim, decide whether to reclaim it, and do so with `--force` without discarding the previous session's work.
- Tell the difference between coordination that belongs in files and coordination that belongs in a message.

**Prerequisites.** Lesson 01 of this module, and a clone of the lab repository. Every transcript below is a real run.

<WhenNotToUse>
  A generated status file earns its keep when the number of plans exceeds what you can hold in your
  head and the number of sessions exceeds one. Below that, it is a second copy of information you
  already have. Do not build one for a two-plan repository — the lab repository in this lesson keeps
  a hand-maintained `STATE.md` on purpose, and says so in its own header comment, because a repo
  that small does not earn a generator. Do not use a claim protocol as a substitute for talking to
  colleagues about who is doing what; it coordinates sessions, not people. And do not reach for it
  when the sessions are not actually independent: work that must be done in one order by one context
  wants a checklist inside a single session, not five plan files.
</WhenNotToUse>

## Concept

### Generated, not written

`STATE.md` in this repository begins with a line that is the whole design in one sentence:

<CodeBlock title="STATE.md, first lines">

```markdown
# STATE.md — Claude Code Training

<!-- Generated by `node tools/plan/cli.ts state` from plans/PNN-*.md frontmatter. Do not edit by hand. -->
```

</CodeBlock>

Everything in it — milestone counts, the claimable list, who holds what, which plans are blocked and why, every open question — is derived from the frontmatter of `plans/P*.md`. The generator is deterministic: the same plan set always produces a byte-identical file. That property is what lets CI fail a pull request whose `STATE.md` is stale, and it is why the file is safe to trust.

Hand-edit it and you have created a second, competing source of truth that will diverge on the first status change nobody remembered to mirror. The lab repository for this lesson demonstrates the honest version of the compromise: it keeps `STATE.md` by hand because two plans do not justify a generator, and its header comment admits that "it is possible … for it to drift from `plans/*.md`. Cross-check `plans/*.md`'s frontmatter if in doubt."

### What "claimable" means

The claim rule is deliberately mechanical, so that two sessions computing it independently reach the same answer. A plan is claimable when **all three** hold:

1. `status` is `todo` — or `in_progress` but **stale**, meaning its `updated_at` is more than 24 hours old. What that age is measured _against_ is the subtle part — every command measures it the same way, and the next section spells out what that reference point is.
2. Every id in `depends_on` has `status: done`.
3. None of its `owned_paths` overlaps the `owned_paths` of a non-stale `in_progress` or `review` plan.

A session that answers correctly from frontmatter alone is telling you the rule is written down somewhere it can find, rather than living in whoever built the tool.

### The claim protocol

There is no lock server, no database and no scheduler. The claim is a commit, and the arbiter is the git remote.

<CodeBlock title="Claim a plan">

```bash
git fetch origin && git checkout main && git pull --ff-only
node tools/plan/cli.ts next
node tools/plan/cli.ts claim P36 --owner opus-p36-2026-09-07
git checkout -b plan/36-l4-m19-visual
git add plans && git commit -m "chore(plans): claim P36"
git push -u origin plan/36-l4-m19-visual
```

</CodeBlock>

`claim` sets `status: in_progress`, writes `owner`, bumps `updated_at`, regenerates `STATE.md`, and prints the exact next commands:

**An unpushed claim does not exist.** The pushed branch is the only thing another session can see; until it is on the remote, a second session running `next` on up-to-date `main` will still be offered the same plan. When two sessions race, the first pushed branch wins, and the loser fetches, sees the branch, and picks something else. Locally, the tool refuses a second claim outright:

### Stale claims

Sessions die. A machine sleeps, a terminal closes, a run is cancelled — and a plan is left `in_progress` with an owner nobody can reach. The answer is an age: an `in_progress` plan whose `updated_at` is more than 24 hours old is **stale**, appears in `next` marked `[stale claim by … — use --force]`, and can be taken over:

<CodeBlock title="Reclaim a stale plan">

```bash
node tools/plan/cli.ts claim P27 --owner sonnet-p27-2026-09-08 --force
```

</CodeBlock>

**Twenty-four hours since when?** Against `newest(s)`, the largest `updated_at` anywhere in the plan
set — never the machine's wall clock. Nothing depends on any one machine's clock, so two sessions
reading the same commit always reach the same verdict. `plans/README.md` §3 specifies this once, and
every command that touches staleness computes it the same way: `tools/plan/state.ts` and
`tools/plan/check.ts` use `newest(s)` for the `STALE` marker in the generated `STATE.md` and for
`check`'s view of which plans are active, and `tools/plan/cli.ts` uses the same `newest(s)` reference
for `next` and `claim` — the two commands a session actually uses to take work.

<Callout>
  This used to be a real gap, not a hypothetical one. An earlier version of `tools/plan/cli.ts`
  passed the wall clock into `next` and `claim` instead of `newest(s)`, so the clock-free guarantee
  the contract states did not hold for the commands a session actually types. In practice the wall
  clock and `newest(s)` sit minutes apart on an active plan set and agree, so the gap was invisible
  day to day — but on a quiet plan set, or between machines with skewed clocks, it meant a
  fast-forwarded clock could "steal" a claim that was still fresh by the contract's own measure, and
  a lagging one could refuse to reclaim a plan that had been abandoned for weeks. The fix makes
  `next` and `claim` share the same `newest(s)` reference point `check` and `state` already used — a
  contract-vs-implementation mismatch worth writing into a plan's `open_questions` the moment you
  spot it, not smoothing over.
</Callout>

`--force` is deliberate friction. Before you type it, read the plan's branch and its Handoff notes and **continue from there** — reuse the branch, do not start over. A stale claim usually means work exists that was never merged; throwing it away is the expensive mistake, not the slow one.

### When a message is the right tool instead

Files coordinate state. They do not coordinate _now_. Claude Code has a separate mechanism for that: cross-session messaging, where Claude uses `ListAgents` to see which of your sessions it can reach and `SendMessage` to deliver text to one by name, and `/list-agents` (also `/peers`) shows you the same list. The docs name the parallel-worktree case explicitly: "when sessions work the same repository in separate worktrees, Claude can tell the other sessions what landed."

Use each for what it is. A claim, a status, a decision and a hand-off are durable facts and belong in committed files, where a session that starts tomorrow will still find them. "I just pushed the schema change, rebase before you continue" is a fact with a half-life of minutes, and belongs in a message. The docs are also clear about the boundary: a message from another session "never counts as your consent, so it can't answer a pending permission prompt on your behalf", and the receiving Claude is instructed never to change permission settings or `CLAUDE.md` because another session asked.

One detail in the second recording is worth a pause. The session read `STATE.md`, found its instruction to "Claim with `node scripts/plan.mjs claim P01 --owner <name>`", and repeated it faithfully. At that tag `scripts/plan.mjs` does not exist at all — it arrives three lessons later, at `lesson/m18-05-solution`, and even then it only lists claimable plans and never claims one. The hand-maintained file described a command the repository did not have, and a careful reader passed it on.

That is exactly the failure mode a generated file removes: when the status file is derived from the same frontmatter the tool reads, it cannot drift into describing a tool that is not there.

## Anti-patterns

**Hand-editing the generated file.** Someone "just fixes" a count, CI's freshness check starts failing for unrelated reasons, and people learn to ignore it. _Fix:_ every change goes through `claim`/`status`, then `state`; treat a stale `STATE.md` as a build failure.

**Claiming without pushing.** The claim exists only on your machine, so a second session takes the same plan and both of you write the same files. _Fix:_ push the branch in the same breath as the claim — it is the visible claim.

**Reclaiming a stale plan by starting over.** The previous session's branch usually contains most of the work and all of its reasoning. _Fix:_ read the branch and the Handoff notes first, reuse the branch, and say in your own notes what you inherited.

**Treating an old timestamp as an abandoned plan.** Twenty-four hours of silence during a long, expensive run is not abandonment. _Fix:_ staleness makes a plan _reclaimable_, not _free_ — check the branch for recent commits before forcing.

**Coordinating durable facts over messages.** "I've taken the auth plan" told to another session is invisible to the session that starts tomorrow. _Fix:_ durable facts go in the plan file and the commit; use messaging for the volatile "rebase now" kind of update.

**One plan per person.** Assigning plans to humans reintroduces the bottleneck the system exists to remove. _Fix:_ `owner` is a session name; anyone free takes whatever is claimable.
