## Objectives & prerequisites

By the end of this lesson you can:

- List what a handoff note must record for a different session to resume a plan without asking a question.
- Write a note that reports evidence rather than assertions, and that names the decisions taken where the plan was ambiguous.
- Use `status PNN blocked --reason` so the blocker lands in the plan file and the generated state view at the same time.
- Tell the difference between a handoff note, an open question and a follow-up plan, and put each in the right place.
- Recognise the notes that fail: the empty placeholder, the summary of the diff, and the optimistic "should pass".

**Prerequisites.** Lessons 01–04 of this module. The lab uses the lab repository's `lesson/m18-05-start` and `lesson/m18-05-solution` tags.

<WhenNotToUse>
  A handoff note is for work that outlives one session. It is not a changelog — the commits already
  say what changed, line by line, and repeating them wastes the one place where the *non-obvious*
  belongs. It is not a code comment either: reasoning that belongs next to the code should live next
  to the code, where the next reader of that function will find it. And skip the ceremony entirely
  for a change you are about to merge yourself in the next five minutes with nobody else in flight —
  in that case the pull request body is the handoff, and duplicating it into the plan file is
  filing, not communication.
</WhenNotToUse>

## Concept

### The question the note answers

Every plan file ends with `## Handoff notes`, and a fresh plan carries only a placeholder:

<CodeBlock title="The unfilled section">

```markdown
## Handoff notes

- _Filled by the executing session: what changed, decisions, follow-ups, blockers._
```

</CodeBlock>

The section answers one question: **what does the next session need that it cannot get from the diff?** The diff already says what changed. It does not say what you tried that failed, which of two readings of an ambiguous requirement you took, what you verified and how, what you deliberately did not fix, or what surprised you.

This matters more here than in a team of people, because the next session may have no memory of this one at all. Claude Code's own best-practice guidance points the same way: a spec is useful because "the new session has clean context focused entirely on implementation", and it asks you to "have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned … Reviewing evidence is faster than re-running the verification yourself, and it works for sessions you weren't watching."

Read what that note is doing:

- **What shipped**, in terms of the thing produced, not the files touched.
- **A real inconsistency found and deliberately not fixed**, with the reason: fixing it means editing a file that belongs to a different plan. The finding is preserved instead of being lost or silently acted on.
- **Verified for real**, naming the command and its result — `npm test` (still 20/20) — and what was checked by hand.
- **Follow-ups**, concrete enough to become a plan: the fix, its single `owned_paths` entry, and the observation that it is disjoint from both existing plans.
- **Status**, and what the next reader is expected to do.

The other plan's note in that tag adds one more category worth copying: a decision, with its reason ("used commander's own `.version()` rather than a bespoke handler — it also gives `-V` for free"), and a failure worth recording ("learned by first writing the test against it and watching it fail"). A wrong turn documented once is a wrong turn nobody repeats.

Here is this lesson's worked example prompt, the one to run before you close a plan:

```text
Read this plan file and the diff on this branch. What would a different
session need to know that neither of them says? Write it as the plan's
Handoff notes.
```

### Blocked is a status, not a note

When you cannot continue, the status change and the note are one action. `status PNN blocked --reason "…"` refuses to run without a reason, appends it under `## Handoff notes` as a dated line, and regenerates the state file so the blocker is visible to everyone:

<Transcript
  src="content/_shared/transcripts/m18-multi-session/05-handoff-notes/02-status-blocked.txt"
  range="2-16"
/>

Two things travel together there. The plan file gains a permanent `- Blocked (2026-09-07): …` line, and the generated `Blocked` table in `STATE.md` picks up the newest such line automatically. Nobody has to remember to tell anyone.

The contract asks a blocked reason to say three things: what blocks you, what you tried, and what you need. The third is the one people leave out, and it is the only one that is actionable by somebody else.

### Handoff note, open question, or follow-up plan?

Three places, three lifetimes. Getting this wrong is how findings disappear.

| It is…                                                     | Put it in                            | Because                                                                |
| ---------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------- |
| Something the next session working _this plan_ needs       | `## Handoff notes`                   | It is scoped to this plan and read when the plan is picked up          |
| A doc conflict or product question the _owner_ must settle | `open_questions` frontmatter         | The generator surfaces it project-wide, next to its plan id            |
| Work that should happen but not here                       | Handoff notes, phrased as a proposal | Plans are curated; a session does not create new plan files on its own |

The escalation ladder for a blocker is worth memorising. A **missing dependency**: name the plan id that should provide it, or add an `open_questions` line saying no plan owns it. A **doc conflict**: prefer the curriculum document for scope questions and the decisions register for anything already decided; if neither covers it, record the question and continue with the most conservative reading — never change a recorded decision yourself. An **owner action** such as a secret or an approval: write the exact action needed and pick a different plan.

### And when a message is better

A handoff note is durable and asynchronous by design. When the other session is running _right now_ and the fact has a half-life of minutes — "I've just pushed the schema change, rebase before you continue" — cross-session messaging is the right channel: Claude uses `ListAgents` and `SendMessage` to deliver text to one of your other sessions by name, and the docs call out the parallel-worktree case directly. Note the boundary the docs draw: the receiving Claude is told the message came from another session and not from you, and it "can't approve anything" and is instructed never to change permission settings or configuration because another session asked.

So: durable facts in files, volatile ones in messages. A decision recorded only in a message is a decision the next session will never see.

## Anti-patterns

**The placeholder left in place.** A merged plan whose notes still say "_Filled by the executing session_" has thrown away everything that session learned. _Fix:_ treat filling it as part of moving to `review`, not as paperwork afterwards.

**Summarising the diff.** "Added three files and updated the tests" is already in `git log`. _Fix:_ write what is _not_ in the diff — the decisions, the dead ends, the things you chose not to do.

**"Tests should pass."** Either you ran them or you did not, and the difference is everything. _Fix:_ name the command and the result, as the docs ask: show evidence rather than asserting success.

**Fixing something outside your paths because you found it.** The finding is valuable; the silent edit is not. _Fix:_ record it in the notes, propose the follow-up with its own `owned_paths`, and leave the file alone.

**A blocker recorded only in a message or a commit.** Nobody reading `STATE.md` will ever see it, which means it blocks the project quietly. _Fix:_ `status blocked --reason`, so the plan file and the generated view move together.

**A blocked reason with no ask.** "Waiting on the API docs" tells nobody what would unblock you. _Fix:_ say what blocks you, what you tried, and what you need — the third part is the actionable one.
