## Objectives & prerequisites

By the end of this lesson you can:

- Navigate a real, running plan system: 48 plan files, a generated status file, and a CLI that owns both.
- Read every section of a generated `STATE.md` and say what decision each one supports.
- Interpret the open-questions list as the system's most valuable output rather than a backlog of failures.
- Decide which parts of this pattern are worth copying into a project of your own, and which are overhead you do not need.

**Prerequisites.** The rest of this module. This lesson is a reading exercise against a public repository, so clone it and follow along.

<WhenNotToUse>
  Copying a case study wholesale is the failure this lesson most wants to prevent. This system was
  built for a specific shape of work: a large body of independent, file-partitionable units, worked
  by sessions that come and go, with no one person holding the whole picture. Most projects are not
  that. If your work is a single evolving codebase with three people who talk to each other daily,
  the plan files will be filed and ignored while the real coordination happens in conversation, and
  you will have added a document set that drifts. Take the pieces that map onto a problem you
  actually have — most often disjoint ownership and written hand-offs — and leave the rest.
</WhenNotToUse>

## Concept

### What is on disk

This website is built from a public repository whose entire working method is committed alongside its content:

<CodeBlock title="The coordination surface">

```text
plans/README.md          the contract: file format, lifecycle, claim rules, shared-file rules
plans/PNN-slug.md        48 work orders, one per unit of work
STATE.md                 generated; never hand-edited
tools/plan/cli.ts        state | next | claim | status | check | show
DECISIONS.md             100 owner decisions, cited as (Dnnn), never re-litigated in a plan
docs/CURRICULUM.md       the authoritative map every content plan reads and none of them edits
research/                the only source for "what the tool does today"
```

</CodeBlock>

Three things about that list are worth more than the list itself.

**The contract is a file, not a habit.** `plans/README.md` states the rules a session must follow, and the CLI enforces the mechanical ones. Rules that live only in someone's head cannot be followed by a session that starts tomorrow.

**Decisions are separated from plans.** A plan may cite a decision and may propose a change to one, but never edits the register. That separation is what stops fifty sessions from each re-deciding the same question slightly differently.

**Facts have a single owner.** Every claim in a lesson traces to a research file or to a URL fetched while writing. "Never write from memory" is enforceable only because there is one place the memory is supposed to live.

### The open-questions list is the interesting part

At the point these captures were taken, the plan set carried 58 open questions. That number looks like a problem and is the opposite of one.

<Transcript
  src="content/_shared/transcripts/m18-multi-session/06-this-repo-as-example/02-state-sections.txt"
  range="12-21"
/>

Every entry is a moment where a session hit something the plan did not answer and **wrote it down instead of guessing**. Read a few of them in the real file and a pattern appears: they are overwhelmingly about ownership. A plan needed a file that belonged to a different plan; a document said one thing and the live documentation said another; a script the rules assumed exists did not. Each one is a small piece of the system telling the truth about itself.

A plan system with no open questions is not a system where everything was clear. It is a system where sessions guessed.

### The thing that makes it work

The property everything else serves is the one from lesson 01: **a session resumes from repository state alone.** You can test any coordination system against it. Point a session with no context at the repository, and see whether it can work out what to do:

Two files read, and it produced the claim command, the branch name, the worktree convention, the install step, the reading order, the dependency check, and the full list of what it may not touch — including the distinction between an owned path and a shared, append-only one. Nothing in that answer came from a human.

Here is the worked example prompt to run against your own project once you have built something similar:

```text
Read this repository's coordination files. If you were a new session with no
context, what would you work on next, and what are you not allowed to touch?
```

If the answer is vague, the gap it exposes is real.

### The pattern was not invented here

This shape — written work orders, disjoint ownership, generated status, hand-offs — was proven on a prior project before it was applied to this one. That is worth saying because it sets expectations: it is a pattern that emerged from running work this way, not a design someone drew first.

It also means the interesting question is not "is this the right system" but "which parts of it does my project actually need". Three tiers, cheapest first:

1. **Disjoint ownership, written down.** The highest value for the least ceremony. Even a comment at the top of a file saying which workstream owns it prevents most collisions.
2. **Hand-off notes on anything spanning more than one session.** Also cheap, and it is what stops the second session from re-deriving the first one's dead ends.
3. **A generated status file and a claim protocol.** Only worth it when the number of plans exceeds what you can hold in your head and the number of sessions exceeds one. Below that, it is a second copy of information you already have — the lab repository for this module keeps its two-plan status file by hand and says so.

Claude Code's own parallelism features slot into the same three tiers. Worktrees give each session a separate checkout; cross-session messaging carries the volatile facts between them; subagents, agent view and agent teams cover the cases where Claude coordinates the workers rather than you. The plan set is the layer underneath all of them: it is what tells a worker what "its files" are in the first place.

## Anti-patterns

**Copying the whole system into a project that does not need it.** Ceremony that nobody reads still costs everybody time, and worse, it looks like coordination while providing none. _Fix:_ start at tier one and only add a tier when its absence has actually hurt you.

**A plan set nobody generates from.** Plan files whose status is edited by hand, with no generated view, are a directory of stale documents. _Fix:_ either generate the view and check its freshness in CI, or drop the status fields and keep the plans as specs.

**Open questions that nobody triages.** A list that only grows becomes wallpaper, and sessions stop adding to it — at which point they go back to guessing. _Fix:_ triage them on a fixed cadence; each one closes as a decision, a follow-up plan, or a documentation fix.

**Treating the case study as the lesson.** The transferable parts are disjoint ownership, written hand-offs and derived status. The specific file names, the CLI and the milestone letters are this project's implementation. _Fix:_ copy the properties, not the filenames.

**Naming people in plan files.** The moment a plan is "Sam's", the system's ability to route work to whoever is free is gone. _Fix:_ `owner` is a session name, and it is set by the tool.
